# KickOS invariants

> Reference (code-synced). The cross-cutting properties a change must not break,
> extracted by the M1.x close-out review across the arch seam, kernel, per-arch
> backends, and docs. Each is a *checklist item* for future milestones (M2 above
> all): re-audit the whole arch/chip/board matrix against these, hunting both
> drift (one arch violates what the others uphold) and absence (a backend that
> forgot one). `source` cites where it lives in the code.
>
> **Cite symbols, not line numbers.** A `file:start-end` range is wrong the moment
> anything above it moves, and it fails silently -- the range still resolves, just
> to the wrong code. Several citations here pointed into `syscall.cc` at lines that
> no longer existed after the per-domain split (`syscall_thread.cc`,
> `syscall_ipc.cc`, `syscall_obj.cc`, `syscall_mem.cc`). Prefer
> `file (symbol / the thing it guards)`; keep a line range only for a fixed asm
> frame or a struct-offset pin, where the line IS the fact.
>
> The per-arch `applies:` lists below name armv7m / armv6m / rx / xtensa. The
> **rv32imac** (RISC-V: ESP32-C6 + QEMU `virt`) port implements the same
> context-switch, critical-section (`mstatus.MIE`), deferred-switch (CLINT `msip`),
> tickless-timer, and telemetry (`rdcycle`) contracts and must be audited alongside
> them; its FP-save invariants are N/A (soft-float, no FP register file). Treat a
> missing rv32imac mention in a specific item as "audit it too", not "exempt".
>
> The same rule covers the three backends that arrived after this file's lists were
> first written, **armv8a**, **rv64imac** and **x86_64**: a missing mention is
> "audit it too". Where an item below is genuinely N/A for one of them the reason is
> a property of the port and is worth knowing. On **rv64imac** the FP items are N/A
> (`-march=rv64imac...`, `-mabi=lp64`, no FP register file); the TLS items are N/A
> because `ARCH_RV64IMAC` selects no `ARCH_HAS_TLS` (`arch/Kconfig`); the telemetry
> items are unreachable because `virt_rv64` sets `KICKOS_HAVE_TRACE_CLOCK` to 0
> (`arch/riscv/chip/virt_rv64/caps.cmake`), so telemetry cannot be enabled on the
> board; and the deferred-switch band items are N/A because this port books a switch
> requested from ISR context onto the interrupt leg's own exit rather than pending a
> separately-prioritised exception, `arch_switch` from thread context completing
> synchronously.

## Context switch & FP save/restore

- **`switch-frame-matches-init`** -- The frame fabricated by arch_context_init must be byte-identical to what the context-switch save path pushes/pops (same order, same slots), and the arch_context field offsets the asm hard-codes (sp@0, npriv@4, resting_npriv@8, trace_tid@12 on armv7m; sp@0/trace_tid@4 on rx; sp/ps/pc/resume_kind/trace_tid on xtensa) must stay pinned by static_assert. A silent struct reorder or frame-layout drift corrupts the saved SP/privilege on the first switch-in.
  - *applies:* context switch; armv7m, armv6m, rx, xtensa, rv64imac (its `arch_context` offsets are pinned by the `KICKOS_RV64_CTX_OFF_*` static_asserts that `switch.S` reads)
  - *source:* arch/arm/armv7m/arch_armv7m.cc (the arch_context offsetof static_asserts, arch_context_init); arch/arm/armv7m/switch.S (PendSV_Handler, under the saved-frame layout comment it must match); arch/rx/rxv3/arch_rxv3.cc (the arch_context offsetof static_asserts, arch_context_init); arch/xtensa/lx6/arch_xtensa.cc (the arch_context offsetof static_asserts, arch_context_init)

- **`npriv-banked-on-switch`** -- CONTROL.nPRIV is saved and restored per switch as if it were a register (ctx.npriv), NOT reset to the thread's resting posture: a thread blocked mid-syscall runs privileged (the SVC trampoline raised it) and must resume privileged. arch_context_init seeds ctx.npriv AND ctx.resting_npriv from the thread's resting privilege.
  - *applies:* context switch + privilege; armv7m, armv6m (rx uses banked PSW.PM the same way)
  - *source:* arch/arm/armv7m/include/kickos/arch/context.h (arch_context::npriv, arch_context::resting_npriv); arch/arm/armv7m/switch.S (PendSV_Handler's CONTROL save and restore); arch/arm/armv7m/arch_armv7m.cc (arch_context_init, which seeds both)

- **`fp-armv7m-lazy-frame`** -- On an FPU-equipped ARMv7-M part the extended FP state is saved/restored conditionally on EXC_RETURN bit4: PendSV must vstmdb {s16-s31} BEFORE stmdb {r4-r11,lr} (higher addresses) on save and vldmia AFTER the callee pop on restore, so a thread with no live FP context carries no FP frame. Breaking the bit4 test or the push/pop ordering corrupts FP state across a switch.
  - *applies:* context switch, FP save/restore; armv7m with __ARM_FP
  - *source:* arch/arm/armv7m/switch.S (PendSV_Handler's __ARM_FP vstmdbeq / vldmiaeq pair)

- **`fp-rx-full-context`** -- The RX SWINT switcher saves the full context each switch: R1-R15 (single-precision FP lives in the GPR file), FPSW, both accumulators, and -- under -mdfpu -- the DPFPU file (DR0-DR15 + DPSW/DCMR/DECNT via DPUSHM/DPOPM); arch_context_init fabricates exactly those slots with the DPFPU reset posture (DPSW=0x100, DECNT=1). Dropping -mdfpu must leave the slots carrying zeroes, not desync the frame.
  - *applies:* context switch, FP save/restore; rxv3 (rx72m)
  - *source:* arch/rx/rxv3/arch_rxv3.cc (arch_context_init's fabricated frame, the __RX_DFPU_INSNS__ slots); arch/rx/rxv3/switch.S (the dpushm/dpopm blocks in _arch_switch and _kickos_rx_restore)

- **`fp-xtensa-caller-saved`** -- On LX6 CPENABLE is global (CP0 enabled for all threads), so FP data registers are NOT banked by that enable. The cooperative (thread-context) switch relies on the compiler spilling caller-saved FP regs; only the preemptive level-1 interrupt frame saves f0-f15+FCR+FSR. A change that assumes the cooperative path saves FP registers is wrong.
  - *applies:* context switch, FP save/restore; xtensa lx6 (esp32)
  - *source:* arch/xtensa/lx6/arch_xtensa.cc (kickos_lx6_init's CPENABLE write); arch/xtensa/lx6/include/kickos/arch/xtensa_frame.h (F_F0 / F_FCR / F_FSR, the level-1 frame's FP slots); arch/xtensa/chip/esp32/startup.S (the level-1 entry's FP save and restore)

- **`x86-64-no-vector-or-x87-state`** -- No vector (SSE/AVX) or x87 instruction may appear in the x86_64 freestanding text, by hand or by compiler codegen (autovectorization, a libcall lowering to SSE): the context-switch and trap paths save no XMM and no FPU state, and `entry_x86_64.cc` sets CR0.EM and CR0.TS and clears CR4.OSFXSR and CR4.OSXSAVE, so such live state does not survive a switch and executing the instruction is also a #UD or an #NM at ring 0.
  - *applies:* context switch, FP save/restore; x86_64
  - *source:* arch/x86/x86_64/switch.S; arch/x86/x86_64/trap_x86_64.S; arch/x86/x86_64/entry_x86_64.cc; tests/static/check_x86_64_no_vector.sh (the fleet-build gate that holds it)

## Critical section & interrupt-priority bands

- **`irqlock-nesting-safe`** -- IrqLock must record the prior interrupt-mask state and restore exactly that on scope exit (never unconditionally unmask), so nested critical sections compose. Every arch's arch_irq_save/restore returns/consumes the full prior state (BASEPRI word, PSW.IPL field, PS, or the sim's SIGALRM/SIGUSR1 unblocked flags).
  - *applies:* critical section / IrqLock; all arches
  - *source:* kernel/include/kickos/irqlock.h (IrqLock); arch/include/kickos/arch/arch.h (the seam, and which half each arch takes inline); arch/arm/armv7m/arch_armv7m.cc (arch_irq_save) and arch/arm/armv7m/include/kickos/arch/irq_inline.h (arch_irq_restore); arch/rx/rxv3/arch_rxv3.cc (arch_irq_save / arch_irq_restore); arch/xtensa/lx6/include/kickos/arch/irq_inline.h (arch_irq_save / arch_irq_restore); arch/sim/sim.cc (arch_irq_save / arch_irq_restore)

- **`basepri-write-needs-barrier`** -- On ARMv7-M, raising BASEPRI is not self-synchronizing: arch_irq_save must follow the msr with DSB+ISB, else an interrupt can still be taken under the old mask on the next instruction and preempt a critical section. (RX MVTIPL and Xtensa RSIL are self-synchronizing and correctly omit the dance.)
  - *applies:* critical section; armv7m
  - *source:* arch/arm/armv7m/arch_armv7m.cc (arch_irq_save, the msr basepri + DSB/ISB); arch/rx/rxv3/arch_rxv3.cc (arch_irq_save, the bare MVTIPL)

- **`device-irq-in-maskable-band`** -- A device IRQ line's priority MUST be programmed into the IrqLock-maskable band BEFORE the line is enabled, or an IRQ can preempt an IrqLock-held section and corrupt kernel state. Bands: armv7m PRIO_DEVICE=0x30 >= lock 0x20; rx IPL_DEVICE=4 < IPL_LOCK=12; xtensa masks levels 1-3. NVIC IPR / ICU IPR reset to 0 (highest), so the write is mandatory, not optional.
  - *applies:* ISR priority bands; armv7m, rx, xtensa
  - *source:* arch/arm/common/arch_arm_common.cc (arch_irq_unmask, whose kickos_arm_irq_line_prio call precedes the enable); arch/arm/armv7m/isa/arm_isa.h (kickos_arm_irq_line_prio, the NVIC IPR write); arch/arm/armv6m/isa/arm_isa.h (the empty v6-M counterpart, PRIMASK masking every line whatever its priority); arch/arm/armv7m/regs.h (PRIO_LOCK_BASEPRI / PRIO_DEVICE); arch/rx/rxv3/arch_rxv3.cc (arch_irq_unmask, the ICU IPR write ahead of icu_ier_set); arch/rx/rxv3/regs.h (IPL_LOCK / IPL_DEVICE); arch/xtensa/lx6/include/kickos/arch/irq_inline.h (KICKOS_LX6_IRQ_LOCK_LEVEL, the RSIL level arch_irq_save raises to)

- **`deferred-switch-lowest-band`** -- The deferred-switch mechanism (PendSV / RX SWINT / xtensa L1-exit) must sit at the lowest active priority AND below the IrqLock threshold, so a switch requested from an ISR fires only after every other exception tail-chains and only once the requesting critical section releases. armv7m PRIO_PENDSV=0xF0; rx IPL_PENDSW=1 (< IPL_LOCK=12).
  - *applies:* deferred-switch model, ISR bands; armv7m, armv6m, rx, xtensa
  - *source:* arch/arm/armv7m/switch.S (PendSV_Handler); arch/arm/armv7m/regs.h (PRIO_PENDSV); arch/arm/armv7m/arch_armv7m.cc (kickos_armv7m_init's SHPR writes); arch/rx/rxv3/arch_rxv3.cc (kickos_rxv3_init's ICU_IPR_SWINT = IPL_PENDSW); arch/xtensa/lx6/arch_xtensa.cc (arch_switch's g_arch_switch_pending); arch/xtensa/chip/esp32/startup.S (the level-1 exit that consumes it)

- **`lx6-secondary-park-masks-before-waiti`** -- The LX6 secondary core's doorbell park body must raise `PS.INTLEVEL` above 0 (an inlined RSIL to a nonzero level, or a call to `arch_irq_save`) before its `WAITI`, and must contain a `WAITI`. `WAITI` takes `PS.INTLEVEL` from its own immediate, so `waiti 0` is the unmask and the sleep together: an RSIL to level 0 anywhere ahead of the first `WAITI`, or a body with no `WAITI` at all, leaves the park either unmasked (it wakes to anything, not only the doorbell) or absent (it never sleeps).
  - *applies:* SMP park/wake, critical section; xtensa lx6 (esp32)
  - *source:* arch/xtensa/lx6/klock_lx6.cc (kickos_lx6_doorbell_park); tests/static/check_lx6_park_mask.sh (the linked-image gate that holds it)

## Deferred switch & blocking model

- **`arch-switch-may-defer`** -- arch_switch MAY not complete synchronously (ARM/RX pend an exception, xtensa flags g_arch_switch_pending when in ISR); the scheduler must not assume the register swap has happened when arch_switch returns. The switch target crosses only through g_arch_next/g_arch_current -- PendSV saves g_arch_current and ignores the `from` argument.
  - *applies:* deferred-switch model; all arches
  - *source:* arch/include/kickos/arch/arch.h (the arch_switch contract); arch/arm/common/arch_arm_common.cc (arch_switch, g_arch_current / g_arch_next); arch/xtensa/lx6/arch_xtensa.cc (arch_switch's g_arch_switch_pending); docs/reference/architecture.md

- **`no-block-from-isr`** -- Blocking (sem_wait, sleep, any detach_current/block_current path) is legal ONLY from thread context: it relies on arch_switch completing synchronously. From ISR context the switch would defer and the 'blocked' thread would keep running, so detach_current panics when arch_in_isr() is true.
  - *applies:* deferred-switch model, sync primitives; kernel + all arches
  - *source:* kernel/sched/sched.cc (detach_current's arch_in_isr panic, block_current); kernel/sync/sync.cc (wq_block, sem_wait)

- **`exit-parks-for-deferred-switch`** -- exit_current must not run off the end after committing the switch-away: on a deferring arch the PendSV/SWINT can only fire once the IrqLock releases, so the EXITED thread (off the ready set, never rescheduled) must park in an arch_idle_wait loop until the pended switch lands. Running past with the switch merely pending is a known-fixed bug class.
  - *applies:* deferred-switch model, thread exit; armv7m, armv6m, rx
  - *source:* kernel/sched/sched.cc (exit_current's arch_idle_wait park loop)

- **`wake-from-a-thread-that-will-not-run-again-must-not-switch`** -- `sched::wake` returns without rescheduling whenever `kernel().current` is EXITED. That state means `exit_current` is past its own `on_remove`, so the thread can never be picked again and a switch there would ABANDON the rest of `exit_current`: the join and wait-until-last waiters its pool scan has not reached yet would never be woken, and `kickos_terminate` would never run when the last non-idle thread leaves. The scan issues those wakes deliberately BEFORE its single final `reschedule()`, which is the one switch away. `Thread::dying` cannot carry this: a joiner may outrank the dying thread, and the priority clause beside it admits exactly that. The failure is silent and port-dependent -- ARM, RISC-V and RX pend the switch until the enclosing IrqLock releases and survive by luck, while the sim and Xtensa/LX6 take it immediately -- and both orders leave every waiter READY, so only the ORDER of the switch distinguishes them.
  - *applies:* scheduler core, thread exit; every arch
  - *source:* kernel/sched/sched.cc (sched::wake's EXITED clause, exit_current's waiter scan); tests/unit/schedwake/wake_dying.cc (the exit-sweep order arm); ../design-m4.8.2-host-unit-tests.md section 8.3

- **`cap-teardown-sweep-is-preemptible-and-must-resume`** -- `cap_teardown` may be switched out mid-sweep and must therefore be resumable rather than uninterrupted: it releases IrqLock between chunks, the dying thread stays on the ready structure and is not EXITED, so `pick_next` can return it again and the sweep stays TOTAL. Two things switch it out, and the difference matters: an RR slice expiry in `sched::tick_rr`, which reaches the switch from an ISR and so lands at a CHUNK BOUNDARY on every port because the chunk's own IrqLock defers delivery; and `sched::wake` of a strictly higher-priority peer from the teardown arms themselves, which is thread context and is not deferred at all, so on a backend whose `arch_switch` is immediate (the sim, and Xtensa/LX6 outside an ISR) it lands MID-chunk with the slot being closed still live. A FIFO dying thread is reachable only by the second. What makes the exposure safe is not the guard but the surrounding construction: each arm unlinks before it wakes, every object stays pinned by the dying thread's own not-yet-dropped cap, the cross-task reply mint has its own `dying` test, and `ThreadPool::alloc` reclaims only an EXITED slot. **The gaps are real on EVERY death path, a cancel honoured at a park prologue included**: such a prologue reads the cancel under its own bracket and hands that bracket to `sched::exit_current`, which ends it only once `dying` is set, so the exclusion never lapses between the cancel and the mark and the sweep still starts at depth zero. A bracket left beneath the sweep would restore the masked state at every chunk and turn it into one window as wide as the table with the kernel lock held throughout, so `sem_wait` takes the dispatch's resolve bracket rather than nesting its own, and above one kernel core a debug build refuses a sweep entered at a nonzero depth.
  - *applies:* capability teardown, scheduler core; every arch
  - *source:* kernel/syscall/cap.cc (cap_teardown's chunk loop, obj_close_protocol's wake sites); kernel/include/kickos/cap.h (the cap_teardown declaration); kernel/sched/sched.cc (exit_current's end of the caller's bracket); kernel/sync/sync.cc (mutex_force_unlock); tests/unit/schedwake/wake_dying.cc (the chunk-boundary resume arm); tests/unit/parkdeath (a cancelled park sweeps with the gaps an ordinary exit does)

- **`arch-in-isr-truth`** -- arch_in_isr() must read true in ISR/handler context and false throughout syscall_dispatch and ordinary thread context. RX has no IPSR: its g_in_isr counter is bumped ONLY by the device-IRQ/timer first-level dispatchers, never by the syscall INT path, so dispatch reads false as the contract requires. **The SYSCALL TRAP is not ISR context for this purpose on any arch**, because the trap-handler IPC fastpath blocks and performs its own switch there: rv32imac and rxv3 satisfy that by not bumping their software counter on the trap path, and ARM by reading exception 11 (SVCall) as thread context.
  - *applies:* deferred-switch model, syscall contract, IPC fastpath; all arches (rx software counter)
  - *source:* arch/include/kickos/arch/arch.h (arch_in_isr, and the arch_syscall dispatch contract); arch/rx/rxv3/arch_rxv3.cc (g_in_isr, arch_in_isr, and the first-level dispatchers that bump it -- kickos_rx_timer_isr / kickos_rx_default_irq / kickos_rx_swint2); arch/arm/common/arch_arm_common.cc (arch_in_isr's IPSR read and its SVCall carve-out); kernel/syscall/syscall_ipc_fast.cc (the leaf that parks from inside the trap)

## Syscall, privilege & the user/kernel boundary

- **`syscall-in-priv-thread-context`** -- The arch MUST run syscall_dispatch() in privileged THREAD context on the calling thread's own continuation, never in handler/ISR context. A blocking syscall blocks by an ordinary synchronous context switch that freezes the mid-dispatch continuation on a stack the CALLING THREAD alone owns, and resumes it inline when rescheduled -- never on a shared or per-entry one, where a second caller blocked in dispatch would overwrite the first's frozen frame. WHICH of the caller's own stacks it is depends on `KICKOS_KERNEL_STACKS`. At 1 the trampoline relocates sp onto that thread's `ctx.kernel_sp` before calling anything and dispatches BELOW a continuation header laid at the block's top (a3, the caller-return, the resume user sp, an alignment word), so a blocking dispatch freezes on the thread's own kernel block, the header survives the block for free, and `ctx.sp` names whichever of the thread's two stacks it was preempted on. At 0 -- the sim, and the no-MPU armv7m boards that keep a red zone instead -- no block exists, dispatch stays on the caller's own thread stack and the continuation freezes there. On ARM the SVC handler redirects to svc_trampoline (privileged thread mode) in both arms; it does not dispatch inside the handler. On x86_64 the relocation is the entry's own FIRST ACT, and `KICKOS_KERNEL_STACKS` is MANDATORY there (`ARCH_KERNEL_STACKS_MANDATORY`) because no red-zone arm could exist: `SYSCALL` LOADS NO STACK POINTER AT ALL. It copies rip to rcx and rflags to r11, takes rip from IA32_LSTAR and the selectors from IA32_STAR, masks rflags with IA32_FMASK, and leaves rsp exactly as the unprivileged caller left it, so privileged execution begins on a caller-chosen stack pointer. THREE INSTRUCTIONS RUN ON IT AND NONE OF THEM DEREFERENCES IT: `swapgs`, then a store of rsp and a load of the kernel stack, both addressed through the gs base `ring3_init` seated by MSR, which ring 3 cannot write, so no store lands on caller-chosen memory and no load can fault on one. THE BLOCK ITSELF IS REACHABLE AND WRITABLE FROM RING 3 on the current x86_64 posture, measured: it is a `.bss` static of one flat link and sits inside the leaf the grant opens. That does not move this clause, which is about the caller's stack POINTER and not about the block's contents, and it costs nothing further on a posture where kernel RAM is writable anyway. Neither can the three be interrupted: IA32_FMASK names the interrupt flag, so SYSCALL has already cleared it when the first of them executes, and the two classes that flag does not hold off, the non-maskable interrupt and the machine check, carry an interrupt-stack-table slot each, so even those build their frame off the entry's own stack pointer rather than on the caller's. The return is `iretq` and not `SYSRET`, which loads no stack pointer either: the caller's rsp travels in a frame word the shared resume epilogue pops.
  - *applies:* syscall + privilege + resume-inline; armv7m, armv6m, rx, rv32imac, rv64imac, x86_64 (xtensa: plain call, trivially satisfied)
  - *source:* arch/include/kickos/arch/arch.h (the arch_syscall contract); arch/arm/armv7m/switch.S (SVC_Handler's redirect, svc_trampoline's transfer onto ctx.kernel_sp with the continuation header above it, and the KICKOS_KERNEL_STACKS=0 arm below); arch/arm/armv7m/include/kickos/arch/context.h (arch_context::kernel_sp); Kconfig (KICKOS_KERNEL_STACKS, and which boards take 1); arch/xtensa/lx6/arch_xtensa.cc (arch_syscall, a plain call); arch/x86/x86_64/switch.S (kickos_x86_64_syscall_entry's three instructions, and arch_syscall's own cs test, SYSCALL recording no privilege level); arch/x86/x86_64/ring3_x86_64.cc (the IA32_FMASK value and the static_assert that the interrupt flag is in it); arch/x86/x86_64/include/kickos/arch/desc.h (ist_nmi and ist_machine_check); docs/reference/porting.md

- **`trap-return-atomic`** -- Trap/exception return must be atomic with respect to interrupts: no interrupt-takeable window may exist while the return-state (return PC + saved status/privilege) is staged but not yet consumed by the return instruction. Otherwise a nested trap overwrites the staged return PC and the outer return jumps back into its own epilogue at the caller's privilege with the frame half-restored. This is an end-property, not a code shape -- each arch satisfies it by its own mechanism, and a unique path still has to close the window: ARM's exception unstack is hardware-atomic and the syscall trampoline returns by ordinary `bx lr` (no return register live); RX pops PC+PSW in one `RTE`; xtensa sets `PS.EXCM=1` before writing `EPC1`; RISC-V restores `mstatus` (MIE=0) BEFORE `mepc` on the ecall-return path -- which alone reaches the restore with MIE=1, because `.Lecall` sets MPIE=1 to make `syscall_dispatch` interruptible.
  - *applies:* trap/syscall return, critical section; armv7m, armv6m, rx, xtensa, rv32imac, rv64imac
  - *source:* arch/riscv/rv32imac/switch.S (.Lrestore); arch/rx/rxv3/switch.S (RTE); arch/xtensa/chip/esp32/startup.S (PS.EXCM before EPC1); arch/arm/armv7m/switch.S (svc_trampoline `bx lr` + HW exception return)

- **`trap-path-reseats-a-caller-owned-register-before-using-it`** -- A trap path must not compute a kernel address through a register the interrupted thread owns. On RISC-V `gp` is x3, ordinary and writable in U-mode, and this tree deliberately keeps it OUT of the frame and re-derives it on resume, so during a trap it holds whatever the interrupted thread left there. The rv32imac entry therefore seats it from the link-time `__global_pointer$` before its first gp-relative access, under `.option norelax`: the relaxed form of that `la` is itself `addi gp,gp,off`, which reads the very register under attack, so relaxability is part of the property rather than a detail of spelling. **The exposure is per IMAGE and not per board**: an access is gp-relative only where linker relaxation finds the global inside gp's plus-or-minus-2048 window, a distance one image's data layout decides, so a clean entry path on one image says nothing about another and a source reading says nothing at all. What makes it an escalation rather than a wild read is that the value reached that way is the running `arch_context`, whose `stack_hi`/`stack_lo` are what the trusted-trap-stack swap tests the interrupted sp against and whose `kernel_sp` the frame store uses: a forged one passes its own bounds test and aims a privileged store. Same shape as `sp`, which that entry already answers with the `mscratch` swap. `tp` is re-derived after the seat for the same reason, and the ordering between them is load-bearing where the linker turns the second `la` into a gp-relative form.
  - *applies:* trap entry, privilege boundary; rv32imac (rv64imac seats its anchor from a link-time word by a different mechanism)
  - *source:* arch/riscv/rv32imac/switch.S (the seat at trap entry and the re-anchor in .Lrestore); tests/static/check_rv32_trap_gp_anchor.sh (derives the mtvec targets from the vector table's own slots, refuses a gp reference standing before the seat in the LINKED image, and refuses a seat carrying `R_RISCV_RELAX` in the archive's relocations, that last one being invisible in the image because both spellings link to the same instruction stream)

- **`syscall-restores-resting-priv`** -- On syscall return the SVC trampoline must restore the caller's resting privilege (ctx.resting_npriv), NOT hard-code nPRIV=1: a privileged thread issuing a syscall must drop back to exactly its entry posture, never be demoted to unprivileged.
  - *applies:* syscall + privilege; armv7m, armv6m
  - *source:* arch/arm/armv7m/switch.S (svc_trampoline's CONTROL write from ctx.resting_npriv); arch/arm/armv6m/switch.S (svc_trampoline, the same restore); arch/arm/armv7m/include/kickos/arch/context.h (arch_context::resting_npriv)

- **`user-thread-return-via-syscall`** -- An unprivileged thread whose entry returns must route through kickos_user_thread_return (which traps out via the exit syscall); it must NOT run the kernel's kickos_thread_return directly, because exit_current with nPRIV=1 makes IrqLock/BASEPRI a no-op and the switch-path SCS write faults. arch_context_init selects the return address by privilege.
  - *applies:* syscall + privilege, thread exit; armv7m, armv6m, rx, rv64imac
  - *source:* arch/arm/armv7m/arch_armv7m.cc (kickos_user_thread_return, and arch_context_init's return-address selection); arch/rx/rxv3/arch_rxv3.cc (kickos_user_thread_return, and arch_context_init's return-address selection); kernel/thread/thread.cc (kickos_thread_return)

- **`privilege-escalation-gated`** -- Spawning a privileged thread must be gated on the CALLER being privileged (-KOS_EPERM otherwise), and that gate is deliberately a raw `Thread::privileged` test and not an authority bit (see `authority-word-narrows-only`): a capability to create privileged children would be equivalent to holding every authority forever AND being able to hand that on, so narrowing it is meaningless and delegating it is unbounded escalation. There is therefore no path by which an unprivileged thread obtains privilege, and the privileged population cannot grow after boot. The acts that merely need authority are gated on the authority word instead -- irq_claim on `AUTH_IRQ`, ram_alloc on `AUTH_MEMORY` (rejecting with NULL, out of the -KOS_E* scheme, see `syscall-return-abi`) -- so an unprivileged holder passes those and the whole-arena grant stays unreachable regardless.
  - *applies:* user/kernel boundary, syscall; kernel (all arches)
  - *source:* kernel/syscall/syscall_thread.cc (thread_create_call's privileged-child check); kernel/syscall/syscall.cc (the KOS_SYS_IRQ_CLAIM and KOS_SYS_RAM_ALLOC dispatch arms)

- **`selftest-scaffolding-carries-its-production-act's-authority`** -- A `KICKOS_ENABLE_SELFTEST`
  image adds syscall ops the production ABI does not compile at all (`KOS_SYS_IRQ_INJECT`,
  `KOS_SYS_ASPACE_PROBE`, `KOS_SYS_GUARD_ADDR`, `KOS_SYS_REBOOT`). They are not exempt from the
  boundary, and **"root-only" is not a gate this tree can spell**: root is unprivileged from its
  first instruction (`root-unprivileged-idle-alone-privileged`), so a `Thread::privileged` test
  would refuse root itself and every selftest arm with it. The rule is therefore the same one
  `privilege-escalation-gated` states for production: a scaffolding op carries the AUTHORITY of
  the production act it performs. `KOS_ASPACE_OP_CAP_SEED` and `KOS_ASPACE_OP_CAP_OBJECTS` take
  frames out of the pool and install capabilities for them in the caller's own table, which is
  `ram_alloc`'s act and `kos_frame_map`'s, so both take `AUTH_MEMORY`. Where an op has no
  production counterpart the gate is on the narrowest unit the act names rather than on the
  caller: nothing in production raises a controller line from userspace, so `KOS_SYS_IRQ_INJECT`
  is gated on the LINE with the same `-KOS_EPERM` `irq_claim` gives a kernel-owned one, and stays
  reachable from an unprivileged thread at authority 0, which is what an arm simulating a device
  needs.
  **WHAT STAYS UNGATED IS ALSO THE CONTRACT.** An op that only MEASURES (the granule, a frame
  count, a scenario run over an address space of the kernel's own making) is reachable by any
  thread in a selftest image, and so is an inject on a line the kernel does not drive; a driver
  already owes idempotence to a wake with no work, a real device being able to fire at any time.
  `KOS_ASPACE_OP_CAP_SELF_SPACE` is deliberately in that set: it names the space the caller's own
  threads already execute in and allocates nothing, and every act its capability enables is gated
  at that act's own syscall. So a selftest image is a WEAKER environment than a production one in
  exactly this respect, and the scaffolding's own refusals are the whole boundary over ops
  production does not have. Same asymmetry from the other side as
  `stub-is-a-weaker-environment-than-the-real-thing`: do not read a selftest image's posture as a
  statement about the shipping one.
  - *applies:* user/kernel boundary, syscall; selftest images only (every op named compiles out
    of production)
  - *source:* kernel/syscall/syscall.cc (the KOS_SYS_IRQ_INJECT dispatch arm);
    kernel/syscall/syscall_aspace.cc (cap_mint_authorised and the two ops it guards);
    user/apps/common/selftest/main.cc (t_irq_kernel_line_reserved);
    user/apps/common/selftest/selftest_aspace.cc (t_cap_objects)

- **`object-pool-keeps-a-slot-from-any-one-task`** -- The semaphore, mutex, endpoint, tier-1
  IRQ-binding and notification pools are one global `SlotPool` each, and a TASK may HOLD at most
  that pool's own budget of slots of it -- `KICKOS_TASK_SEMAPHORE_BUDGET`,
  `KICKOS_TASK_MUTEX_BUDGET`, `KICKOS_TASK_ENDPOINT_BUDGET`, `KICKOS_TASK_IRQ_HANDLE_BUDGET`,
  `KICKOS_TASK_NOTIFY_BUDGET` -- refused with -KOS_EOVERFLOW. **THE BUDGET IS THE WHOLE CEILING.** `task_object_ceiling` reads
  it and nothing else: no pool width is consulted at a creator, and no second term can be the
  one that actually decides. What carries the structural half is a BUILD-TIME relation instead
  -- each budget is asserted strictly below its own pool's width in `cap.h` -- so **no single
  task can take a pool's last slot**, and a board that narrows a pool without narrowing its
  budget fails the build naming both figures and the fix. That is the denial the bound exists
  to prevent: a supervisor respawning a driver needs an endpoint of its own, and the endpoint
  pool is four slots on every board that does not raise it. **THE THREAT IS ACCIDENT AND NOT
  MALICE**, the party holding those slots being a well-behaved driver that died at its own
  legitimate maximum with its slots still allocated, `sched::exit_current` running
  `cap_teardown` after `task_release` and dropping IrqLock between chunks, so the sweep's EPIPE
  wake can respawn while the pool is at its fullest.

  **FIVE FIGURES AND NOT ONE**, because the pools are sized apart on purpose (16/8/4/8/8 by
  default). A single budget would be forced down to the narrowest charged pool minus one, so
  the endpoint pool would set the semaphore allowance; buying a task more semaphores would then
  cost endpoint, mutex and IRQ `.bss` that nothing uses (`STATE.md` carries the measurement that
  decided it). A board that narrows a pool therefore states the matching budget in its defconfig
  (`bluepill-c8`,
  `f302nucleo`), and a partition that widens the endpoint pool raises the endpoint budget with
  it, its AMP ports being seated in root's table from boot and counted from then on.

  **THE CEILING IS A COMPILE-TIME CONSTANT AND NOT PER-TASK STATE.** `Task` carries no budget
  field, so no creation site owes a seed it could forget, and no stored copy can drift from the
  Kconfig it was taken from. A pool this charges is **either 0 or wider than its budget**, and
  the budget floor of 1 makes that refuse a pool of exactly one slot too, where the ceiling
  could only ever be 0 and the pool would cost `.bss` nothing could allocate. A separate assert
  in `instance.h` bounds all four widths at 32, a hold set being a `uint32_t` of pool slots,
  and the Kconfig ranges are narrowed to match.

  **THE UNIT IS A HOLD, NOT A CREATE, AND THE UNIT OF A HOLD IS A POOL SLOT.** What a task
  holds is DERIVED at the admission from the capability tables of its live members AND from the
  two references a BINDING keeps past the capability that made it: every charged entry in every
  such table marks the pool slot it names, each member's `Thread::notify_bound` marks the
  notification it is bound to, each held `CAP_IRQ` marks the notification its binding raises
  into, and the ceiling is compared against how many DISTINCT slots were marked. So two capabilities on one object cost a task
  one, which is what the pool actually gives up; a capability delegated into a task counts
  against THAT task and not against whoever created the object; and a capability the kernel
  seated (a console stdout copy, an AMP port) counts exactly as an own-create does. **A
  capability whose object is DEAD but whose slot is still allocated counts as well**, that
  holder being exactly why the slot is not free; one whose slot has already been freed counts
  for nothing, the handle no longer resolving. **A BINDING IS COUNTED BECAUSE IT HOLDS THE
  OBJECT ALIVE**, which is the point of its own reference
  (`notification-is-the-delivery-object`): read off capabilities alone, the charge would
  disappear at the binder's close while the pool slot stayed allocated, and a task could hold
  the whole notification pool from inside its budget one bind at a time -- reserve included, so
  a supervisor could no longer create the notification a driver restart needs. The charge lasts
  exactly as long as the reference: a `kos_notify_unbind`, the binder's death, or the close of
  the last `CAP_IRQ` naming the line gives it back. **A CLIENT THEREFORE OWES A CLOSE ON
  -KOS_EPIPE**: the peer closing does not free this side, so a client that falls back on a dead
  endpoint and keeps the capability strands that pool slot for its own lifetime, and the charge
  above is what makes the leak visible instead of billing it to a task that has already died.
  Keyed on -KOS_EPIPE alone: -KOS_EBADF is a route that was never published and has nothing to
  close, and a zero-byte answer is a LIVE endpoint whose receiver had no buffer, so a fallback
  closing on every non-positive return throws a working route away. The three console clients
  in the tree do this (`user/src/newlib_stubs.cc`, `user/include/kickos/sys/emit.h`,
  `tests/tap/tap.cc`), and `emit.h` names them as one policy that must stay in step. **Nothing
  records a charge anywhere**, which is the whole mechanism: there is no refund at a release,
  no sweep at a task's death, and no state that can go stale against the tables. It is also
  why a create/destroy loop stays flat for free and why a recycled task slot cannot inherit
  its predecessor's holds.

  **A DELEGATION IS ADMITTED LIKE A CREATE.** A spawn's grant list is checked against the
  DESTINATION task before any reference is taken (`task_object_admit_grants`), the whole list
  as one take: a grant naming a slot that task already holds costs nothing and two grants
  naming one slot cost one, and the spawn answers -KOS_EOVERFLOW if the list would carry the
  task past a ceiling. Without that check a task at its ceiling passes its objects into a
  second task and takes its whole ceiling again. **A GRANTED LINE IS TWO SLOTS AND NOT ONE**:
  a `CAP_IRQ` whose binding is attached brings the notification it raises into, so the list
  stages that object against the notification ceiling as well, deduplicated against what the
  destination already holds and against the rest of the list. Admitting each grant against its
  own kind alone hands a destination at its notification ceiling a distinct object nothing
  asked it about, and the creates that then see the excess do not undo it.

  **AND THE ATTACH IS ADMITTED AGAINST EVERY TASK HOLDING THE LINE**, not against the
  attacher's alone (`task_object_admit_binding_notify`, asked in `irq_bind_notify`). The line
  can be delegated before it carries an object at all, and the attach that comes afterwards
  seats a hold on every task holding it. The attacher's own task passes trivially, already
  holding the capability it attaches; a peer at its notification ceiling refuses the attach
  with -KOS_EOVERFLOW. Grant admission alone leaves this ordering open and the reverse is
  equally true, so both are checked.

  **THREE CHARGED INSTALLS ARE UNADMITTED, AND NONE IS UNCOUNTED.** `amp_endpoint_mint` and
  `amp_port_bind_local` reach `endpoint_slot_claim` with no `task_object_admit`, because
  neither is a route an untrusted task can spend -- the first is privileged and the privileged
  population cannot grow after boot (`privilege-escalation-gated`), the second runs at kernel
  init and panics rather than returning a refusal. `cap_seat_stdout` is the third: it writes
  slot 0 directly, from `cap_install_defaults` at every spawn and from `cap_console_publish`,
  and asks no admission either. What each installs is nevertheless a capability in a task's
  table and counts against that task from then on like any other hold. The bound is on what an
  unprivileged task can TAKE; the counting is over everything it HOLDS, and the two are
  deliberately not the same set.

  The three are unequal in what they can do to a ceiling, and the difference is whether a POOL
  SLOT is claimed. `cap_seat_stdout` claims none: it is an `obj_ref_inc` on the endpoint the
  console was already published on, so the task's hold count rises by at most ONE and only for
  a task that did not already hold that slot, and the slot it names is spent for the life of
  the image whatever anyone's ceiling says, which is why the SLOT behind slot 0 is a seat the
  image spends and the INDEX is not. **The two AMP minters DO claim, and their claim is
  bounded at BUILD time and not at run time.** `amp_ports_seat` panics on a refusal, so there
  is no run-time answer that could hold root to its ceiling. Two relations carry it, and they
  live apart because they read different declarations at different points of the configure:
  `cmake/amp_partition.cmake` refuses a partition whose crossings do not fit
  `KICKOS_MAX_ENDPOINTS`, and `kickos_endpoint_seats_check`
  (`cmake/cap_table.cmake`, called once the service-list target exists) refuses
  `ports + RETAINED_ENDPOINTS >= KICKOS_TASK_ENDPOINT_BUDGET`. Together with the `cap.h`
  assert that is `ports + retained < budget < pool`. The assert alone does NOT reach it: it
  relates the budget to the pool, and an image whose seats outnumber the budget still sits
  below the pool, so without the CMake relation root boots at or past its own ceiling on a
  board that configured and built cleanly. **THE BUILD SUM IS NOT EVERY SEAT.** A driver an
  APP brings up under `KOS_DRV_EP_RETAIN` keeps a further slot in root, and no build can read
  that posture, so the headroom the strict relation leaves is what those come out of.

  The bound is per TASK and not per THREAD because a thread's own capability table already
  bounds one thread and a thread can spawn siblings to widen that. **IT BOUNDS ONE TASK AND
  NOT THE SYSTEM**: two tasks at their ceilings still empty a pool between them, and
  `KOS_SYS_TASK_CREATE` carries no authority bit, so a single unprivileged caller reaches that
  by minting puppet tasks up to `KICKOS_MAX_TASKS` and seating a thread in each. **So this
  invariant is not a bound on an adversary**, and no shape of it can be while task creation is
  free. Nor would an adversary bound start here: a respawn needs a THREAD before it needs an
  endpoint, and the thread pool carries no quota at all.

  **A DYING MEMBER KEEPS ITS NAME UNTIL ITS TABLE IS SWEPT, and that ordering is what makes
  the bound hold across a death.** `cap_teardown` drops IrqLock every `KCAP_TEARDOWN_CHUNK`
  entries, so a sibling of the SAME task runs while the dying member's capabilities are still
  seated and their pool slots still allocated. Retiring `Thread::task` before the sweep, as
  `sched::exit_current` once did, hid those holds from the admission and handed that sibling a
  WHOLE FRESH CEILING, reserve included, for the length of a chunked teardown: one task, no
  adversary and no delegation was enough to empty a pool. So the name is retired AFTER the
  sweep wherever the death leaves a sibling behind, and only where the death EMPTIED the group
  is it retired before it, the slot being free to re-hand then and a stale name making the
  corpse a phantom member of whatever lands there. Witnessed by
  `tests/unit/taskbudget`'s mid-sweep arm, which drives a real teardown and creates from the
  gap before its first chunk.

  The admission COSTS a walk of the asking task's members' tables, masked: `KICKOS_THREAD_SLOTS`
  pointer compares plus, for each member, its table width in entry reads, and each CHARGED
  entry then costs a `SlotPool::live_index`, which is resolve's own test and no divide. A
  `CAP_IRQ` entry costs one more resolve and a `SlotPool::index_of`, whose division the
  compiler keeps only where `sizeof(Notification)` is not a power of two: it is 16 bytes
  wherever a pointer is 4 and 24 wherever it is 8, so the 64-bit targets pay a divide here and
  no 32-bit one does. It is paid at the five creators and once per spawn with a non-empty grant
  list, never on an IPC or a wait path. The ATTACH pays that walk `KICKOS_MAX_TASKS` times,
  which is the price of asking a question about every holder of a line and not about the
  caller; a task with no live member costs the thread-slot compares alone, and an attach is a
  setup call that no driver makes on a serviced event.
  - *applies:* syscall object pools; kernel (all arches)
  - *source:* kernel/sched/sched.cc (the name retired after the sweep);
    kernel/syscall/cap.cc (`task_object_holds`, `task_object_admit`,
    `task_object_admit_grants`, `task_object_admit_binding_notify`); kernel/irq/irq.cc
    (`irq_bind_notify`); kernel/include/kickos/cap.h (`task_object_ceiling` and the
    five budget-below-pool asserts); CMakeLists.txt (the AMP port count against the endpoint
    budget); kernel/include/kickos/instance.h (`task_object_count`);
    Kconfig and kernel/include/kickos/config/system.h (the five figures and their defaults);
    the five creators and kernel/syscall/syscall_thread.cc (the grant list);

- **`root-unprivileged-idle-alone-privileged`** -- Exactly ONE thread in the system is privileged, and it is `idle`. Root is unprivileged on EVERY board, unconditionally: `ThreadAttr::privileged` DEFAULTS to `false` (`kernel/include/kickos/thread.h`), `kmain` sets `root_attr.privileged = false` explicitly, and `idle_attr.privileged = true` is the only assignment of `true` left. There is no build knob, no preset and no porting escape hatch that restores a privileged root: the knob that once selected the posture was DELETED in M4.5.6, and so was the `FATAL_ERROR` that refused a stale cache entry, so a stale `-D` for it is now SILENTLY IGNORED on an in-tree and an out-of-tree configure alike, with nothing but CMake's generic unused-variable warning. There is no incantation to clear, because there is no guard left to clear. Combined with `privilege-escalation-gated` (the privileged population cannot GROW after boot) the privileged population is therefore fixed at one for the life of the system. **There is no demotion instant**: privilege is a property of the frame `arch_context_init` fabricates and of the region set `thread_create` composes from it, so root is unprivileged from its FIRST instruction -- no window exists in which root runs privileged and then drops. Two consequences a change must not break. (1) Root's authority word is seated UNCONDITIONALLY with `CAP_AUTH_ALL` (`authority-word-narrows-only`): with no ring to short-circuit `cap_check_authority`, a root left at authority 0 would fail every authority gate including its own shutdown. (2) The kernel must never call a kernel-internal function that masks IRQs or touches kernel `.bss` from root's frame -- it faults there and LOSES the diagnostic. That is why returning from `main` panics THROUGH the `KOS_SYS_PANIC` syscall trap and never calls `kpanic` directly, and why the ungated `kos_panic` exists at all. A test asserting anything about a privileged CALLER is unwritable by construction: `idle` runs no tests, which is why `mpu_privileged_guard` was retired rather than fixed, and `user/apps/common/rootfault` makes the stronger claim instead (root TRAPS on a cross-domain write) on every `KICKOS_HAVE_MPU` image. (3) **A privileged thread holds no ADDRESS SPACE**, every privileged spawn resolving to the kernel domain, which carries none: where the backend translates, the low half then still names whichever process was installed last, so the kernel may write NOTHING at an app-half address on such a thread's behalf. That is why the switch path asks `aspace_seated_for` before it primes or seats libc's reentrant state -- both the slot array and the word libc resolves from are the app's, and priming for an unseated thread writes hundreds of bytes into another process's copy of them, which a backend forbidding privileged access to the low half faults on outright. The population being fixed at one makes it survivable today and not correct: it is the SPAWN of a privileged thread that would land the write, and the gate above is the only reason none exists. Witnessed by `reent_seating`, whose positive half asserts the posture is reached at all. The companion property, which every core holds and not only a privileged thread's: **A CORE'S TRANSLATION BASE NAMES THE SPACE OF THE THREAD IT IS RUNNING, OR THE BOOT ROOT**, and ABOVE ONE KERNEL CORE a thread that has passed `task_release` in `sched::exit_current` is running on the boot root (`aspace_install_boot`, called between the stack release and the reference drop). At one kernel core that reroot is deliberately absent, and the property holds by a different route: nothing frees the tables before the last member's `aspace_release`, which activates the boot root itself ahead of the destroy, and a non-last-member exit frees nothing and leaves its own space installed for the sibling that follows it, so no reroot and no non-tagged flush is spent there. So a space installed anywhere implies a live member, which implies a positive refcount, which is the negation of `aspace_release`'s destroy precondition: no core can hold the root of a memberless task, and the peer loop in `aspace_release` is bookkeeping rather than a repair. It has to be a repair-free property and not a repaired one, because that loop clears another core's cached cell and cannot reach that core's translation register. Witnessed by the `KOS_ASPACE_OP_RELEASE_PEER_HITS` counter, which must read 0 -- beside `KOS_ASPACE_OP_RELEASE_RUNS`, since 0 hits is equally the answer for a run in which no destroy ran.
  - *applies:* kernel init, syscall, user/kernel boundary, address space; kernel (all arches), every board
  - *source:* kernel/init/kmain.cc (idle_attr/root_attr privilege + the unconditional cap_seat_authority); kernel/include/kickos/thread.h (ThreadAttr::privileged default); kernel/syscall/syscall.cc (the KOS_SYS_PANIC arm and its noinline message-buffer helper); user/apps/common/rootfault

- **`fault-kills-the-unprivileged-thread-task`** - A fault kills the faulting thread's TASK instead of the system exactly when three clauses hold together: the CPU was UNPRIVILEGED at fault time, it was in THREAD context, and the thread is not already dying. Every other fault panics as it did before. The discriminator is the CPU's privilege, NOT the thread's identity and NOT `ctx.resting_npriv`: syscall dispatch runs privileged on the thread's own stack (`syscall-in-priv-thread-context`), so a fault there is a kernel bug in code the thread merely called and must reach the panic dump. The arch half is `arch_fault_is_user_thread`, whose fallback TU declines, so an un-ported backend keeps the panic path with no edit; the core half re-tests what it can (no current thread, `idle`, `Thread::privileged`) so the rule does not rest on every backend's predicate being exact. `Thread::dying` is set at the top of `sched::exit_current` and NEVER cleared, so a fault taken anywhere in the death path (a re-fault on an overflowed stack is the case that matters) escalates to the panic path instead of looping through the redirect again. The rule is NOT scoped by MPU posture: privilege comes from `arch_context_init` and root is unprivileged on every board (`root-unprivileged-idle-alone-privileged`), so a flat board kills a faulting thread exactly as an enforcing one does and root itself dies with its own task -- its slot reaching `EXITED` is permitted, and `ThreadPool::alloc` retires that slot rather than reclaiming it (`every-syscall-caller-holds-a-pool-slot`); what differs on a flat board is only which accesses fault at all. THE SCOPE IS THE TASK AND NOT THE THREAD: a fault is the one death `sched::exit_current` propagates to the group (`sched::EXIT_FAULTED`), because the faulting thread's siblings share the address space it was writing and no caller is watching a fault. That read as one thread for as long as a plain spawn was alone in its task; a plain spawn is now a thread of the caller's task, so an arm witnessing containment must give its victim a task of its own. Every other death ends one thread: `kos_task_kill` and `kos_task_slay` are the verbs for the group and cancel every member themselves. Which backends may do this is a CONFIGURE-time classification, not an arch name a gate re-derives: `KICKOS_HAVE_PRIV_RING` (per BOARD, since the ARMv6-M privilege extension is optional and Cortex-M0 omits it) gates `KICKOS_FAULT_ISOLATION`, which both selects the seam TUs and, spelled `KICKOS_FAULT_OUTCOME`, is the token the fault gates parse. Reasoning: `../design-m4.7.9-fault-isolation.md` (section 3); porting contract: `docs/reference/porting.md`.
  - *applies:* fault handling, privilege, thread exit; armv7m, armv6m, rv32imac, rv64imac, rxv3, sim (lx6 and Cortex-M0 boards decline and keep panicking; lx6 by HARDWARE, having no privilege ring to read)
  - *source:* kernel/init/fault.cc (kickos_fault_kill_thread / kickos_thread_fault_exit); arch/include/kickos/arch/arch.h (arch_fault_is_user_thread / arch_fault_redirect_to_exit); arch/common/arch_fault_is_user_thread_default.cc (the declining fallback); kernel/sched/sched.cc (exit_current, where `dying` is set); kernel/include/kickos/thread.h (Thread::dying); CMakeLists.txt (the KICKOS_HAVE_PRIV_RING / KICKOS_FAULT_ISOLATION classification); user/apps/common/faultsurvive + tests/integration/check_faultsurvive.sh

- **`fault-kill-path-never-enters-panic`** - Nothing on the thread-kill path may print, and in particular it must NEVER call `kpanic_enter`: that masks interrupts, forces the synchronous writer and reclaims the console permanently and unconditionally-once (`panic-console-probe-independent`), which is exactly wrong for a system that is meant to survive this fault. So the arch handler asks `kickos_fault_kill_thread` ahead of its first output AND ahead of its `kpanic_enter`, `arch_fault_redirect_to_exit` hands the fault facts to `kickos_fault_record` instead of printing them, and `kickos_thread_fault_exit` prints them later in thread context through `kprintf_fault`, which is NOT the ordinary path: `fault-record-is-printed-only-by-its-owner` states the two ways it differs, and both are load-bearing here. A reporter that prints first would kill the console of a system that then keeps running. The rule is about the RECLAIM, not about staying silent: a published console still gets the record, over the driver rather than over the device, which is `fault-record-is-printed-only-by-its-owner`. Reclaiming instead was rejected on register facts, not on taste -- EVERY `arch_console_reclaim` body in the tree clears a UART TX interrupt enable AND reprograms baud, audited over all of them and with no exception, and the shape is the same everywhere: an absolute store zeroing whatever register carries the TX interrupt enable (`C2`, `CR1`, `SCR`, `CTRL`, `IMSC`, `INT_ENA`, `CCR`/`TCSR`) and then a rewrite of the divisor (`BDH`/`BDL`/`C4`, `BRR`, `IBRD`/`FBRD`, `BAUD`, `CLKDIV`, `FDR`/`BRG`). Re-derive the set with `grep -rn "^void arch_console_reclaim(void)" arch/`, minus the declaration in `arch/include/kickos/arch/arch.h`; `chip_esp32c6.cc` and `arch/arm/chip/xmc4800/usic_uart.cc` each carry a conditional store: the former restores a divisor captured in `arch_init`, the latter skips the baud rewrite when `baud_for_periph` resolves none for the live peripheral clock. So it is not reversible from the kernel side and a SCOPED reclaim would silence a live IRQ-driven driver's TX source and park it forever, which is the same hazard `console_on_driver_death` already defers around. A wedged console is strictly worse than a late one. A RAW pre-console localizer counts as output for this rule and moves below the kill test with everything else: `rxv3`'s `KICKOS_RX_MPU_TRACE` mark pokes the SCI6 transmit register directly, which is the very peripheral the console drains, and it interleaves with buffered console text rather than replacing it.
  - *applies:* fault handling, console; armv7m, armv6m, rv32imac, rv64imac, rxv3, sim
  - *source:* arch/arm/armv7m/arch_armv7m.cc (kickos_armv7m_fault_report, the kill test ahead of kpanic_enter); arch/riscv/rv32imac/arch_rv32imac.cc (kickos_rv_fault_report); arch/rx/rxv3/arch_rxv3.cc (kickos_rx_fault_report, the kill test ahead of both kpanic_enter and rx_mpu_mark); arch/sim/sim.cc (on_sigsegv / on_sigill); kernel/init/fault.cc (kickos_fault_record and the deferred print)

- **`fault-record-is-printed-only-by-its-owner`** - The fault facts live in ONE file-scope record, not in per-thread fields, because `Thread` carries no tail padding on any target, so another field would grow every TCB (on a 32-BIT target: 256 bytes where `KCAP_RUN_CHUNKS` is 1, 264 where it is 2, 248 on RXv3; the host sim is 2480 and the figure does not apply there). The `static_assert` pair beside `struct Thread` does NOT enforce those literals: it recomputes the expectation from the target's own `arch_context`, `arch_mpu_region` and `CapRun` sizes and pins only the scalar remainder, plus the absence of tail padding. That record is NOT protected by `fault-kills-the-unprivileged-thread-task`'s dying clause: `Thread::dying` is not set until `sched::exit_current` runs at the END of `kickos_thread_fault_exit`, so the whole window between the exception return and the print is PREEMPTIBLE and a second, unrelated thread's fault can overwrite the record first. The record therefore carries the `Thread*` it was captured for, and a stub that does not own it prints `PC lost to a later fault` and LEAVES IT VALID for the thread that does, rather than printing another thread's PC, status and address. Both threads still die correctly and both still announce themselves by name; the residual cost is that the first thread's PC is lost in a double-fault race, which is accepted (`../design-m4.7.9-fault-isolation.md` section 9.3). A change that widens the dying clause to cover this window would also make a re-fault on an overflowed stack unreportable, which is the case the clause exists for. **The record's TRANSPORT is not the ordinary one, and it may not be**: `console_emit` DROPS every kernel chip write while a userspace driver owns the console, so on the boards whose default service list carries a console driver (`frdmk64f`, `xmc4800-relax`) the whole record was lost while isolation itself worked perfectly -- measured both ways at one tree, `.session/logs/m483-fs-frdmk64f-faultsurvive.log` against `m483-fsk-frdmk64f-faultsurvive.log`. The five print sites therefore call `kprintf_fault`, which differs from `kprintf` in two ways. The first: while the state is USER_OWNED it also hands the formatted line to the published endpoint's ALREADY-PARKED receiver (`cap_console_deliver`), through the kernel's own identity reference on that endpoint rather than through the dying thread's cap table, which a thread spawned before the publish never had seated. It reaches the wire because the DRIVER prints it, which is the only agent permitted to touch a published device at all. The second: it formats into `KDIAG_FAULT_LINE_MAX` bytes and not the 256 an ordinary `kprintf` gets, because this descent runs on the dying thread's own block below the exit red zone and that array is its largest term -- the reserve is `EXITK` on the arches that carve blocks and `EXIT` on the six armv7m presets that do not, and at 256 the array alone outweighed the whole console tail under it. The cost is a fault line past the bound being truncated, which `tests/unit/faultline` bounds by proving every record of the catalogue fits at a 38-character thread name -- more than `KICKOS_THREAD_NAME_MAX` permits, so the fit carries headroom and no shipped name can reach the truncation; a REPORTER STACK of its own was priced against this and refused, because `EXITK` sizes no allocation on any of the 54 declared presets while a per-core array would spend kernel `.bss` on every one of them, and its claim has no refusal arm that keeps the second faulter's announcement. Three properties are load-bearing and each rules out a cheaper variant. It NEVER PARKS, so no fault record can wedge a dying thread on a driver that is mid-write or gone -- which is why `endpoint_send` could not be reused even with a zero timeout, since `park_deadline_arm` floors any non-`KOS_TIMEOUT_NONE` deadline to `KICKOS_TIMER_MIN_DELTA_NS` and switches away. It is NARROW to this one caller, because routing all of `kconsole_write` would relight the kernel debug console post-handover and retire `check_sim_published.sh`'s negative assertion, which is the only proof that a handover happened at all. And ORDER survives without luck: the delivery pops the driver out of `recv`, so a later user `kos_send` finds no parked receiver and parks in `send_waiters`, leaving the driver to emit the record, return to `recv`, and only then take that line -- the `survived > killed` ordering assertion holds under a published console too. **What it still loses, deliberately:** a line dropped when NO receiver is parked at that instant (the faulter was the driver's last receiver, or the driver is mid-write), and a line handed over but never drained because the system shut down before the driver was scheduled (`kickos_terminate` flushes the KERNEL ring only). **A record is up to THREE separate deliveries from five call sites emitting four kinds of line, and only the first is unconditional**, because the first one pops the driver out of `recv` and the second needs it back: what puts it back is the pre-existing rule that a console service's `cfg->prio` is `>=` every stdout client (a rendezvous carries no priority inheritance, D9), so the woken driver preempts the faulting client and re-parks. A console provisioned below one of its clients -- already forbidden for that other reason -- would truncate every fault record to its banner line. RTT is ungated by ownership, so `xmc4800-relax`'s `CONSOLE_BOTH` posture always had the line on the second transport; `frdmk64f` is chip-only and had none.
  - *applies:* fault handling, diagnostics; armv7m, armv6m, rv32imac, rv64imac, rxv3, sim
  - *source:* kernel/init/fault.cc (FaultRecord::owner, kickos_fault_record, kickos_thread_fault_exit, the kprintf_fault sites); kernel/init/console.cc (kprintf_fault's array and kvprintf_route's USER_OWNED arm); include/kickos/diag.h (KDIAG_FAULT_LINE_MAX beside the records it bounds); kernel/syscall/syscall_ipc.cc (cap_console_deliver, beside the endpoint_send arm it mirrors); kernel/syscall/cap.cc (cap_console_target); tests/unit/faultline (the bound holds the catalogue, in both diagnostic postures); tests/integration/check_sim_pubpanic.sh (case 2) and check_sim_faultsurvive_pub.sh (the ordering claim)

- **`fault-frame-untrusted-until-proved`** - A fault fact read from a REGISTER (privilege, cause, fault-status, fault-address) is always valid; a fault frame that lives in MEMORY on the faulting thread's stack is not, and a backend must gate it on `kickos_fault_frame_trusted(frame, bytes)` before it reads a single word. Two failures hand over a frame the thread never legitimately produced: a wild SP, which the bounds test catches, and a stacking abort, which it cannot (hardware stacking decrements SP before it writes, so a stack overflow leaves the frame pointer naming memory that was never written) and which armv7m catches instead on the CFSR bits MSTKERR/MUNSTKERR (bits 4/3) and STKERR/UNSTKERR (bits 12/11), mask 0x1818, read out of the register first. NEITHER test subsumes the other and a backend needs both wherever both apply. `MLSPERR`/`LSPERR` are deliberately excluded from the mask: lazy FP preservation leaves the integer frame valid, so including them would panic a legitimate user fault. `kickos_fault_frame_trusted` fails closed on no current thread, on `idle` and on a thread with no recorded stack, and it is written on the room REMAINING inside the stack so a frame pointer near the top of the address space cannot pass by overflowing the addition. The hazard is not theoretical: an earlier implementation read the stacked IPSR field out of that stale RAM and declined only BY ACCIDENT, because those bytes happened to be non-zero. **A THIRD test exists for a core that cancels the faulting instruction**, where neither of the two above can see an overflow at all: RXv3 restores the cancelled instruction's architectural state (RXv3 ISA UM sec.5.3.1), so the USP reads as it did before the denied push, and the frame sits on the kernel ISP where nothing the thread did can invalidate it. `kickos_fault_below_stack(addr)` answers whether the faulting ADDRESS landed beneath the running thread's stack, which a downward-growing stack makes EXACT for the overflow class; it also fails closed with no recorded stack. Its converse is deliberately imprecise and the cost is measured: an operand access to an address BELOW the faulting thread's own stack base escalates to the panic dump instead of dying alone. A distance threshold instead of the stack base would fail in the UNSAFE direction, since a frame larger than the threshold puts privileged code back on an exhausted stack.
  - *applies:* fault handling, memory safety; armv7m, armv6m, rv32imac, rv64imac, rxv3 (the two RISC-V backends prove the frame with the sibling test `kickos_fault_frame_on_kernel_stack`, their U-mode entry building every frame on `ctx.kernel_sp`; sim: the resume context is the host ucontext on a dedicated signal stack, so there is no guest frame to fabricate)
  - *source:* kernel/init/fault.cc (kickos_fault_frame_trusted, kickos_fault_below_stack); arch/arm/armv7m/arch_armv7m.cc (arch_fault_is_user_thread, the 0x1818 early-out); arch/arm/armv6m/arch_armv6m_fault.cc (bounds test only, no CFSR on v6-M); arch/riscv/rv32imac/arch_rv32imac.cc; arch/rx/rxv3/arch_rxv3.cc (USP containment plus the MPDEA below-stack test, no CFSR analogue); tests/integration/check_faultsurvive.sh (asserts MSTKERR in the overflow arm rather than only that a panic happened)

- **`fault-exit-code-is-not-a-joiner-signal`** - A fault-killed thread exits with `KOS_EXIT_FAULT` (139, `user/include/kickos/sys/abi.h`): that is the process status when it was the last thread live, and it is distinct from `kfault_terminate`'s 132, so a capture tells a survived fault from a panic. A JOINER cannot read it. `sched::exit_current`'s waiter sweep hardcodes the join wake result to 0 for every exit, clean or faulted, and a clean `kos_exit(139)` aliases the code in any case. A supervisor must therefore watch liveness-by-activity rather than a cause: join the watched thread with a deadline, where 0 means it died and -KOS_ETIMEDOUT means it is alive but silent. Making the fault case distinguishable would be an ABI change to the join result, not a fix here.
  - *applies:* thread exit, join, fault handling; kernel (all arches)
  - *source:* user/include/kickos/sys/abi.h (KOS_EXIT_FAULT); kernel/init/fault.cc (the exit_current call); kernel/sched/sched.cc (exit_current's waiter sweep, `w->wait_result = 0`)

- **`every-syscall-caller-holds-a-pool-slot`** -- `idle` is the ONE TCB the thread pool does not seat, and it issues no syscall, so every thread that can reach `syscall_dispatch` occupies a `ThreadPool` slot and `threads.index_of(current())` is therefore never -1 at any syscall. Root is not an exception: `kmain` claims root's slot through `ThreadPool::alloc` before any spawn can run, so root is slot 0 at generation 0 and `handle_for(0)` is the bare handle `0`. Three mechanisms rest on the property and none has a fallback. (1) A `CAP_REPLY` entry names its caller BY POOL HANDLE (`cap_install_reply`), so a caller with no slot could not be named and `kos_call` could not answer it; that is why the non-pool refusal `endpoint_call` used to carry could be deleted rather than widened. (2) `kill_tag_of` derives a thread's kill-gate identity from its slot index and answers the shared `KILL_TAG_BOOT` for anything off-pool, so a second off-pool TCB would silently share one cancel identity with `idle`. (3) `ThreadPool::is_root` is the slot COMPARISON `t == &slots[ROOT_INDEX]`, and `KOS_SYS_EXIT` reads it to send root's exit to `kickos_terminate` instead of `sched::exit_current`. Root MAY die by a kernel-internal route -- a fault, a group cancel, wild-stack containment -- so the slot comparison is not what keeps root's authority out of a stranger's hands: what does is that `ThreadPool::alloc` NEVER RECLAIMS `ROOT_INDEX`. The slot is RETIRED for the life of the system, claimed at boot and never handed out again whether root is alive or dead, so `gen[ROOT_INDEX]` is immutable after boot and no successor can ever answer the comparison. A retired slot keeps its dead occupant's `task` at `nullptr`, which is why `amp_probe_caller_ok` fails closed on a null root task rather than matching -- after root's death the AMP probe is refused to everyone, permanently. The alternative test, `spawner_tag == KILL_TAG_NONE`, is WRONG here because `ThreadPool::alloc`'s reclaim sweep clears an orphaned child's tag to `KILL_TAG_NONE`, so it would shut the system down on any orphan's ordinary exit. What keeps `idle` outside the property is STRUCTURAL, not its body: `kmain` creates it with `cap_run = CapRun{}`, an empty directory, so its capability capacity is 0 and every `cap_lookup` fails `-KOS_EBADF` ahead of any mint, park or send. A change that gives `idle` a run breaks this invariant even if `idle_entry` still only calls `arch_idle_wait`. **Enforcement is two `KICKOS_ASSERT`s and nothing else**: one in `cap_install_reply` for the slot itself, one in `kmain` pinning root's claim to `ROOT_INDEX` so an allocation slipped in ahead of root panics at boot rather than silently redirecting that thread's exit. The RETIREMENT is structural rather than asserted, and deliberately so: the skip is the first statement of `alloc`'s scan, upstream of the `EXITED` key rather than a test racing it, and a second compare beside it would say that the slot can change hands when the skip is what guarantees it cannot. Both are unconditional (`KICKOS_ASSERT` is not debug-gated), but there is no configure-time or link-time check. A new off-pool TCB is therefore a design decision, not an addition: it needs a kill tag of its own and a reply-naming answer before it can issue a syscall.
  - *applies:* syscall, capability object model, thread pool, kill gate; kernel (all arches), every board
  - *source:* kernel/init/kmain.cc (kernel().idle_tcb, its empty cap_run, root's ThreadPool::alloc and the ROOT_INDEX assert); kernel/include/kickos/thread.h (ThreadPool::index_of / kill_tag_of / handle_for / is_root); kernel/syscall/cap.cc (cap_install_reply, the other assert); kernel/syscall/syscall.cc (KOS_SYS_EXIT, the is_root reader); kernel/syscall/syscall_ipc.cc (endpoint_call, which no longer refuses a non-pool caller)

- **`user-args-validated-at-boundary`** -- Every user-supplied scalar must be range-checked or clamped at the syscall boundary before use, and an invalid one returns a negative -KOS_E* code (never panics): priority is bounds-checked before it indexes ready lists / shifts a 1u<<prio bitmap; console len is clamped to 4096; injected/attached IRQ lines are checked against [0,KICKOS_MAX_IRQ); an unknown syscall number returns -KOS_EINVAL. The MPU does NOT make this optional now that it enforces. `syscall_dispatch` runs PRIVILEGED, so it is on the wrong side of the very boundary the MPU checks: an unvalidated scalar becomes an out-of-bounds access by the KERNEL, which the region set permits by construction. Enforcement contains a bad *user* pointer only where it exists: on a flat posture, which is what a board with no MPU backend has and what any board's `flat` variant selects, there is no region set to check against, so `user_readable_ok` / `user_writable_ok` fall through to `arch_user_text_readable` / `arch_user_data_writable`, whose non-enforcing arm must be a WHITELIST of the chip's linker-defined memories (code/rodata extent, and static RAM up to the arena base -- `__kickos_rom_start/_end`, `__kickos_sram_start`, all STRONG references -- absent from `tests/static/weak_allowlist.txt` on purpose -- so a chip that omits them fails the LINK). Admitting "anything outside the arena" instead let an unmapped address through and HARD-FAULTED the kernel inside `kaccess_from_user` (MEASURED on mps2-an386 and mps2-an505: `kos_panic((char const*)0xCCCCCCC0)`, `BFAR=0xccccccc0`). Only these checks contain a bad user *index*.
    THE RULE COVERS THE ACCESS AND NOT ONLY THE CHECK, because the check and the access are not one instruction and nothing keeps a sibling out of the gap between them. `access_copy` reaches every granule through its own `arch_aspace_acquire`, which answers null once that page is unmapped, and `ep_copy` refuses a copy whose two ends are the same memory under one owner. So a range this boundary proved good can be refused at the copy, by two routes that need different amounts of authority: a sibling holding `AUTH_MEMORY` + `CAP_FRAME` + `CAP_ASPACE` can `KOS_SYS_FRAME_UNMAP` the page under a thread PARKED in recv, and -- with no capability whatever -- two threads of ONE task share a space, so one static array is one address for both ends of a rendezvous. NO copy site may therefore panic on false: every one answers a negative -KOS_E* code, and `-KOS_EFAULT` is the code at all of them, the two routes being indistinguishable from a bool. `KICKOS_ASSERT` on a copy would put `kpanic` on the syscall descent as well, which every region board's trap red zone is measured against.
    A REFUSAL IS NOT A NO-OP, and the contract says so rather than pretending otherwise (the `KOS_ETIMEDOUT` precedent in `syscall-return-abi`): the copy stops at the first granule refused, so a PREFIX has landed. What every site owes is that the party holding that prefix is a party told the copy failed -- both ends of a rendezvous are answered, and a receiver already off its queue is answered rather than dropped, never `0`, which would misdescribe an indeterminate buffer as a zero-length arrival. The FAR delivery arms are inside this rule and not beside it: each writes the code to a parked TCB through `Thread::wait_result`, so having no syscall return costs them nothing (`ipc-call-reply.md`). `cap_console_deliver` is the one copy site still answering `0`, and that page carries the reason and the scope. Two shapes owe nothing: a 4-aligned word cannot straddle a granule, so the scalar reads are total; and a stream reports the bytes that reached their destination (`KOS_SYS_KCONSOLE_WRITE` answers a short write).

  - *source:* kernel/syscall/syscall.cc (KOS_SYS_KCONSOLE_WRITE len clamp; the KICKOS_MAX_IRQ checks on inject/unmask/attach; the dispatch `default:` -KOS_EINVAL; cap_out_deliver, console_write_user and user_panic, the three access sites there); kernel/syscall/syscall_thread.cc (thread_create_call prio bounds vs KICKOS_PRIO_MIN/MAX, and its four kaccess_from_user reads); kernel/syscall/syscall_mem.cc (user_range_ok / user_readable_ok / user_writable_ok, and access_copy which is the one access); kernel/syscall/syscall_ipc.cc (the five ep_copy/kaccess sites, every one answering -KOS_EFAULT to both ends); kernel/syscall/syscall_ipc_fast.cc (the copy moved AHEAD of the commit, so its refusal is the fastpath's ordinary fall-through); arch/common/arch_ram_common.cc (arch_user_text_readable / arch_user_data_writable, the non-enforcing whitelist); user/apps/common/panicgate (the wire gate: message, null, wild, oversized); user/apps/common/selftest (ipc_one_buffer_both_ends, recv_buf_unmapped)

- **`syscall-return-abi`** -- A syscall that can fail returns its error as the NEGATED code -KOS_E* (`system/include/kickos/sys/errno.h`); a success -- a handle, a count, or a byte-count -- is NON-NEGATIVE, so `rc < 0` is unambiguously an error and never aliases a valid handle/count. Magnitudes mirror POSIX errno (EPERM/ESRCH/EIO/EBADF/ENOMEM/EFAULT/EBUSY/EINVAL/EMFILE/EPIPE/EDEADLK/ENOSYS/EOVERFLOW/ENOTSUP/ETIMEDOUT/ECANCELED, plus EOWNERDEAD below); the sign is applied at the return site (there is no positive success-variant). KOS_ETIMEDOUT carries a promise beyond the POSIX name: a caller-supplied deadline passed and NOTHING happened FOR THE CALLER, so an expiring KOS_SYS_SEND_TIMED delivered no bytes, an expiring KOS_SYS_REPLY_RECV received none, and an expiring KOS_SYS_CALL_TIMED got no reply. It is NOT a promise that the whole transaction was undone: a call whose request a server had already taken leaves that server holding its one-shot reply capability, and the server's later KOS_SYS_REPLY consumes it and answers -KOS_ESRCH. That residue is bounded but NOT inert -- see `abandoned-reply-cap-cannot-reach-a-later-call`. -KOS_EFAULT carries a residue of the same shape, and for the same reason it is written down rather than engineered away: the code covers a buffer that was never the caller's AND one that STOPPED being reachable mid-call, and in the second case the copy had already moved the granules below the one refused, so a destination the kernel answers EFAULT about holds a head of the new bytes over a tail of the old. It is bounded by KOS_EP_MSG_MAX on the IPC paths and is nothing at all on the scalar reads, a 4-aligned word not straddling a granule. What the code DOES promise is that no party is told a transfer succeeded over a buffer in that state: both ends of a refused rendezvous are answered EFAULT, which is why a receiver whose page went away is not woken with a byte count of 0; the far delivery arms carry that same code on `Thread::wait_result`, having a parked TCB to write and needing no syscall return for it. A MINT has a residue of its own, and a bigger one: `cap_out_deliver` writes the handle after the object exists and the capability is installed, so an EFAULT there leaves the caller holding a capability at an index it was never told, reclaimed when its holder dies. Undoing it was rejected rather than skipped -- `handle_close` is type-agnostic and would free a sem, a mutex or an endpoint cleanly, but the same call serves the THREAD mint, where the child is already RUNNING and no handle close retracts it, so the rollback would read as an undo at one site and be a half one at another. AN UNDISCLOSED ONE-SHOT REPLY CAP IS UNDONE, and it is not a counter-example to that: it has one type, one minter and one retraction, `cap_uninstall_reply`, reached only where `write_recv_info` failed to hand its holder the handle (`ipc-call-reply.md`), where the rollback rejected here would have to be the type-agnostic `handle_close`. The out-pointer still holds the codec's NONE the stub seated before trapping, so the "always written" guarantee is untouched and the caller is never handed a number it cannot spend. THREE exhaustion answers must not be collapsed: -KOS_ENOMEM is a supply that could not be ALLOCATED (an object pool, the thread pool, the RAM arena, the MPU descriptor budget), -KOS_EOVERFLOW at one of the four object creators, or at a spawn whose grant list would carry the destination task past a ceiling, is a supply that EXISTS and that this TASK may not hold more of (`object-pool-keeps-a-slot-from-any-one-task`; the same code obj_ref_inc gives a holder count at its ceiling, one scope down), -KOS_EMFILE is ONE thread's capability table refusing a mint, either because its free list is empty or because it already holds KICKOS_CAP_REPLY_MAX live CAP_REPLY entries (the second fires with free slots) -- opposite fixes (more RAM against a wider declared table), and while they shared a code a full table surfaced as a mislabelled `pool too small` skip. EOWNERDEAD is the robust-mutex case: a mutex ACQUIRED while its prior owner died holding it is still returned negative (-KOS_EOWNERDEAD), which a caller must special-case as HELD. Five syscalls stay OUT of the scheme by return type: ram_alloc returns a pointer (every failure is NULL -- a negated errno cast to a pointer would be non-NULL); cpu_clock_hz/cpu_clock_set return a u64 Hz and KOS_SYS_PERIPH_CLOCK_HZ a u32 Hz, in each case a 0 that already means unknown/no-silicon-clock; and the selftest-only KOS_SYS_GUARD_ADDR returns a raw address. THE TABLE'S CODE LISTS ARE GATED, and while they were not a budget refusal reached the API header and none of the four creator entries beside it: `tests/static/check_syscall_return_codes.sh` (ctest `syscall_return_codes`) reads each `KOS_SYS_*` entry's documented codes against the codes its dispatch arm returns, and fails on a code the arm answers that the entry does not name, and on a creator that charges the task object budget while naming fewer than all three exhaustion answers. It holds ONE direction: an entry naming a code its arm cannot return passes, so does one widened to the whole taxonomy, and a code forwarded through a variable (`return rc`) or handed to another thread's `Thread::wait_result` is invisible to it. So a clean run says nothing was SEEN to be missing, never that an entry is complete.
  - *applies:* user/kernel boundary, syscall ABI; kernel (all arches) + userspace wrappers
  - *source:* system/include/kickos/sys/errno.h; user/include/kickos/sys/abi.h (the return-type notes on the syscalls outside the scheme); kernel/syscall/syscall.cc (every dispatch return site) + the per-domain implementations it calls (syscall_thread.cc, syscall_ipc.cc, syscall_obj.cc, syscall_mem.cc); tests/static/check_syscall_return_codes.sh (the table-against-dispatch gate, and what it does not read)

- **`handle-not-pointer-across-boundary`** -- No kernel pointer crosses the user/kernel boundary: kernel objects (semaphores, threads, IRQ bindings) are named by small integer handles resolved through a single validate-and-resolve chokepoint. Semaphore access migrated to per-thread capabilities at M3 (see `object-access-via-per-thread-cap`); thread and IRQ-binding handles still pack index+generation, and the freeing path bumps the slot generation so a stale handle fails to resolve rather than aliasing a recycled slot (ABA). The kernel must never strlen a user pointer (kconsole_write takes explicit buf,len).
  - *applies:* user/kernel boundary; kernel (all arches)
  - *source:* kernel/syscall/syscall.cc (the KOS_SYS_KCONSOLE_WRITE buf,len arm); kernel/syscall/cap.cc (cap_resolve); kernel/include/kickos/instance.h (the generational slot pools)

- **`object-access-via-per-thread-cap`** -- A userspace-named kernel object (semaphore, PI mutex, or IPC endpoint) is reached ONLY through a per-thread capability, never a global id: KOS_SYS_SEM_WAIT/SEM_POST (and the mutex/endpoint send/recv syscalls) take a cap handle, and cap_resolve validates index/liveness/type/rights then WRAPs to the global object pool -- two generations guard it, the per-thread cap-gen (use-after-close) then the object's own object-gen (use-after-destroy), both u16. Resolve-and-use run under ONE continuous IrqLock, so a concurrent handle_close cannot free the object between resolve and use. An ISR NEVER resolves a cap: irq_claim allocates the binding once and hands irq_event_isr that binding's own address as its pre-bound argument, so the ISR reaches it with no lookup (current() in ISR context is a random interrupted thread's table). B1 placement contract: a freshly spawned child table is all-CAP_EMPTY with cap-gen 0, so handle == index on a fresh table; a spawn-delegated cap i lands at child index i+1 (index 0 reserved), rights narrowed subset-only (child.rights = parent.rights & mask, never widened, requires CAP_TRANSFER), and the whole caps list is validated before the child slot is claimed. Cap handles are opaque, and the old global sem id is gone. The NAME `kos_sem_destroy` survives as a source-compatibility alias of `kos_handle_close` (`user/include/kickos/sys.h`) -- so it no longer means "destroy this semaphore" but "drop MY cap", and the object outlives the call whenever another holder remains. CAP_WAIT and CAP_SIGNAL are enforced at cap_resolve ((rights & need) == need), and that is the only place any USE of an object tests them. CAP_TRANSFER is enforced at the DELEGATE SITE instead -- thread_create_call's grant loop refuses a source entry without it with -KOS_EPERM -- and no cap_resolve call site anywhere passes it as `need`. That is not an inconsistency: CAP_TRANSFER gates the COPY of an entry into a child table, not any use of the object, so there is no resolve that would have anything to ask for. Memory R/W/X stays in the MPU descriptor, not the cap.
  - *applies:* user/kernel boundary, capability object model; kernel (all arches)
  - *source:* kernel/include/kickos/cap.h; kernel/syscall/cap.cc (cap_resolve/handle_close/cap_teardown); kernel/syscall/syscall.cc (the KOS_SYS_SEM_*/MUTEX_* dispatch arms); kernel/syscall/syscall_ipc.cc (endpoint_send/recv/call/reply); kernel/syscall/syscall_thread.cc (thread_create_call's B1 delegation -- the grant loop's CAP_TRANSFER check is the delegate site); kernel/sched/sched.cc (cap_teardown on exit)

- **`own-create-skips-reserved-cap-index`** -- The well-known cap indices [0 .. KICKOS_CAP_FIRST_DYNAMIC) (today [0..2): index 0 = KOS_CAP_STDOUT, index 1 = KOS_CAP_CLOCK) are reserved slots (`system/include/kickos/sys/cap_index.h`). An own-create (sem/mutex/endpoint create) takes the head of the run's free list in O(1) (cap_install -> cap_run_peek_free) and allocates nothing, refusing -KOS_EMFILE on a full table; it can NEVER land on -- and alias -- a reserved index, and the mechanism is NOT a scan floor but that the reserved plane is never THREADED ONTO the list at all (cap_run_free_build starts at KICKOS_CAP_FIRST_DYNAMIC, and cap_run_free_release / cap_run_free_unlink no-op below it), so no pop can hand back a well-known index. A release goes to the list TAIL, so with F free slots each slot's cap-gen advances once per F mints rather than one counter absorbing every mint. A reserved slot is written ONLY by the kernel (cap_install_defaults seats stdout and is the sole writer of index 0) or by explicit spawn delegation (delegated cap i lands at index i+1, so delegated cap 0 lands on the reserved clock index and every further one lands in the dynamic range); cap_install_at rejects index 0 outright. The range is NOT frozen, but every move of it is an ABI break and the two directions have different rules. Renumber DOWNWARD only for a slot NOTHING seats; the table width follows on its own, because the reserved range is one of the four terms ROOT's width is summed from at configure (cmake/cap_table.cmake; the others are the service list's RETAINED_CAPS, the widest app KICKOS_CAP_PEAK and the widest declared peak of concurrent INBOUND reply capabilities), and it is also charged to KICKOS_CAP_CHILD_WIDTH, which every SPAWNED thread gets and which no app declares: the width is per thread, not one number per image. So the usable dynamic count is unchanged with no board edit. Append by raising the last reserved index and KICKOS_CAP_FIRST_DYNAMIC together, which costs one slot on every table in the fleet -- so weigh it first against putting the state in the TCB instead, as the authority word does (`authority-word-narrows-only`). Either way the cap.h static_assert guarantees >=1 dynamic slot survives.
  - *applies:* user/kernel boundary, capability naming; kernel (all arches)
  - *source:* system/include/kickos/sys/cap_index.h; kernel/include/kickos/cap.h (cap_run_free_build / cap_run_free_release / cap_run_free_unlink -- the reserved plane's exclusion from the free list); kernel/syscall/cap.cc (cap_install -- the O(1) free-list pop; cap_install_at -- rejects index 0; cap_install_defaults -- the sole writer of index 0)

- **`authority-word-narrows-only`** -- Axis-3 authority is PER-THREAD STATE that only ever shrinks; it is NOT a capability and has no cap-table entry. Shape: `Thread::authority`, one uint8_t of `CapAuthority` (AUTH_*) bits, sited in the TCB padding before `quantum_ns` so it costs the TCB nothing. It shares no numbering with `CapRights` -- separate enums in separate fields, so neither constrains the other and nothing has to keep them disjoint. It names no pool object, holds no refcount and bumps no generation, which is exactly why it is not a table entry: an entry would spend a well-known index on every board in the fleet (`own-create-skips-reserved-cap-index`) to store eight bits the TCB already had room for. NON-DELEGABLE BY CONSTRUCTION rather than by a refusal: thread_create_call's delegation loop copies CapEntry fields and there is no entry to copy, so no forgery path exists to close and none has to be maintained. A child's word comes from exactly one place, `cap_seat_authority(child, p->authority)` on the spawn path. Monotone in both directions: a spawn seats only bits the caller itself holds (cap_check_authority, else -KOS_EPERM; bits outside CAP_AUTH_ALL are -KOS_EINVAL), cap_seat_authority masks to CAP_AUTH_ALL so a bit no gate reads can never be seated, and KOS_SYS_CAP_NARROW applies `word &= mask`, which can only CLEAR. KOS_CAP_AUTHORITY survives as a PSEUDO-HANDLE and nothing else -- the argument kos_cap_narrow takes to NAME the word, deliberately `0x7FFFFFFF`, whose index field is the all-ones value the codec's capacity rule keeps out of every table, so no table can mint it (cap.h static_asserts the index field, and separately caps KICKOS_MAX_HANDLES at 2^16 - 1). cap_narrow_authority refuses any other handle with -KOS_EINVAL (an object cap's rights are not narrowable in place: dropping CAP_WAIT from an endpoint cap would need obj_close_protocol's recv_holders accounting), and KOS_SYS_CAP_NARROW is deliberately UNGATED (an authority required in order to drop authorities could never be given up). Every gate is a cap_check_authority call site and is true when the caller is privileged OR holds every requested bit, so a privileged caller passes regardless of its word -- but `idle` is the only privileged thread (`root-unprivileged-idle-alone-privileged`) and it calls none of them, so in practice the BITS decide every gate. cap_check_authority is the ONE cap.h entry point that does not require IrqLock: it reads the subject's own TCB byte, written only by that thread or by its parent BEFORE the child first runs, so on a single core there is no concurrent writer -- an SMP kernel must revisit this with the rest of the IrqLock-as-mutual-exclusion contract. The kernel seats root UNCONDITIONALLY with CAP_AUTH_ALL, and the ordering is load-bearing twice: AFTER thread_create, which zeroes the TCB and would wipe the word, and BEFORE sched::start, so the seat precedes root's first instruction. -KOS_EBADF is still reachable and must still be tolerated: a narrow to 0 succeeds and leaves the word 0, so a SECOND narrow has nothing to give up and is refused -KOS_EBADF on a word the caller legitimately emptied itself. A privileged caller lands on the same refusal -- its permission does not come from this word, so narrowing it would be a lie.
  - *applies:* user/kernel boundary, authority model; kernel (all arches)
  - *source:* kernel/include/kickos/thread.h (Thread::authority); kernel/include/kickos/cap.h (CapAuthority, CAP_AUTH_ALL, the pseudo-handle static_assert); system/include/kickos/sys/cap_index.h (KOS_CAP_AUTHORITY); kernel/syscall/cap.cc (cap_check_authority / cap_seat_authority / cap_narrow_authority); kernel/syscall/syscall_thread.cc (thread_create_call's authority validation and its single cap_seat_authority call); kernel/syscall/syscall.cc (the KOS_SYS_CAP_NARROW arm + every cap_check_authority gate); kernel/init/kmain.cc (the unconditional root seat, ordered between thread_create and sched::start)

- **`privilege-only-boundary-m1`** -- The M1 posture: the user/kernel boundary was privilege-only (CONTROL.nPRIV / PSW.PM + SVC trap) with arch_mpu_apply a no-op on every MCU backend, so an unprivileged thread could read/write kernel memory. **SUPERSEDED at M2** (see below): the MCU backends now enforce -- K64F SYSMPU + XMC PMSA + RX72M MPU + ESP32-C6 PMP all proven on silicon (selftest under enforcement + a cross-domain mpu_fault trap on each; the C6 proof covers SRAM/domain isolation -- its peripheral APM open is a follow-on); xtensa/no-MPU parts stay privilege-only. Historical: code written before M2 must not assume isolation.
  - *applies:* user/kernel boundary, MPU; armv7m, armv6m, rx, xtensa (sim enforces via mprotect; xtensa has no per-thread MPU)
  - *source:* superseded -- see `mpu-apply-on-every-switch-in` for the enforcing backends

- **`mpu-apply-on-every-switch-in`** -- The running thread's MPU region set must be (re)loaded on every switch-in and at first start, replacing the whole active set; region granting must be fail-closed (a region not a page-aligned/pow2 sub-range the backend can describe is skipped, never applied). Mechanism: `arch_mpu_apply` stashes the set at the switch decision; the arch/chip `kickos_arch_mpu_commit` programs the hardware from the switch epilogue after the physical swap (the deferred-commit seam, `../design-mpu-commit-deferred.md`). **THE STASH IS ONE CELL, so a commit that is NOT a switch's goes through `arch_mpu_apply_now` and never through apply-then-commit.** `kos_mem_self_grant` must have the caller's widened set live before it returns, and a switch to another thread may already be BOOKED behind it; an apply there overwrites the booked image, and the epilogue then programs the CALLER's descriptors onto the incoming thread, which runs under them until the next switch re-stashes. `arch_mpu_apply_now` programs the given set now and puts the booked image back, masked, so a switch booked inside its own window is not the one the restore drops. Every backend defines it: on a deferred one it is that swap, elsewhere it is `arch_mpu_apply`, which already programmed. `kickos_arch_mpu_commit` is the switch epilogue's entry and nothing else's. NO BACKEND CAN REACH THE BAD ORDERING TODAY, and the fix is the seam saying so rather than each trap path being re-read: PendSV is the lowest-priority exception on both M-profiles and drains at the SVC slow path's exception return, ahead of `syscall_dispatch`; the rv32 `ecall` arm forces `MPIE=1` on the way into the trampoline, so a booked msip is taken at the `mret`; RX's generic arm inherits a thread PSW with `I=1 IPL=0`, so a booked SWINT is taken at the same `rte`. What is left open is a SUPERVISOR caller trapping with the mask already raised, which the ARM and RX slow paths neither clear nor refuse (the ARM IPC fastpath does refuse, on `ICSR.PENDSVSET`), and no such caller exists in the tree. **A COMMIT WRITES THE DESCRIPTORS WHOSE WORDS CHANGED**, which is `mpu-commit-writes-what-changed` below and the one place this tree remembers what it last wrote to a device. What a commit GUARANTEES is unchanged: when it returns, every descriptor holds the incoming set. Under `KICKOS_HAVE_MPU=0` there is no reload at all and no stub call either: `MpuSet::apply` is empty there, which is what a translating board's switch pays for a region set it never programs. A privileged thread gets a permissive background (the whole arena / supervisor-all); an unprivileged thread gets only its explicit set (app code RX + app-data RW-NX + domain region(s) + its own stack). The stack region being PER-THREAD is a region-backend STRENGTHENING and not the portable promise: the set is rebuilt per thread and reloaded per switch-in, so a sibling faults on another's stack here, while a translating backend maps a task's stacks task-wide and a sibling reaches them. Portable code may rely only on the floor, that a thread-scoped grant guarantees access to its HOLDER (`../design-m6-mmu.md` F9). ENFORCED on MCU at M2: SYSMPU (K64F), PMSAv7/v6-M (XMC4800, STM32F411, i.MX RT1062, RP2040 -- the shared armv7m/armv6m PMSA backend), PMSAv8 (RP2350, its own base+limit/MAIR backend), PMP/NAPOT (RISC-V), RX MPU -- K64F/XMC/RX/C6/RP2040/RP2350/RT1062 proven on silicon; sim via mprotect. A chip declares itself enforcement-capable twice, and the pair is checked: `select HAS_MPU` in `arch/Kconfig`, without which the enforcing posture cannot be selected at all, and `arch/<family>/chip/<chip>/mpu.cmake`, which also picks the PMSAv8 backend source. A posture that resolved enforcing on a chip shipping no `mpu.cmake` is a configure FATAL_ERROR, never a silent no-op. A chip MAY also declare thread-INVARIANT fixed regions (`kickos_arm_mpu_fixed`, programmed once into the LOW descriptor slots so per-thread grants in the high slots still override them) -- required on a speculating core, where an unbacked-but-Normal aperture stalls the core fault-lessly.
  - *applies:* context switch, MPU, user/kernel boundary; kernel + sim + the MCU MPU backends (M2)
  - *source:* kernel/sched/sched.cc (switch_book's arch_mpu_apply, and start's first-thread apply); kernel/include/kickos/mpuset.h (MpuSet::apply, empty without an MPU); kernel/thread/thread.cc (region-set build); arch/arm/common/arch_arm_common.cc (the arch_mpu_apply stash, shared by every ARM backend); arch/arm/common/arch_arm_mpu_pmsav7.cc (kickos_arm_mpu_program, the PMSAv7 descriptor writer); arch/arm/chip/mk64f/chip_mk64f.cc (kickos_arch_mpu_commit, SYSMPU); arch/riscv/rv32imac/arch_rv32imac.cc (arch_mpu_apply stash + kickos_arch_mpu_commit, PMP); arch/rx/rxv3/arch_rxv3.cc (arch_mpu_apply stash + kickos_arch_mpu_commit, RX MPU); arch/sim/sim.cc (arch_mpu_apply mprotect)

- **`mpu-commit-writes-what-changed`** -- A commit programs ONLY the descriptors whose words differ from what the hardware already holds, against a per-backend RECORD of those words; a descriptor the record says is current is left standing. THE GUARANTEE IS UNCHANGED (`mpu-apply-on-every-switch-in`): when a commit returns, every descriptor holds the incoming set. **Why the record and not the image pointer.** `MpuSet`'s mutators re-encode IN PLACE (`kernel/include/kickos/mpuset.h`) and thread slots come from a static pool, so the same `arch_mpu_encoded*` can address different words on a later commit: comparing the pending image's ADDRESS against the last-committed one is unsound, and `kos_mem_self_grant` takes exactly that path (`syscall.cc`, `add_enforced_retyping` then `apply_now`). Only a copy of the WORDS answers what stands in the hardware. **The record is a MEMO OF THE LAST WRITE, not a second opinion about the hardware.** The kernel is the only writer of these descriptors, so the hardware holds what this code put there and reading it back would answer nothing the writer did not already know. What the record supplies is the words of the PREVIOUS commit, which nothing else still has: `MpuSet` re-encodes in place and thread slots come from a static pool, so last commit's image is gone by the time this one wants to compare against it. It can therefore go stale in exactly one way, another writer moving a descriptor outside a commit, which is why the invalidation set below is enumerated and held by a gate rather than by convention. The measurement that makes the comparison worth doing at all: `f411disco` (armv7m, PMSAv7, enforcing, 84 MHz) read `MPU_COMMIT 247/247 min=247 n=520039` against an 80/80/232 switch distribution, so the descriptor write cost three times the whole bracketed switch; and the all-or-nothing same-set skip that shipped before this fired 5 times in ~10^6 commits, because every near miss differed in the LAST-APPENDED region, which `kernel/thread/thread.cc` makes the thread's own stack. A switch between two threads of one domain therefore has ONE descriptor to rewrite and seven that already stand. **INVALIDATION IS THE WHOLE CORRECTNESS BURDEN.** A partial commit makes a record/hardware disagreement PERMANENT where a total commit erased it, so every path that programs or suspends a descriptor outside a commit's own loop must clear the record first. The sites: `kickos_arm_mpu_fixed_init` (PMSAv7, which zeroes `MPU_CTRL`, moves the low rows and moves the boundary the per-thread slot index is taken from); `kickos_arm_pmsav8_init` (per CORE, where the descriptors stand at reset and the MAIR indirection changes what an AttrIndx means); the K64F `rgd0_ready` and the RXv3 `mpu_ready` one-shots, which live INSIDE their own commits and are read before the record is, RX's `MPOPI.INV` clearing every region's V bit outright. `tests/static/check_mpu_record.sh` holds the class: a tracked source that writes an MPU descriptor register keeps a record, invalidates it and reads it, or is named in that gate with the reason its backend commits totally. What does NOT invalidate: the HardFault/NMI window of `mpu-bypass-windows-accepted`, which BYPASSES the MPU (no `HFNMIENA`) without moving a descriptor, so the record stays true across it. **One asymmetry is RECORDED rather than fixed**: `mpu_held_invalidate()` clears only `arch_cpu_id()`'s record, while `g_fixed_count`, which the partial path reads as the first per-thread slot index, is chip-wide. On a multicore PMSAv7 part where each core ran the fixed-region init, a core could hold a record taken at a different `k` than the one now in force, and its skip would then compare the right words against the wrong slots. No such part exists, the only chip declaring fixed rows being single-core, and the ARM stash `g_pend_image` is one global against this `[KICKOS_NUM_CORES]` record for the same reason; an M-profile SMP port owes both a per-core form. **WHICH BACKENDS SKIP, and the ones that do not.** PMSAv7 (armv7m + armv6m, `arch/arm/common/arch_arm_mpu_pmsav7.cc`) is the best case: descriptors are individually addressable through `MPU_RNR` at 4 MMIO stores apiece, and a partial commit also writes neither `SCB_SHCSR` nor `MPU_CTRL` and issues no barrier when nothing moved -- which NARROWS the per-descriptor reprogram residual of `mpu-bypass-windows-accepted` to the slots that actually change. **Its diff is UNROLLED slot by slot and the two postures are separate bodies, and that shape is load-bearing rather than taste**: written as one loop carrying the posture test, `-Os` re-reads the record flag and re-checks the slot bound every iteration and a SKIPPED descriptor costs 14 instructions and three taken branches, which is most of what the skip buys back; unrolled it costs eight and one. The unroll is why this backend's flash cost is the fleet's largest (+364 B on `f411disco-bench` against +96 SYSMPU, +72 RX, +48 PMSAv8; the record itself is 64 to 96 B of `.bss`), and it is why `ARCH_MPU_ENCODED_SLOTS == 8` is now static_asserted here. It also makes the descriptor-budget refusal TOTAL: the first commit spins on `k + 8 > DREGION` exactly as `kickos_arm_mpu_fixed_init` always did, so a part too narrow to hold a full per-thread set is refused whether or not it declares fixed rows, where before only a chip with fixed rows was asked. **ALL THREE REGION BACKENDS REFUSE SUCH A PART, and none of them truncates**, the project's rule being to refuse rather than silently mask: PMSAv8 reads `DREGION` in `kickos_arm_pmsav8_init` and spins there, beside the fixed-row refusal that function already carried, where its commit loop used to run to `hw_regions` and drop the image slots above it; RXv3 refuses at BUILD time, its region count being a chip constant rather than a register field, so `static_assert(ARCH_MPU_ENCODED_SLOTS <= MPU_REGION_COUNT)` says what the other two spin on. Nothing in the fleet is near either limit -- PMSAv7 and PMSAv6-M implement 8 or 16 descriptors wherever an MPU is present, RP2350 implements 8, RX72M 8, K64F 12 -- so NO VEHICLE CAN WITNESS any of the three. The record is `[KICKOS_NUM_CORES]` and indexed by `arch_cpu_id()`, the MACHINE identity and not the kernel slot (`kickos_kernel_core()`), because the ARM core MPU is per-core banked; the SYSMPU keeps ONE record for the chip because the crossbar unit is not. PMSAv8's `MPU_CTRL` disable/re-enable brackets the whole commit and is per-commit, so only the slot loop shortens. SYSMPU is 4 stores an RGD and RXv3 is 2 stores a slot plus a per-commit read-back that a commit writing nothing skips. **The rv32 PMP stays TOTAL and that is a measured decision, not an omission**: `pmpaddr0..7` are individually addressable CSRs but the eight cfg bytes ride four to a CSR, and the sequence is unrolled with immediate CSR numbers, so a per-entry skip spends a load and a taken branch where the write spends a load and a `csrw`. Measured at M8.11 on `esp32c6-wroom-bench`: the total commit compiles to 39 instructions and reads `MPU_COMMIT 75/75 n=520039` (~2 cycles an instruction, so no `csrw` is the outlier a skip would need), while the per-entry form compiles to 120 with ~55 on the all-skip path. QEMU is not the instrument for it either: its `pmpaddr` write carries a TLB flush and the same row reads 2897 there. rv64imac, armv8a, x86_64, the LX6 and the sim have empty commits and hold no record.
  - *applies:* context switch, MPU, user/kernel boundary; the PMSAv7/PMSAv8/SYSMPU/RX MPU backends (M8.11)
  - *source:* arch/arm/common/arch_arm_mpu_pmsav7.cc (the record, mpu_held_invalidate, the unrolled PMSAv7 diff and kickos_arm_mpu_fixed_init); arch/arm/common/arch_arm_pmsav8.cc (its own record + the per-core invalidation in kickos_arm_pmsav8_init); arch/arm/chip/mk64f/chip_mk64f.cc (SYSMPU record, one per chip -- the crossbar unit is not per-core banked -- invalidated by the rgd0_ready one-shot); arch/rx/rxv3/arch_rxv3.cc (RX record, invalidated by the mpu_ready MPOPI.INV one-shot); arch/riscv/rv32imac/arch_rv32imac.cc (the total PMP commit and the measurement comment saying why); tests/unit/mpuskip/ (the PMSAv7 writer compiled for the host over a modelled MPU: the skip, a set whose WORDS changed under one image pointer, and a commit after an invalidation); tests/static/check_mpu_record.sh (the class)

- **`mpu-bypass-windows-accepted`** -- PMSA enforcement is NOT total: two windows bypass it, both accepted residuals bounded by the reasons below, and a change must keep them bounded rather than assume the region set always applies. (1) MPU_CTRL is enabled as `MPU_CTRL_ENABLE | MPU_CTRL_PRIVDEFENA`, WITHOUT `HFNMIENA`, so the MPU is off inside HardFault and NMI handlers; accepted because that path is short and runs cached. This is the window that also drops any chip fixed regions' effect (`mpu-apply-on-every-switch-in`), which is what makes it matter on a speculating core: on Cortex-M7 an unbacked-but-Normal aperture stalls the core with no fault to report, so the anti-speculation wrap is off exactly where a stall is hardest to diagnose. (2) The reprogram window -- and it is NOT the same shape on the two PMSA revisions, which is the thing to get right before touching either. **PMSAv7's `kickos_arm_mpu_program` does NOT zero `MPU_CTRL`.** The MPU stays enabled across the whole reprogram and each per-thread descriptor is disabled INDIVIDUALLY (`MPU_RASR = 0`) in the instructions before its base moves, so the chip fixed rows `[0, k)` hold throughout and the imxrt1062 ERR011573 wrap over the FlexSPI band this code executes from is never dropped. Since M8.11 that window is narrower again: a commit disables and rewrites only the slots whose words moved (`mpu-commit-writes-what-changed`), so a slot that already stands is never unmapped at all. A leading `MPU_CTRL = 0` there is the removed bug, not the design, and must not come back; the only place zeroing it is correct is `kickos_arm_mpu_fixed_init`, which runs at boot before the caches. The v7 residual is therefore per-descriptor rather than global: per-thread slot `j` is unmapped between its `MPU_RASR = 0` and its rewrite, with the commit running privileged in the switch epilogue where PRIVDEFENA supplies the background. **PMSAv8 is the revision that DOES zero it**: its own `kickos_arch_mpu_commit` (`arch_arm_pmsav8.cc`) writes `MPU_CTRL = 0` and reprograms with the MPU wholly off, so on v8-M the window is total for its duration. Both shapes are accepted because the commit brackets the entire disable/reprogram/re-enable in `cpsid i` and the window runs from already-cached fetches, so no NEW speculation is armed inside it. What bounds the v8-M window is an UNSTATED PRECONDITION in the code: it is harmless only because no PMSAv8 chip in the tree declares fixed regions, which `arch_arm_pmsav8.cc` asserts in prose and nothing enforces. A PMSAv8 part that ever needs a fixed row -- an anti-speculation wrap, a locked-down aperture -- would have it dropped for the length of every switch, and no gate would report the change.
  - *applies:* MPU, context switch, fault/NMI paths; the ARM PMSA backends (armv7m, armv6m, PMSAv8), imxrt1062 above all
  - *source:* arch/arm/common/arch_arm_mpu_pmsav7.cc (kickos_arm_mpu_program, whose only MPU_CTRL write is the enabling one and whose per-descriptor disable is MPU_RASR = 0; kickos_arm_mpu_fixed_init, the one MPU_CTRL = 0 in the file); arch/arm/common/kickos_arch_mpu_commit_default.cc (the cpsid bracket around the v7 program); arch/arm/common/arch_arm_pmsav8.cc (the v8-M commit: same bracket and same enabling value, plus the MPU_CTRL = 0 the v7 path does not have, and the no-fixed-regions precondition in its header comment); docs/design-teensy-mpu-hang.md

- **`grant-refuses-kernel-reserved-blocks`** (Rule 7) -- The grant path MECHANICALLY refuses any MMIO/RAM grant that overlaps a kernel-owns-for-life block (timebase, IRQ controller, every access-permission controller -- the MPU/PMP twin AND any bus-side gate such as the K64F AIPS PACR pages or the ESP32-C6 HP_APM/HP_TEE -- clock/reset gates), binding EVERY granter including privileged ones (not "trust the granter"). grant_region_admissible (kernel/grant) refuses size-0/wrap, then any reserved-block overlap, then requires: a DEVICE grant be privileged + exactly one MPU descriptor (no rounding) + not a bit-band alias; a RAM grant satisfy the arch's region-admissibility predicate AND be confined to the user arena for EVERY caller (no privileged waiver). That predicate is `arch_ram_region_admissible` (arch/include/kickos/arch/arch.h), which is power-of-two size plus natural alignment where `arch_mpu_region_pow2()` is 1 (PMSAv7, PMP NAPOT) and a granule multiple of `arch_mpu_min_region()` where it is 0 (PMSAv8, SYSMPU, RX RXv3). It is deliberately NOT `arch_mpu_region_encodable`, which answers the same question for an MMIO window and on the sim admits EXACTLY ONE -- the published fake-register base at exactly `0x10000` (`privileged-write-seam-possession-and-allowlist`) -- and fail-closes on every other address and every other shape of that one. domain_for (kernel/domain) runs it on a SHARED grant at the region-commit chokepoint before allocating a domain slot; thread_create_call runs it on every PER-THREAD grant, the caller-owned stack and the DEV window both, because those are regions of the thread and never of its task's domain; and thread_create carries a backstop assert over the whole composed set. Each enforcing chip MUST declare arch_reserved_blocks -- NO fallback TU on purpose, so a forgetful enforcing port fails to LINK (affirmative fail-closed). On a bit-band core (arch_bitband_present() != 0) the overlap test also covers each reserved block's word-per-bit alias image and a device grant into either alias window is refused. grant_reserved_validate asserts at boot that arena + app extents are reserved-disjoint. Under KICKOS_HAVE_MPU=0 the whole module is inline no-op stubs (admissible always true), so call sites are #if-free and pay zero flash. **Arena CONFINEMENT is the whole of what this predicate says about a RAM range's provenance**: which task INSIDE the arena reserved a block is a second authority, asked beside this one at each of the three call sites and deliberately NOT folded into it (`arena-block-owner-is-the-reserving-task`), which is what keeps kernel/grant arch-seam-only and lets its host gate compile with no task pool behind it.
  - *applies:* memory-domain grant, MMIO isolation, single-ownership; kernel (grant/domain) + enforcing MPU chips (M4)
  - *source:* kernel/include/kickos/grant.h; kernel/grant/grant.cc (grant_hits_reserved/grant_region_admissible/grant_reserved_validate); kernel/domain/domain.cc (domain_for); kernel/syscall/syscall_thread.cc (thread_create_call's stack_base / mem_base / MMIO grant paths) + kernel/syscall/syscall.cc (KOS_SYS_GRANT_PROBE); kernel/thread/thread.cc (thread_create backstop assert); kernel/init/kmain.cc (grant_reserved_validate at boot); arch/include/kickos/arch/arch.h (arch_reserved_blocks/arch_bitband_present)

- **`arena-block-owner-is-the-reserving-task`** -- An arena block is nameable in a syscall argument ONLY by the task that reserved it, and by every thread of that task. OWNERSHIP IS PER TASK AND NOT PER THREAD: a task's threads share its domain, so a sibling handing on a block its peer reserved is the recorded M4.6 shared-block design (an IRQ thread and a service thread over one block) and must keep working, while a range a SIBLING TASK reserved is `-KOS_EPERM` on all three paths that let a caller name one: a spawn's `mem_base`, a caller-owned `stack_base`, `kos_mem_self_grant`. Arena confinement is a DIFFERENT question and answering only it was the hole: an unprivileged thread with no AUTH_MEMORY at all could pass another task's region base as `mem_base` with `task = KOS_TASK_NONE` and the child's domain WAS that task's memory, or name a sibling's stack block as `stack_base`. **THE TWO BACKENDS ANSWER ONE QUESTION.** Under translation a reservation is an address in ONE task's namespace, so the space's own `VirtualRanges` is the authority and each site asks it through `aspace_handoff` / `aspace_self_grant` / `vr_caller_nameable`; under region descriptors the bump allocator keeps no owner, so `ram_owner_alloc` records `(base, committed size, task handle)` in a bounded table and `ram_owner_nameable` is the region-side backend of the same question. A second call beside either would be the second truth the tree refuses. **TOTAL over an address no record describes**, exactly as `vr_caller_nameable` is total over a null entry: that is nobody's reservation, so no site keeps a list of its own, and the kernel's OWN arena blocks (the boot stacks in `kmain`, the thread pool's default stacks, the sim's guard page, the x86_64 frame pool) reach `arch_ram_alloc` directly, are recorded nowhere, and are therefore nameable by nobody. That is why the record lives in a KERNEL-side wrapper over the seam and not in the seam: three backends define `arch_ram_alloc` and two of its callers are not user allocations at all, so a seam-level owner argument would have to invent an owner for them. The owner is the TASK HANDLE, index AND generation, so a recycled task slot inherits none of its predecessor's blocks. **NOTHING FREES A RECORD**, exactly as the bump allocator never takes a block back (`porting.md`, the arena section): a dead task's blocks stay spent and nameable by nobody, so the table is a LIFETIME budget for the whole image, `KICKOS_RAM_OWNER_SLOTS`. A full table answers NULL from `kos_ram_alloc` and SPENDS NO ARENA doing it (the slot is found before the allocation, or a caller that kept asking would drain the arena one lost block per call) -- NULL being also what an exhausted arena answers, because that call returns a pointer and `syscall-return-abi` leaves it no route out for an errno. The `mem_base` arm is asked only where the field becomes a region of something, which is `domain_for`'s own two short circuits (a privileged child resolves the kernel domain; a member's memory is its GROUP's and is refused -KOS_EINVAL), so the existing refusal codes do not move. Under `KICKOS_HAVE_MPU=0` the module is inline stubs and no board pays the table: there is no isolation to breach where nothing is enforced, which is the same posture Rule 7 takes.
  - *applies:* memory-domain grant, spawn admission, single-ownership; kernel (ramown/mem + syscall) + every enforcing backend, region and translating (M8.3)
  - *source:* kernel/include/kickos/ramown.h + kernel/mem/ramown.cc (ram_owner_alloc/ram_owner_nameable, the region backend); kernel/include/kickos/vrange.h (vr_caller_nameable, the translating twin) + kernel/mem/aspace.cc (aspace_handoff/aspace_self_grant); kernel/syscall/syscall.cc (KOS_SYS_RAM_ALLOC records, KOS_SYS_MEM_SELF_GRANT asks); kernel/syscall/syscall_thread.cc (spawn_masked's mem_base and stack_base arms, task_create_call's grant); tests/unit/ramowner/owner_table.cc; user/apps/common/selftest (cross_task_block, and domain_share / caller_stack as the sharing controls)

- **`dev-window-access-is-thread-scoped-its-lifetime-task-scoped`** -- A granted DEV window is held by the ONE thread that asked for it, and POSSESSION IS AN EXPLICIT THREAD-LOCAL RECORD (`Thread::dev_base`/`dev_size`, seated once at `thread_create`) rather than a walk over what the caller can reach. That distinction is the whole invariant on a translating backend, where the window's MAPPING is task-wide and every peer could reach the registers: authority stays with the holder and the periph seam reads the record, never the region set (`../design-m6-mmu.md` F9). Under a region backend the two coincide, the window being composed as a region of that thread alone and never of its task's domain -- a deliberate refusal, not an omission, since a task-wide window would fix a lifetime problem by handing register access to a peer that never asked. **On a translating backend that reach is exactly what a peer gets, and only the authority is withheld.** The lifetime is the task's instead, and `task-scoped-death-and-a-cancel-that-reaches-every-park` delivers it on the path that needs it: a member's FAULT cancels the rest, so a window survives no fault in its group. Every other death returns only the dying thread's own window, and the supervisor that wants the whole group's has `kos_task_kill`, which is what a driver bring-up failure already calls. `Thread::mem_base` is the other half of the split and goes the other way: it is the group's, so a member spawned into a task may not bring one (-KOS_EINVAL) and shares its task's domain region instead.
  - *applies:* MMIO isolation, memory domains, thread lifecycle; kernel + every enforcing chip
  - *source:* kernel/include/kickos/thread.h (Thread::dev_base / dev_size); kernel/thread/thread.cc (thread_create seats the record and composes the region, dev_window_free); kernel/domain/domain.cc (domain_for, which no longer takes an MMIO window at all); kernel/syscall/syscall_thread.cc (the DEV window's admission and exclusivity, and the member-brings-no-memory refusal); docs/design-task-layer.md

- **`task-scoped-death-and-a-cancel-that-reaches-every-park`** -- A FAULT ends the faulting thread's whole task: `sched::exit_current` cancels every live member of that task, at `CANCEL_KILL`, before it releases the task reference. It is the only death that reaches the group from there, and the only one that has to: siblings share the address space the faulting thread was writing, and no caller is watching a fault. **Every death a caller asked for ends ONE thread** -- an ordinary return, `kos_thread_kill` and `kos_thread_slay` alike -- because a caller holding a thread handle could have named the group instead, and the two verbs that do (`kos_task_kill`, `kos_task_slay`) cancel every member themselves before the first victim reaches its exit. Propagating a victim's kind from its own exit would add nothing to those two and would collapse `kos_thread_slay` into `kos_task_slay`, leaving a parent unable to stop one uncooperative worker without dying with it. `sched::exit_current` cannot derive the scope from the thread, a fault setting no `cancel_kind`, so the fault path names itself (`sched::EXIT_FAULTED`); a test on the exit CODE would put the boundary inside a number an app may hand to `kos_exit`. The `dying` test in `thread_cancel` is the ONLY thing sparing a thread from its own group's cancel and it must cover both directions, the thread whose exit issued the cancel and a peer already tearing down; a second "except this one" guard beside it is refused as the copy that goes stale. A cancel is TOTAL over `WaitKind` (`thread_abort_park`): every park ends, and where the primitive has a code to carry one it reports -KOS_ECANCELED. The unwind is per-kind and is not a wake -- a mutex waiter does NOT acquire the mutex and the owner's inherited priority is reverted, a semaphore's count is left alone so a later post still hands its token to a genuine waiter, an endpoint park goes through `endpoint_wait_abort`, and a sleeper's deadline is dropped. The DEATH POINT AT `CANCEL_KILL` is the next syscall ENTRY (`syscall_dispatch`), deliberately not the exit: breaking the park gives the thread one window to clean up over memory it already holds, and the entry check is what ends a thread that ignored the code or was parked in a primitive with no channel to report through. The one thread THAT does not reach is one that never asks the kernel for anything again, and no caller may assume it will not be: 0 from `kos_thread_kill`/`kos_task_kill` means the request was accepted, never that the thread is gone. **`CANCEL_SLAY` DOES reach exactly that thread**, and reaches it without its consent: the claim is a switch INTO the victim, which rebuilds its context into the exit stub (`kernel/sched/sched.cc`, `switch_book`), so a victim RUNNING on a peer core loses that core instead -- `thread_cancel` raises a reschedule on the core holding it (`kernel/thread/park.cc`) and that core's `available_to` refuses to re-pick its own slain `current` (`kernel/sched/policy_fifo_rr.cc`), which is what turns the raise into a pass. Witnessed by `user/apps/common/slaypeer` + `tests/integration/check_slaypeer.sh`, whose victim spins unprivileged and makes no syscall at all. Consequently `kos_thread_slay` answers 0 only once the claim has landed, and there the answer IS the thread being off its core. The claim's outstanding-ness has ONE spelling, `thread_slay_claim_pending` (`kernel/include/kickos/thread.h`) -- the same refusal of a second copy as the `dying` test above, applied to the three sites that have to agree on it (the placement answer, the switch that owes the pass, the redirect that takes it).
  - *applies:* thread lifecycle, scheduler, IPC, driver teardown; kernel (all arches)
  - *source:* kernel/thread/park.cc (thread_abort_park/thread_cancel/task_cancel_group); kernel/sched/sched.cc (exit_current); kernel/syscall/syscall.cc (the death point); kernel/syscall/syscall_thread.cc (thread_kill/task_kill); tests/unit/taskdeath/group_kill.cc

- **`dev-window-exclusivity-is-bounded-by-the-silicon`** -- A DEV window has exactly ONE holder: `thread_create_call` refuses a second grant overlapping a live one with `-KOS_EBUSY`, and the test is a RANGE overlap (`dev_window_free` -> `grant_ranges_overlap`), not an exact-base compare, so a partial overlap cannot slip past. Possession is a per-THREAD record and never a property of its task's domain (`dev-window-access-is-thread-scoped-its-lifetime-task-scoped`), so `dev_window_free` scans live THREADS and reads each one's record rather than its reachable regions -- which is what keeps the scan honest on a backend that maps the window task-wide; a thread that is EXITED, INACTIVE or `dying` is not a holder, and the `dying` arm is what lets a supervisor woken by the teardown's EPIPE respawn into the window at once instead of racing the corpse. That is what lets two unprivileged drivers share one peripheral MODULE through disjoint per-channel windows: on `xmc4800`, `xmcuart`/`xmcuartirq` hold `[0x40030000,0x400301FF]` (USIC0 CH0) and `xmcssc` holds `[0x40030200,0x400303FF]` (CH1). The module-level clock gate and reset are NOT reachable from either: `CGATCLR0`/`PRCLR0` are in the SCU, which `arch_reserved_blocks` withholds from every grant, and `kickos_xmc_usic_init()` ungates USIC0 from `arch_init`.
  **The per-channel window is NOT a complete isolation boundary, and the silicon is why.** `KSCFG` is a CHANNEL register at channel_base + `0x0C`, so it is inside each channel's granted window, and it is `rw` from user mode -- but `KSCFG.MODEN` gates the whole MODULE (XMC4700/4800 RM, USIC V2.16, section 18.9 p.18-165: "If the module clock is disabled by KSCFG.MODEN = 0, the module cannot be accessed by read or write operations (except register KSCFG that can always be accessed)"). So the holder of CH0 can stop CH1, and the holder of CH1 can stop CH0, and no kernel check can prevent it without taking a register the driver legitimately needs for its own bring-up.
  This is an ACCEPTED HARDWARE FLOOR, not a defect to fix: isolation is as perfect as the hardware permits, and where the silicon puts a module-wide control inside a per-channel window, two drivers on one module must trust each other. The kernel's guarantees stop at the window boundary. A chip that wants stronger separation has to put its channels in separate blocks.
  Consequence for the console: `arch_console_reclaim_window` on `xmc4800` returns CH0 only, so `xmcssc` holding CH1 does not defer a console reclaim, which is correct -- but a reclaim reprogramming CH0 cannot restore a module a CH1 holder has gated.
  - *applies:* MMIO isolation, memory domains; kernel + every chip granting a sub-block window
  - *source:* kernel/thread/thread.cc (dev_window_free); kernel/syscall/syscall_thread.cc (thread_create_call's -KOS_EBUSY); kernel/include/kickos/grant.h (grant_ranges_overlap); arch/arm/chip/xmc4800/regs/usic.h (KSCFG at 0x0C, KSCFG_MODEN); arch/arm/chip/xmc4800/chip_xmc4800.cc (arch_reserved_blocks, the SCU block); system/init/xmc4800-relax/service_list.cc (the two disjoint windows)

- **`privileged-write-seam-possession-and-allowlist`** -- The seams that perform a privileged peripheral act on an unprivileged caller's behalf -- `arch_periph_enable` (`KOS_SYS_PERIPH_ENABLE`, the clock-ungate + bus-side unprotect for a block) and `arch_periph_reg_write` (`KOS_SYS_PERIPH_REG_WRITE`, one store to one register) -- are gated on POSSESSION, never on an authority bit. The predicate is `caller_holds_mmio_block(base)`: the CALLING THREAD's own DEV-window record (`Thread::dev_base`/`dev_size`, seated once at `thread_create` from the spawn's grant) must have a base equal to the requested base EXACTLY. **Possession is authority, not reachability**, and reading it off the caller's region set is what made the two the same thing: under a backend that maps a window task-wide, a walk over what the caller can reach answers yes for every peer in the task, so the seam would hand registers to a thread that never asked. The record is thread-local on every backend, which is what keeps this contract and its two board-registered arms unchanged under translation (`../design-m6-mmu.md` F9). Containment does NOT count, so a window covering several blocks is not a licence to act on a block it merely contains. A **privileged** caller short-circuits the check and passes unconditionally, as in `cap_check_authority`; the only privileged thread in a running image is `idle`, which calls no syscalls. The register-write seam takes the STRONGER predicate `caller_holds_mmio_reg(base, offset)`: the window matched by the exact base must ALSO CONTAIN `[base + offset, +4)`. Without that span the possession check bounds nothing but the base -- a 32-byte window at a block's start reaches every register the chip table names anywhere in that block (MEASURED: a holder of 32 bytes at `0x40000000` passed the gate at offsets `0x40`, `0x1000` and `0x0FFFFFFF`). The offset must also be 4-ALIGNED and `base + offset` must not wrap; both are `-KOS_EINVAL`, refused ahead of possession because they are malformed requests rather than possession failures. Possession rather than a capability because where the silicon puts a block's controls inside the window, holding the window already carries the authority; a bit would be a second, forgeable name for the same fact. Failing the gate is `-KOS_EPERM`. **Possession must never become blanket write access to the block**, because that is precisely what the bus classification withholds -- so `arch_periph_reg_write`'s per-chip backend is an ALLOWLIST of exact `(base, offset)` pairs and anything it does not name is `-KOS_EINVAL`. A per-BLOCK entry would hand back exactly what the silicon refuses and turn the seam into a privilege-escalation primitive keyed on a grant. The granularity is therefore the REGISTER, never a range, and an absent entry is a DECISION, not an omission (`xmc4800`'s U0C0 has no entry because the kernel owns the console channel's baud and enable). **"One register" is not "only the authority the driver needs"**, so each entry ALSO carries a per-entry VALUE MASK: `(value & ~mask) != 0` is `-KOS_EINVAL`, REFUSED WHOLE and never trimmed, because a silently dropped configuration bit is the failure class the read-back exists to catch. On `xmc4800`, `CCR` grants `MODE[3:0] | RIEN | AIEN` -- 6 bits of 32, with `RIEN`/`AIEN` deliberate because `xmcssc` arms them last -- and withholds `TBIEN`, `HPCEN`, `PM`, `RSIEN`, `DLIEN`, `TSIEN` and `BRGIEN`; `FDR` grants `STEP | DM`, and `BRG` every writable field, where a mask withholds only read-only and reserved bits and so buys little. `static_assert`s pin each composed grant, so a field-mask edit cannot widen it silently. A tabled block must also be CLOCKED. The contract now REQUIRES it (`arch/include/kickos/arch/arch.h`), though no backend enforces it: a store into a clock-gated block faults INSIDE the privileged store and reaches `kfault_terminate`, i.e. whole-system death from one syscall -- an unprivileged caller's one-syscall system-kill primitive. Not live today only because `kickos_xmc_usic_init()` runs unconditionally from `arch_init` so USIC0 is never gated; a `U1C0`/`U2C0` entry (gated at reset behind `CGATCLR1`) would arm it. TWO backends exist in-tree: `xmc4800` (real MMIO) and the SIM, which assumes NO fixed host address: it tries FIVE candidate bases in order with `MAP_FIXED_NOREPLACE` (`0x40000000`, `0x100000000`, `0x400000000`, `0x10000000000`, `0x100000000000` -- 1 GiB to 16 TiB) and PUBLISHES whichever landed as the only base the seam and the encoder answer for, the grantable window being `0x10000` (64 KiB) inside a mapping twice that, so its allowlist can carry one entry OUTSIDE the grantable window to reproduce the containment hazard on the host. The sim one is what puts the MECHANISM under a CI gate -- allowlist match, mask compare, refuse-not-trim, containment, alignment and wrap are each mutation-proved. Two arms move the other way once the window is 64 KiB, and the retraction belongs here: `grant_reserved`'s `DEV_UNPRIVILEGED(0x40000000, 0x1000)` case is VACUOUS on the sim, because `arch_mpu_region_encodable` admits the published base at exactly `0x10000` and nothing else, so deleting the `AUTH_MEMORY` refusal it is meant to exercise leaves the same answer (the authority test runs first, encodability refuses the identical request anyway). Conversely the misaligned-offset and wrapping arms, vacuous EVERYWHERE while they ran from a holder (from one both answer `-KOS_EINVAL` regardless), now DISCRIMINATE: they moved to the UNHELD worker, where a dropped check falls through to possession and answers `-KOS_EPERM` instead. What the sim cannot model is the bus classification itself: that an unprivileged store is silently DISCARDED remains a `pvprobe`-only fact, as does any chip's actual mask column. A chip with no backend answers `-KOS_ENOSYS`, never 0: a caller reaching for the seam has a register the bus refuses it, so a success answer would report a store that never happened. Every call site READS THE REGISTER BACK, because the discard is silent in both directions and the read-back is the only evidence a store landed -- and a read-back comparison must mask any field the hardware itself drives (the XMC `FDR` `RESULT[25:16]` case), or a landed store reports as discarded. `arch_periph_reg_write`'s default decline is a ONE-SYMBOL archive member (`arch/common/arch_periph_reg_write_default.cc`), NOT a weak symbol. The load-bearing half is that a chip's definition must live in an ALWAYS-ANCHORED archive member (`chip_<chip>.cc`, force-loaded via `-u g_isr_vector` -> `startup.S` -> `Reset_Handler`), because that member is extracted in link pass 1 before `syscall.cc` makes the symbol undefined. Scan order (`kickos_arch_*` after `kickos_chip_*`) is only a BACKSTOP, and the mechanism is stated once, in `arch/CMakeLists.txt`, rather than restated here: reversing the group FAILS THE LINK with a multiple-definition error wherever both the fallback and the backend are anchored (`TODO.md` carries the `qemu-m33` and `qemu-arm64` evidence, `arch_shutdown` and `kickos_arch_mpu_commit` among them). The anchored member IS the invariant, and a chip putting its definition in a dedicated TU nothing else references gets NEITHER protection and SILENTLY DECLINES at runtime: MEASURED by reversing the group AND moving `arch_idle_wait` into an unreferenced TU, whereupon the link succeeded with ZERO diagnostics while `objdump` showed the fallback's `wfi` where the chip's `nop` belonged. The anchoring is now ENFORCED in-tree, not merely evidenced, by `tests/static/check_seam_defaults.sh` (ctest `seam_defaults`, on every board): its leg 2 requires the fallback member to be ABSENT from the selftest's `-Wl,-Map` link map wherever a backend defines the seam, its leg 3 requires the fallback to be PRESENT and pulled by that exact symbol where none does, and its leg 4 refuses any weak symbol outside `tests/static/weak_allowlist.txt`. This is no longer a one-off for this seam: it is how EVERY optional seam in the tree resolves, `__attribute__((weak))` having been removed from all of them (`arch/CMakeLists.txt` states the rule canonically, under "Seam fallbacks: the lone-TU rule"). Honest about the mechanism -- it is LINKER behaviour, not language semantics, but behaviour every Unix-like linker and MSVC `.lib` shares, unlike `weak`, whose archive interaction is implementation-defined. Adding a second symbol to the default TU breaks the member's other half (it would be extracted unconditionally and collide on every chip with a backend). Membership in the class-2 family requires a MEASURED hardware refusal, never a plausible reading of a manual.
  - *applies:* MMIO isolation, syscall, user/kernel boundary; kernel + per-chip backends (enforcing chips)
  - *source:* arch/include/kickos/arch/arch.h (arch_periph_enable / arch_periph_reg_write); kernel/include/kickos/thread.h (Thread::dev_base / dev_size, the possession record); kernel/thread/thread.cc (thread_create seats it); kernel/syscall/syscall_mem.cc (caller_holds_mmio_block / caller_holds_mmio_reg); kernel/syscall/syscall.cc (the KOS_SYS_PERIPH_ENABLE and KOS_SYS_PERIPH_REG_WRITE arms); arch/common/arch_periph_reg_write_default.cc (the lone-TU decline); arch/arm/chip/xmc4800/chip_xmc4800.cc (the U0C1 FDR/BRG/CCR allowlist); tests (selftest periph_enable_unheld / periph_reg_write_unheld, whose arm 3 is the offset bound); user/apps/xmc4800-relax/pvprobe (the silicon discriminator)

- **`tls-carve-sits-below-stack-lo`** -- Where `KICKOS_TLS` is on, a thread's thread-local block is carved off the LOW end of that thread's OWN stack block, and `ctx.stack_lo` is seated ABOVE the carve, so a thread's own SP can never reach its own thread-local storage. `thread_create` computes `tls_block_size()` (the `.tdata`+`.tbss` span the linker laid out, plus the ABI's fixed bias `KICKOS_ARCH_TLS_TCB` -- 8 on armv7m/armv6m/lx6, 0 on rv32imac/rxv3 -- rounded to `KICKOS_STACK_ALIGN`), seats the template with `tls_seat` at the block's base -- which IS the thread pointer -- and hands `arch_context_init` a stack that STARTS above the carve, which is what seats `stack_lo`. **The seat goes through the frame pool where the stack is a mapped run** (`ustack_kptr`): such a block is named by a virtual address in the CHILD's address space, which is not the running one at spawn, so a direct dereference of the base would write into whatever the running space maps there. An arena block and a caller-supplied pointer are not pool frames, the pool says so, and both are dereferenced directly. The switch and trap guards compare the live SP against `stack_lo`, so a descent into the carve is a stack-bound refusal and never a silent clobber of the thread's own thread_locals. It costs no MPU descriptor: the region already added for the stack spans the carve. The SIZE is not a knob and must not become one -- a number typed into a defconfig cannot track a template the linker owns -- and with no `thread_local` declared the carve is zero bytes. `idle` is the only TCB that may take no carve, and the exemption is keyed on the idle TCB by IDENTITY (`kernel().idle_tcb`) rather than on the stack's size, because a caller-supplied stack that passed admission would otherwise skip the carve while the thread pointer went on answering for it. **This is naming, not isolation**: peers in a task share the whole app-data window, so a thread_local is private by convention and a peer can scribble it.
  - *applies:* thread creation, TLS, stack bounds; armv7m, armv6m, rv32imac, rxv3, lx6 (sim cannot: `ARCH_SIM` does not select `ARCH_HAS_TLS`)
  - *source:* kernel/thread/tls.cc (tls_block_size, tls_seat, tls_stack_admissible); kernel/include/kickos/tls.h; kernel/mem/ustack.cc (ustack_kptr, the pool-side alias); kernel/thread/thread.cc (the carve ahead of arch_context_init, and idle's identity-keyed exemption); arch/arm/armv7m/arch_armv7m.cc (arch_context_init seating ctx.stack_lo from the post-carve base); arch/common/sections.ld.h (the .tdata/.tbss template); Kconfig (KICKOS_TLS)

- **`tls-thread-pointer-forces-a-pow2-stack-stride`** -- With `KICKOS_TLS` on AND the thread pointer derived by MASKING SP, every thread stack block must BE one power-of-two stride and every block in the image must share the SAME one. **The condition is the MECHANISM and not the feature, and the arch declares which it has**: `ARCH_TLS_FROM_SP` (`arch/Kconfig`), selected by armv6m, armv7m, rv32imac, rxv3 and lx6, reaching CMake and C as `KICKOS_TLS_FROM_SP`. The reason is ARM: unprivileged M-profile code has no register that differs per thread except SP, so `__aeabi_read_tp` is SP masked down to the thread's own block (`(sp - 1) >> LOG2 << LOG2`, and the subtract is load-bearing because a stack top is EXCLUSIVE, so an empty stack has SP at base + stride and a plain mask would send it to the NEXT block). rv32imac has `tp` and rxv3 an emutls anchor and both mask anyway, which is a chosen uniformity, so the select states it rather than the ISA implying it. One image has ONE mask, so `KICKOS_USER_STACK_SIZE` and `KICKOS_ROOT_STACK_SIZE` must both be powers of two and must round to the same one; the top-level `CMakeLists.txt` refuses each failure BY NAME at configure time, and `arch_ram_region_align` / `kickos_region_align` stride every arena block by the rounded size. The geometry that produces is what `tls_stack_admissible` demands at runtime: a block must be stride-aligned and EXACTLY one stride wide, since two smaller blocks fit inside a single stride and mask to the same base -- a non-power-of-two there has every spawn refused at RUNTIME rather than at configure. **An arch that SEATS the register owes neither half.** armv8a writes `TPIDR_EL0` from the context and the context derives the block base by SUBTRACTION, so the stack's low bound owes no alignment past the ABI's sixteen bytes: `tls_stack_admissible` asks only for `KICKOS_STACK_ALIGN` there, the configure refusals do not fire, and a stack may be any number of pages at any page boundary -- which is what lets one be frames with an unmapped guard page below instead of a naturally aligned arena block. Both arms still require a block strictly LARGER than the carve. `qemu-arm64` states 12288 and 20480 and runs its whole suite on them; `tests/unit/tlscarve`'s `tls_carve_seat` target is the same fabrication with that one clause inverted. A part too small to pay the rounding turns the knob off and keeps a thread instead of a thread_local; `f302nucleo` and `bluepill-c8` both make that trade. The leaf's INSTRUCTIONS are pinned by a structural gate, because the range-edge case is one no runtime witness can see: C code never runs with SP at an exclusive stack top, so a tlsprobe passes with and without the subtract that makes that case correct.
  - *applies:* TLS, thread stack geometry, arena allocation; armv7m, armv6m (the mask), and every board whose arch selects ARCH_TLS_FROM_SP with the knob on (the stride)
  - *source:* arch/arm/read_tp.S (__aeabi_read_tp); arch/Kconfig (ARCH_TLS_FROM_SP); Kconfig (KICKOS_TLS, KICKOS_TLS_FROM_SP); CMakeLists.txt (the stride refusals, KICKOS_TLS_STRIDE / KICKOS_TLS_STRIDE_LOG2); cmake/boot_arena.cmake (kickos_pow2_ceil, kickos_region_align's KICKOS_TLS leg); kernel/thread/tls.cc (tls_stack_admissible); tests/unit/tlscarve (tls_carve_seat, the inverted clause); tests/static/check_arm_read_tp.sh (ctest arm_read_tp)

- **`no-privileged-tu-reaches-thread-local-storage`** -- No privileged translation unit may contain a thread-local access, and this is a GATE and not a convention: `tests/static/check_no_privileged_tls.sh` (ctest `no_privileged_tls`, registered from `arch/CMakeLists.txt`) fails the build when `kickos_kernel`, `kickos_arch_<arch>`, `kickos_chip_<chip>` or `kickos_lib` carries one. It reads RELOCATIONS and undefined symbols rather than source, because a thread_local reached through an inline function in a header leaves no `thread_local` anywhere in the privileged `.cc` that emitted the access: it refuses `R_ARM_TLS_LE32` (armv7m, armv6m), `R_RISCV_TPREL_HI20`/`_LO12_I`/`_LO12_S`/`_ADD` (rv32imac) and `R_XTENSA_TLS_TPOFF` (lx6), plus an UNDEFINED reference to any of the three ABI entry points a thread_local can reach through -- `__aeabi_read_tp`, `__emutls_get_address`, `__tls_get_addr`, with the RX psABI's extra leading underscore admitted -- which catches an access the relocation scan would miss because the linker had not resolved it yet. It is registered on EVERY cross board and not only where `KICKOS_TLS` is on, since a kernel TU that grows one where the knob is off is the same bug arriving somewhere the app cannot see it (the sim is not registered at all). What it protects: the thread pointer is a property of the UNPRIVILEGED thread that is running -- on ARM and RX it is derived from SP, so privileged code executing on a per-thread KERNEL stack masks down to a block that is no thread's TLS, and on RISC-V and Xtensa it is a register the kernel wrote for the thread it last resumed. Every one of those is a wrong answer that looks like a right one and NONE of them faults. Per-slot kernel state belongs in an array indexed by `kickos::Kernel::threads.index_of()`, which is how the per-thread `struct _reent` is reached. An arch that grows a fifth relocation spelling passes VACUOUSLY until its name is added, which is why the per-arch set is spelled out in the script and not globbed.
  - *applies:* TLS, user/kernel boundary, privileged archives; every cross arch (sim: not registered)
  - *source:* tests/static/check_no_privileged_tls.sh (the relocation and entry-point sets, and the failure text); arch/CMakeLists.txt (the no_privileged_tls registration and the four archives it is handed)

## Tickless timer & clock

- **`timer-min-delta-guard`** -- A deadline must never be armed in the past, so the next-event time is floored at KICKOS_TIMER_MIN_DELTA_NS ahead of the clock. `arm_slice` floors an RR quantum where it is born, so a sub-min-delta quantum (including a hostile user value) collapses to the min slice rather than re-arming every tick (interrupt storm). Deadlines handed to arch_timer_arm are ABSOLUTE and immutable for their whole life; a deadline already in the past is an immediate fire, which every backend produces by flooring the programmed delta at one tick (`timer-delta-clamp-before-convert`).
  **The floor belongs where the deadline is BORN, and `ktime_rearm` must not apply one.** `ktime_rearm` runs on every context switch, so a floor recomputed there against a fresh `ktime_now()` re-derives a deadline inside the min-delta window to a DIFFERENT value on every call -- which is precisely the quantity every arch backend dedups on (`g_armed_deadline_ns` on ARM, `g_rx_armed_ns` on RX, the absolute compare on CLINT/POSIX). The dedup then never matches, the one-shot countdown restarts from zero before it can reach the compare, and such a sleeper is held off for as long as switches keep arriving faster than min-delta; on ARM the same reprogram also writes `ICSR.PENDSTCLR` unconditionally, destroying a SysTick expiry latched while `ktime_rearm` held BASEPRI. So the floor is applied ONCE against ONE clock reading at each of the THREE sites where a deadline is born -- `ktime_sleep_until` for a sleeper, `arm_slice` for an RR quantum, `ktime_deadline_arm` for the deadline a timed wait hangs off a park on some other queue -- and `ktime_rearm` passes the absolute deadline through untouched. A new birth site adds a fourth entry here; it does NOT get to re-derive the floor further down.
  - *applies:* tickless timer; kernel + all arches
  - *source:* kernel/time/time.cc (ktime_rearm, ktime_sleep_until, ktime_deadline_arm); kernel/sched/policy_fifo_rr.cc (arm_slice); tests/unit/ktime/ktime_rearm.cc (the host gate: it reads the exact value the backends dedup on, which no on-target arm can see)

- **`rearm-before-switch`** -- ktime_rearm must program the next-event timer for the INCOMING thread before arch_switch, because the outgoing thread will not return to switch_to until it is itself resumed -- so the incoming thread's policy deadline (RR slice) must be armed now, not after the switch.
  - *applies:* tickless timer, context switch; kernel
  - *source:* kernel/sched/sched.cc (the two ktime_rearm calls, in switch_to and start)

- **`rr-quantum-is-wall-clock`** -- A round-robin quantum measures WALL-CLOCK time, not CPU time. `Thread::slice_deadline_ns` is an ABSOLUTE deadline, and policy_on_switch_in re-arms it ONLY when the thread is not RR-with-a-quantum, or the deadline is UINT64_MAX (unset), or it is already past: a deadline still in the FUTURE survives the switch untouched. Re-arming unconditionally on switch-in refunds the whole quantum on every resume, so a thread preempted more often than its quantum never reaches an expiry AT ALL -- round-robin silently degenerates to FIFO and the equal-priority peer starves for as long as the preemption lasts. ONE periodic higher-priority thread is enough to trigger it (a prio-13 driver IRQ thread against prio-10 RR peers is the shipping posture, not a contrived case). The guarantee this buys is that **no equal-priority peer waits longer than one quantum of REAL time**; it deliberately does NOT give each thread quantum_ns of CPU. CPU-time accounting is the alternative and was REFUSED: it needs an on_switch_out hook and a slice_left_ns field, and it weakens the peer-latency bound to "eventually" -- a thread preempted for 10 ms would still be owed its full slice afterwards. A full quantum is granted (arm_slice) in exactly two places, and the distinction is the whole invariant: policy_on_slice_expire ALWAYS re-grants after rotating to the peer -- which is what keeps a sole RR thread with no peer from sitting on a deadline in the past -- while policy_on_switch_in re-grants only when there is no live deadline to preserve. A sub-min-delta quantum is clamped inside arm_slice, see `timer-min-delta-guard`. Corollary, and equally load-bearing: **sched::tick_rr(now) must run BEFORE the sleeper-wake loop** in ktime_on_timer. tick_rr charges the slice to whatever kernel().current names, and sched::wake reschedules and REASSIGNS kernel().current, so running it after the loop charges the wrong thread and DROPS the expiry. On a coarse clock the sleeper and slice deadlines quantise together, which makes that the common case rather than a race. Both halves are mutation-proven: reverting EITHER gives zero slice expiries and an AAABBB interleave where ABABAB is required, measured on qemu-an386 under MPU with a prio-13 periodic thread. A slice-expiry COUNTER is the evidence -- the interleave string alone passes with zero expiries whenever the workers hand each other a semaphore token.
  - *applies:* scheduler policy, tickless timer; kernel (all arches)
  - *source:* kernel/sched/policy_fifo_rr.cc (arm_slice / policy_on_switch_in / policy_on_slice_expire); kernel/sched/sched.cc (tick_rr); kernel/time/time.cc (ktime_on_timer -- tick_rr ordered ahead of the wake loop); kernel/include/kickos/thread.h (Thread::slice_deadline_ns, quantum_ns)

- **`timer-delta-clamp-before-convert`** -- The ns->cycle conversion for the one-shot timer must clamp the delta to the counter's one-shot range BEFORE the ns*freq multiply (else a far-future or UINT64_MAX deadline overflows), and sleep deadlines must saturate to UINT64_MAX on now+ns overflow. A clamped deadline fires early and the kernel re-arms the remainder (harmless extra wake).
  - *applies:* tickless timer, ns<->tick; armv7m, armv6m, rx, xtensa
  - *source:* arch/arm/common/arch_arm_common.cc (arch_timer_arm's clamp ahead of the ns*freq multiply); kernel/time/time.cc (ktime_sleep_ns's now+ns saturation); arch/rx/rxv3/arch_rxv3.cc (arch_timer_arm); arch/xtensa/lx6/arch_xtensa.cc (arch_timer_arm)

- **`cycle64-wrap-extend-atomic`** -- The software 32->64-bit extension of the free-running cycle counter (catch-wrap on each read) must run under the critical section so the {read counter, compare to last, bump high} sequence is atomic against a concurrent reader from thread and ISR context. LIMITATION: a wrap not observed within one 2^32-cycle period is missed (M1).
  - *applies:* tickless clock; armv7m (PER CHIP, not the arch layer -- `arch_armv7m.cc` states
    there is deliberately no DWT fallback TU, the DWT being debug-domain), rx (CMTW1),
    xtensa (CCOUNT)
  - *source:* arch/arm/chip/imxrt1062/chip_imxrt1062.cc (gpt_ticks, the wrap-extend read bracketed by arch_irq_save/restore -- on armv7m the extension is per chip, the arch trace clock being a raw DWT read); arch/rx/rxv3/arch_rxv3.cc (g_cyc_high / g_cyc_last, now_cycles); arch/xtensa/lx6/arch_xtensa.cc (now_cycles)

- **`conversions-track-live-clock`** -- All ns/cycle conversions and the SysTick/baud programming must track the LIVE SystemCoreClock (or kickos_rx_timer_hz), not a compile-time constant; the cached reciprocal-multiply / max-delta must be recomputed when the clock value changes. A PLL bring-up that updates SystemCoreClock must therefore keep the timer and clock correct. WHERE that recompute may happen is not free: a STATELESS cache may re-derive itself lazily on observing a changed clock (arch_timer_arm's cached max_delta does), but the monotonic clock's accumulator rate may not, and `clock-anchor-sole-writer-at-rate-edge` is the binding rule for it.
  - *applies:* tickless timer, ns<->tick, SystemCoreClock; armv7m, armv6m, rx, xtensa
  - *source:* arch/arm/armv7m/arch_armv7m.cc (ns_to_cycles, off SystemCoreClock); arch/arm/common/arch_arm_common.cc (arch_cpu_clock_hz, and arch_timer_arm's cached max_delta recomputed when the clock moves)

- **`timer-disarm-clears-pend`** -- 'Disarm' must mean no callback will fire: disarming (and reprogramming) the one-shot timer must clear any interrupt request already latched while the line was masked (ARM ICSR PENDSTCLR; RX clears the IR flag), or a stray timer callback fires once on the next IrqLock release.
  - *applies:* tickless timer; armv7m, armv6m, rx, rv64imac (parks `stimecmp` at all-ones, `STIP` following the comparator with no latch of its own to clear)
  - *source:* arch/arm/common/arch_arm_common.cc (arch_timer_disarm's ICSR PENDSTCLR); arch/rx/rxv3/arch_rxv3.cc (arch_timer_disarm's ICU IR clear)

- **`clock-retune-coherence-tail`** -- A runtime core-clock retune is ONE ordered sequence and each step is load-bearing in that position: refuse unless the console is KERNEL_OWNED (return the unchanged Hz before anything is masked, because the kernel cannot re-derive a userspace driver's baud); take the IrqLock (single-core, so this quiesces the one timer); arch_timer_disarm; drain the console ring and wait for the TX shift register to go idle; call arch_cpu_clock_set, which internally does the flash-wait-state/voltage step, the divider or PLL walk, the anchor re-price at the rate edge and the SystemCoreClock write, and returns the LANDED Hz; re-derive the console baud; ktime_rearm. The baud step is gated on an ACTUAL move (`hz != 0 and hz != previous`), NEVER on a success flag: a backend that fails its relock and parks the core on a fallback point (K64F fail_to_fei, ~20.97 MHz) still MOVED the clock and rewrote SystemCoreClock, so it returns that non-zero Hz and needs the identical tail. A return of 0 means "this chip cannot change its clock at all" and never "failed but moved". THE GATE NEEDS BOTH ANSWERS AT ONE WIDTH: `arch_cpu_clock_hz`, `arch_cpu_clock_set` and `cpu_clock_set` all answer a u64 Hz, so a landed rate compares exactly against `previous` and the console refusal returns the same number the success path would. The flush must reach transmission-complete, not TX-buffer-empty, or the byte still clocking out of the shift register is garbled by the new baud. ns-valued sleep deadlines and the RR slice are clock-invariant and are deliberately NOT rescaled, which holds ONLY because the anchor keeps `now` continuous (`clock-anchor-sole-writer-at-rate-edge`).
  - *applies:* tickless timer, clock retune, console baud; kernel + the retuning chips (xmc4800, mk64f)
  - *source:* kernel/time/clock_select.cc (cpu_clock_set, the whole sequence); arch/arm/chip/xmc4800/chip_xmc4800.cc and arch/arm/chip/mk64f/chip_mk64f.cc (arch_cpu_clock_set / arch_console_flush_sync / arch_console_retune); arch/common/arch_cpu_clock_set_default.cc (the 0 "cannot change" fallback); arch/common/arch_console_flush_sync_default.cc + arch/common/arch_console_retune_default.cc (the no-op fallbacks)

- **`clock-anchor-sole-writer-at-rate-edge`** -- The tickless clock's epoch anchor (base_ns, base_ticks, mult_q32) is written ONLY at a rate edge: `init()` at boot, plus `reprice()` inside arch_cpu_clock_set on a retuning chip. arch_clock_now is a PURE read of that triple. The lazy `if (hz != cached_hz) recompute mult` each affected arch_clock_now once carried MUST stay removed: the rate prices the WHOLE accumulated tick count, so a read landing between the SystemCoreClock write and the re-anchor would reprice all of history at the new rate and freeze that phantom forward jump into base_ns PERMANENTLY (seconds to minutes on the shipped ratios, K64F's 120 -> 20.97 MHz being the widest at about 5.7x, and every ns deadline compared against `now` goes with it). reprice() captures base_ns under the OLD rate BEFORE the clock hardware moves, so only the ticks inside the brief masked retune window are mispriced, as frozen skew rather than a jump. The three stores are not atomic as a group, so they need the retune's IrqLock; a synchronous fault handler reading the clock between them is an accepted panic-path-only window.
  - *applies:* tickless clock, ns<->tick, clock retune; every chip whose arch_clock_now converts a hardware tick count (mk64f, xmc4800, stm32f411, stm32f103, stm32f302, sam3x8e)
  - *source:* arch/include/kickos/arch/clk_anchor.h (init / ns_from / reprice); arch/arm/chip/xmc4800/chip_xmc4800.cc and arch/arm/chip/mk64f/chip_mk64f.cc (the g_clk anchor + the reprice at the rate edge in arch_cpu_clock_set); arch/arm/chip/stm32f411/chip_stm32f411.cc (anchor with no retune, sole writer init)

- **`timer-arm-dedup-needs-disarm`** -- The kernel is the SOLE authority for what each core's one-shot comparator is programmed for (`Kernel::timer_armed_ns`, one cell per kernel core), and no backend keeps a second copy: every `arch_timer_arm` reprograms whatever it is handed. `ktime_rearm` early-returns when the deadline it computes is the one that cell already names, which is the guard that stops a far deadline being restarted on every reschedule -- blindly reloading a countdown each switch means the compare is never reached and the sleeper starves. **Every path that leaves the comparator describing something other than what was last armed must therefore go through `ktime_disarm`**, which programs disarmed and forgets, or the following re-arm is skipped as a repeat of a deadline nothing is counting. Three such paths exist and all three are load-bearing: the expiry itself, because a backend that clamps a far deadline into a narrow counter fires EARLY and is re-armed for the same absolute deadline (armv7m/armv6m SysTick's 24 bits, rxv3 CMTW's 32, the x86_64 APIC's initial-count) and an LX6 goes further, its pending CCOMPARE0 match being cleared only by the next write to that register; a clock-rate change, since the nearest deadline_ns is usually unchanged across it and the arm would be deduplicated away while the hardware still counts at the OLD rate; and a disarm the kernel performs for any other reason. The cell is zero-initialised deliberately -- 0 is a value no deadline computation can produce -- so the first rearm after boot always programs, whatever a bring-up probe left in the hardware.
  - *applies:* tickless timer, clock retune; every arch (the clamping backends are where a missed re-arm starves rather than merely fires late)
  - *source:* kernel/time/time.cc (ktime_rearm's dedup against the cell, ktime_disarm, ktime_on_timer's disarm ahead of the queue read); kernel/include/kickos/instance.h (Kernel::timer_armed_ns); kernel/time/clock_select.cc (the disarm ahead of the retune, the re-arm after it); tests/unit/ktime (the repeated-rearm and fired-comparator arms)

## IRQ dispatch

- **`irq-table-no-null-slots`** -- Every IRQ line is seeded (by irq_init, before any driver attaches) with the null-object default handler that masks the line and bumps the spurious counter, so the ISR dispatch path indexes the table with NO null check and an unhandled enabled line cannot storm or be silently dropped.
  - *applies:* IRQ dispatch; kernel + all arches
  - *source:* kernel/irq/irq.cc (irq_default_handler, set_default, irq_init, and kickos_isr_irq's unchecked table index); kernel/init/kmain.cc (irq_init, before console_buffer_init)

- **`one-driver-per-line`** -- A line may be claimed (irq_attach or irq_claim) only while it still holds the null-object default; a second claim fails (false / -KOS_EBUSY) rather than overwriting an existing driver and orphaning its irq_wait forever. No stealing. It is also what orders the console handover: the kernel's own console_tx_deinit must have detached the TX line before any tier-1 claim of it can pass.
  - *applies:* IRQ dispatch; kernel
  - *source:* kernel/irq/irq.cc (irq_attach, irq_claim)

- **`no-driver-on-a-kernel-vector`** -- A line the arch declares kernel-owned (`arch_irq_line_kernel_owned`) is refused BOTH minting entries, before either takes a resource: irq_claim answers -KOS_EPERM and irq_attach false. Such a line is dispatched by the arch to a kernel service of its own ahead of `kickos_isr_irq`, so it holds no irq_table slot, and the refusal has to be at mint time rather than at detach: a binding there would drive nothing, and the detach that closing its capability performs would MASK the line the kernel rings its peers on, which is an unprivileged thread killing the cross-core doorbell with an ordinary claim-and-close. The declaring backends are the RP2350's SIO_IRQ_BELL and the arm64 GIC's doorbell SGI; every other backend takes the fallback and declares none.
  - *applies:* IRQ dispatch; kernel + any arch routing a line to its own vector
  - *source:* kernel/irq/irq.cc (irq_claim, irq_attach); arch/include/kickos/arch/arch.h (arch_irq_line_kernel_owned); arch/arm/chip/rp2350/chip_rp2350.cc; arch/arm64/common/arch_arm64_gicv2.cc, arch_arm64_gicv3.cc; tests/unit/irqquiesce/quiesce.cc

- **`console-returns-to-the-kernel`** -- A console the kernel has handed to a userspace driver must come BACK on every path that ends that driver, or the system goes permanently mute: `console_emit` DROPS every kernel write while `USER_OWNED`, so a dead driver takes the panic banner, the fault dump and ordinary `kprintf` with it. Two triggers reach the same `RECLAIMED` state. A PANIC reclaims from any prior state (`kpanic_enter`), because ownership tracks a publish and not whether the device is garbled. A DRIVER DEATH is NOTED when the published endpoint's `recv_holders` reaches 0 -- keyed on that count and NOT on a thread identity -- but the note alone does NOT reclaim: the precondition is asked of the DEVICE. `console_on_driver_death` defers while any live domain still holds `arch_console_reclaim_window()`, because a driver is a THREAD GROUP and the endpoint's last RECEIVER is the service thread rather than the thread holding the registers; reclaiming on the note alone reprogrammed the UART under a live IRQ thread and silenced its own source. What the note's persistence across a refusal buys, and which exit finally reclaims, is in `console.md`. The death path is deliberately TWO halves: the cap layer only NOTES the fact, and `exit_current` acts on it AFTER the whole `cap_teardown` loop and before `domain_release`. Ordering is the point -- reclaiming inside a cap arm would run at an arbitrary index in that loop, possibly while the dying driver's IRQ cap is still live and its TX line still armed, so re-initialising the UART could race an interrupt still firing into `irq_event_isr`. `RECLAIMED` is stored BEFORE the body on both paths, so a fault inside a reclaim body cannot recurse and the body runs exactly once. **What is NOT implied**: a per-chip `arch_console_reclaim` body exists on every chip except `mps2`, `nrf51`, `sam3x8e`, `stm32f103`, `stm32f302` and `virt`, so on those six the state flips and the polled route is restored but the DEVICE is whatever the driver left. The sim needs no body at all (host fd 1 holds no state), which is why it can gate the state machine without a board. A VOLUNTARY close of the last receiver reclaims too, acted on inside handle_close rather than deferred: there is no teardown loop to finish first, and a note left pending would reclaim the console at an unrelated later thread exit.
  - *applies:* console ownership; kernel + every board that publishes a console
  - *source:* kernel/init/console.cc (ConsoleState, console_note_driver_death, console_on_driver_death, kpanic_enter); kernel/syscall/cap.cc (obj_close_protocol's CAP_ENDPOINT arm at recv_holders -> 0, and handle_close); kernel/sched/sched.cc (exit_current); tests/integration/check_sim_drvdeath.sh

- **`publish-then-prove-before-any-client`** -- A console handover is not complete at the publish: it is complete when the driver is PROVEN to be receiving. The publish must come first, because on a chip where the driver takes the UART the kernel was driving, the kernel has to let go before the driver may touch it (one device, one owner) -- so a span in which kernel-console writes are DROPPED is inherent and is not a defect. What must not happen is a CLIENT running inside that span. So the bring-up tail closes the caller's own WAIT-bearing cap and then probes the route with a ZERO-LENGTH rendezvous on cap 0, the same path every client uses: a rendezvous send returns only once a receiver has taken it, so on success no client can observe an unserved console, and it costs no bytes on the wire. The close-before-probe order is load-bearing: it leaves the driver as the SOLE receiver, so a driver that dies during bring-up takes recv_holders to 0, which both EPIPEs the probe AND reclaims the console -- which is the only reason a bring-up failure is reportable at all rather than structurally mute. A driver that HANGS in bring-up instead of dying parks the probe indefinitely; that is a loud hang rather than a silent boot, and per-chip bring-up polls are bounded by KICKOS_POLL_SPIN_MAX. A failed spawn takes the same route (close first, then report).
  - *applies:* console handover; every board with a userspace console service
  - *source:* user/include/kickos/sys/driver_service.h (console_handover_finish, and bring_up, which is the one caller on every board); system/init/sim/service_list.cc (the two window-thread postures, which hand-roll the same order because their window base is probed); tests/integration/check_sim_drvdeath.sh (case 2)

- **`irq-line-is-a-capability`** -- A tier-1 line binding is a POOLED, REFCOUNTED kernel object named by a `CAP_IRQ` capability, not an integer handle in a bump array. Three consequences a change must not break. (1) MINTING is gated on `AUTH_IRQ` -- namespace-wide, since the caller names a bare line number -- while `bind_notify`/`ack`/`discard` are gated on POSSESSION of the cap plus `CAP_WAIT` at the one chokepoint (cap_resolve_e). No authority bit gates use, and there is no per-line authority: while userspace tier-2 irq_attach exists, it is a wider door over the same namespace, so a finer bit would buy nothing. (2) RELEASE rides the walk that already exists: `cap_teardown` on thread exit, fault-kill and voluntary `handle_close` all reach irq_ref_drop, which at refs -> 0 takes the binding off its notification's signaller chain, DETACHES the line, and frees the slot. Detach strictly before free is load-bearing -- irq_event_isr holds the binding's ADDRESS as its pre-bound arg, so the slot must stop being reachable from the dispatch table before it returns to the pool, and the binding's reference on its notification is released at that same point rather than at the unchain, because a dispatch on another core may already have loaded that pointer. The generational SlotPool then makes every outstanding cap naming that slot inert rather than dangerous. (3) The latency invariant SURVIVES pooling: a SlotPool slot address is stable for the slot's life, so the ISR still does zero lookups. There is NO leak-never-strand arm and none owed: a waiter is parked on the NOTIFICATION and not on the line, so dropping the last capability naming a line while a driver waits strands nobody -- it takes the line away, which is what closing that capability says.
  - *applies:* IRQ dispatch, capability layer; kernel
  - *source:* kernel/include/kickos/cap.h (CapType); kernel/irq/irq.cc (irq_claim, irq_bind_notify, irq_ack, irq_ref_drop); kernel/syscall/cap.cc (the CAP_IRQ arms of obj_ref_inc / obj_ref_drop / obj_close_protocol / cap_resolve_e); kernel/syscall/syscall.cc (the KOS_SYS_IRQ_CLAIM authority gate); docs/reference/ipc-call-reply.md

- **`notification-is-the-delivery-object`** -- A raise is delivered into a `Notification` (kernel/include/kickos/notify.h), never into a word of a thread's TCB. Four consequences a change must not break. (1) The PENDING SET lives in the object, so it survives its bound thread's death with no transfer to perform, which is the whole of a driver handover. (2) THE BADGE BELONGS TO THE CAPABILITY and is set at the COPY: `kos_notify_badge` mints a second name carrying one bit and the source's rights, and refuses a source already badged, so an unbadged capability is the unconfined name and a badged one reaches its own bit and no other. A badge is copied INTO an IRQ binding at attach, because ISR context may resolve no capability, walk no pool and allocate nothing. (3) THREE HOLDERS count a reference: every capability naming it, the BIND, and each attached IRQ binding. The bind's own reference is what lets the last capability close under a live binding; leaning on the binder's capability would hand a stranger the object the moment that capability closed. All three are CHARGED, the budget counting a slot a task can keep allocated and not a name it can spend (`object-pool-keeps-a-slot-from-any-one-task`). (4) `notify_unbind_self` runs in `sched::exit_current`'s FIRST locked block and NOT inside `cap_teardown`, whose sweep drops and retakes IrqLock every `KCAP_TEARDOWN_CHUNK` slots: an object still naming a thread across one of those gaps is a wake into a thread already in teardown. NO AUTHORITY BIT and no new right: claiming a LINE still needs `AUTH_IRQ`, `CAP_WAIT` binds and waits, and `CAP_SIGNAL` signals and may be installed as a signaller.
  - *applies:* IRQ dispatch, IPC, capability layer; kernel
  - *source:* kernel/include/kickos/notify.h; kernel/notify/notify.cc; kernel/irq/irq.cc (irq_event_isr, irq_bind_notify, irq_signallers_rearm, irq_unchain_signaller); kernel/sched/sched.cc (exit_current); tests/unit/irqbindown, tests/unit/capbadge

- **`isr-mask-then-wake-wait-rearm`** -- The first-level ISR must mask the line (so it cannot re-fire while its driver services it in thread context) then raise its badge bit in the notification it signals. The line is re-armed (unmasked) by the driver's NEXT `kos_notify_wait`, which auto-re-arms every SIGNALLER CHAINED ON THAT OBJECT whose badge the accept mask covers -- so a `wait; service` loop alone keeps receiving IRQs (no forgot-to-ack deadlock). A line attached to NO notification can never be armed at all: `irq_ack` refuses it `-KOS_EINVAL`, because opening a source whose raise lands nowhere is a LOST interrupt and not a deferred one. Calling irq_wait asserts the previous event was fully serviced (e.g. device W1C done) before the auto-re-arm unmask -- the same service-before-unmask ordering the explicit ack used to carry. irq_ack stays OPTIONAL and idempotent: an early re-arm that only reacts sooner to a still-pending latch -- a raise on a masked line is latched one-deep and redelivered at the next unmask, so neither the ack nor the early re-arm is load-bearing for keeping the event (the latch-and-coalesce contract carries it either way); a double ack, or an ack after the next wait already re-armed, is a no-op. The per-binding needs_rearm flag is set when the WAIT CONSUMES the bit -- NEVER in the ISR (ISR-set races the ack;compute;wait unmask -> phantom wake -> empty-FIFO read). **A claim does NOT arm the line**: needs_rearm starts TRUE and the FIRST wait over its bit arms it, in the thread that will consume the event, so no window exists in which a line is armed while its owner is not yet running. Two consequences for callers. The first arm ALWAYS discards the pending latch first, whatever the trigger type -- a raise landed before the line had an owner is pre-claim garbage that would otherwise phantom-wake the first wait -- and a LEVEL binding keeps discarding on every rearm, after the driver's own device clear. That discard is TOTAL over every place a raise can be held. Above one kernel core irq_event_isr drops, before it masks anything, a raise taken on any core but the binding's claim core: every raise of a claimed line lands on its claim core, so such a raise was held by that core from before the claim, as a queued post or an interrupt acknowledged and not yet dispatched. The backend's clear, run on the claim core, discards what that core holds: its controller latch, a raise it has taken and not dispatched, a peer's post it has not taken yet, and on the LX6 its inject latch. And a parent that claims a line, delegates it, and then injects onto it must ARM it first (its own ack does), because the delegated child may not have reached its first wait yet and that first arm would discard the raise. The ISR handler runs by index with its arg being the pre-bound binding -- no table search on the hot path (latency invariant).
  - *applies:* IRQ dispatch, ISR wakes pre-bound target; kernel + all arches
  - *source:* kernel/irq/irq.cc (irq_event_isr, rearm_locked, irq_signallers_rearm, irq_ack); kernel/include/kickos/irq.h (IrqBinding, IrqTrigger); arch/include/kickos/arch/arch.h (the latch-and-coalesce contract above arch_irq_mask, arch_irq_clear_pending); arch/sim/sim.cc (arch_irq_unmask); arch/riscv/rv64imac/arch_rv64imac.cc, arch/xtensa/lx6/arch_xtensa.cc (arch_irq_clear_pending above one kernel core); tests/unit/irqlinecore; user/apps/common/selftest/selftest_smp.cc (t_irq_cross_core_wake, t_irq_reclaim_stale_raise)

- **`irq-handler-does-not-migrate`** -- Above one kernel core a thread handling a line is pinned to that line's core, and the kernel refuses rather than moves it. `irq_claim` is refused `-KOS_EPERM` unless the claimer's OWN mask is exactly the one core it runs on, and the line is routed there; a wait over a notification carrying lines, the fused receive's wait included, `irq_ack` and `irq_discard` are refused `-KOS_EPERM` unless the caller's OWN mask is exactly that claim core, a mask merely containing it included. EPERM and not EINVAL: the mask is expressible and pinning the caller satisfies it. Each refusal is decided under the lock scope of the operation it admits, since a task-mate may re-mask the caller the moment that lock drops. The kernel never writes the mask; the thread pins itself (`kos_thread_self` plus `kos_thread_set_affinity`) or its spawner pins it. Every raise, touch and wake of the line therefore happens on one core, which is what lets `irq_event_isr` treat a raise taken on any other core as stale. A thread with a wide mask is never an IRQ waiter, so work pushed across cores never carries one. One-core images carry none of it.
  - *applies:* IRQ claim, wait, ack, discard, fused receive; kernel above one kernel core, every claimer in the tree
  - *source:* kernel/irq/irq.cc (irq_claim, irq_ack, irq_discard, admit_claim_core, irq_admit_signallers); kernel/notify/notify.cc (notify_wait, notify_wait_admit); kernel/syscall/syscall_ipc.cc (endpoint_reply_recv); tests/unit/irqlinecore; tests/unit/fusedwake; user/apps/common/selftest/selftest.h (irq_spawn, TAP_ADD_IRQ); user/src/driver_service.cc

- **`line-masking-owned-by-handler`** -- A bound IRQ line must re-deliver on every fire; masking policy is owned by the handler tier, NOT the arch first-level / doorbell dispatcher, which only demuxes the physical source and calls kickos_isr_irq(line). A tier-1 (IRQ-as-event) binding masks on entry (irq_event_isr) and re-arms (unmasks) on the driver's next `kos_notify_wait`, or earlier via the optional irq_ack; a tier-2 (irq_attach) binding has no re-arm path, so any masking the arch dispatcher imposes strands it -- the line dies after one delivery and later injects are dropped. End-property, not code shape: an arch's dispatcher must not add masking its handler tier never undoes (the xtensa doorbell once did, and a tier-2 waiter hung).
  - *applies:* IRQ dispatch; software-doorbell backends: sim, rv32imac, rv64imac (one physical doorbell, `sip.SSIP`), rxv3, xtensa
  - *source:* kernel/irq/irq.cc (irq_event_isr masks; irq_wait auto-re-arms, irq_ack optional early re-arm); arch/xtensa/lx6/arch_xtensa.cc, arch/riscv/rv32imac/arch_rv32imac.cc, arch/rx/rxv3/arch_rxv3.cc, arch/sim/sim.cc (doorbell dispatchers: demux + deliver only)

## Console

- **`console-line-atomic`** -- The unit of atomicity the console owes is a LINE, and the ring is what makes it one: console_tx_insert_line copies a whole line under one IrqLock or refuses it, so two producers on two cores interleave whole lines and never bytes within a line. It NEVER WAITS under that lock, which is why ISR and fault context may use it where console_tx_write (which waits unmasked between ring-sized chunks) may not. The ring is therefore MULTI-producer; its consumer is the TX-empty ISR on a backend that has one and the producing thread itself on a backend that does not (irq_line < 0, serialised by the single-drainer flag). Panic and pre-arm boot still take the bounded polled writer (arch_console_write_sync), panic because the system stops afterwards and a queued line is a line nobody reads. A LINE THE RING CANNOT TAKE DOES NOT GO OUT. Each chip's arch_console_write is the insert and nothing else, and it reports whether the line landed. A direct write while the ring holds bytes would put a SECOND writer on the device, and the drain and that writer interleave mid-line, so a fallback cannot keep a line atomic however it is locked. The console is a debug facility, so a line lost to pressure is lost; the syscall reports the short count and its caller decides. The one direct write left is the UNARMED ring before console_tx_init, where no drain exists to interleave with. console_emit stays the single OWNERSHIP chokepoint and consults the three-state ownership axis g_console_state (KERNEL_OWNED buffered/sync as above; USER_OWNED drops the chip path entirely -- RTT still carries it; RECLAIMED polled-only) BEFORE the buffered-vs-sync sub-decision. A device poke while KERNEL_OWNED brackets itself in the g_chip_writers count so kos_console_publish (which flips the state to USER_OWNED last) drains a stale racing writer off the device before returning; console_tx_write's disarm fallback re-reads the state and DROPS the poke unless still KERNEL_OWNED.
  - *applies:* console single-producer ring; kernel + buffered-console chips
  - *source:* kernel/init/console.cc (ConsoleState + g_chip_writers + console_emit, and kpanic_enter's reclaim wiring); kernel/init/console_tx.cc (console_tx_write's disarm re-check, console_tx_deinit); kernel/syscall/syscall.cc (KOS_SYS_CONSOLE_PUBLISH drain); lib/include/kickos/console_tx.h; docs/reference/console.md

- **`console-publish-prime-atomic`** -- The producer's 'copy burst, publish head, enable TX IRQ' must publish head and enable the IRQ together under IrqLock, atomic against the ISR's 'drain to empty, disable IRQ', so there is no lost wakeup; the TX IRQ stays enabled whenever the ring is non-empty and the ISR disables it only on empty. The TX ISR therefore MUST sit in the IrqLock-maskable device band and must never sem_post/switch/block.
  - *applies:* console single-producer ring, ISR band; kernel + buffered-console chips (mk64f, xmc4800)
  - *source:* kernel/init/console_tx.cc (console_tx_write's publish-and-prime, console_tx_isr); lib/include/kickos/console_tx.h (console_tx_backend, console_tx_write, console_tx_isr); docs/reference/console.md

- **`panic-console-probe-independent`** -- Panic/fault output must not depend on the buffered ring or on an external debug probe: kpanic_enter sets g_console_panicking, flushes queued bytes in order via console_tx_flush_sync, then prints through the polled synchronous writer and halts. kpanic_enter calls arch_console_reclaim() and flips the state to RECLAIMED from ANY prior state, not only USER_OWNED: the ownership axis tracks a PUBLISH, never whether the device is GARBLED, and a thread granted the console window can wreck the channel with no publish at all (KERNEL_OWNED). The gate is therefore `state != RECLAIMED`, and the RECLAIMED store happens BEFORE the call -- which makes the reclaim UNCONDITIONAL-ONCE, so a synchronous fault inside the reclaim body re-enters and stops rather than recursing with the old state (a pre-existing recursion hazard the widening closed), and a body that truncates the byte in the shift register cannot cut the banner it just printed. Every chip body must be IDEMPOTENT ABSOLUTE STORES for this to be safe on a device no driver ever touched -- that idempotence is the LOAD-BEARING justification for the widened gate, not an aside. WITNESSED on silicon (`user/apps/xmc4800-relax/conreclaim`, xmc4800-relax, `c5d9b0d`): a KERNEL_OWNED channel gated at `KSCFG.BPMODEN=1, MODEN=0` still delivered its `=== MPU FAULT ===` banner, where the pre-widening behaviour was nothing after the pre-scramble line. kickos_isr_fault funnels through kpanic_enter FIRST so a terminal fault in the userspace driver still reclaims and prints. M2 DEPENDENCY: only a TERMINAL fault exit may reclaim -- a kill-and-resume fault path must NOT, since the driver keeps the device and a dark report there is correct. The synchronous writer must remain a real transport (the fallback TU arch/common/arch_console_write_sync_default.cc aliases arch_console_write, which is correct ONLY on a polled-only chip; a buffered console MUST define its own), never RTT-only.
  - *applies:* console panic-sync; kernel + all chips
  - *source:* kernel/init/console.cc (g_console_panicking + console_emit's routing, kpanic_enter and its reclaim, the kickos_isr_fault funnel); arch/common/arch_console_reclaim_default.cc (the no-op fallback); docs/reference/console.md

## Telemetry

- **`telemetry-emit-atomic-one-lock`** -- Every telemetry emit must assign the sequence number, sample arch_trace_now(), encode, and write to the sink under ONE IrqLock; splitting them lets a preempting context interleave an out-of-order seq/stamp and silently corrupt the host's loss/latency accounting. records_attempted/dropped are RMW under that same lock.
  - *applies:* telemetry record framing; kernel (all arches)
  - *source:* kernel/include/kickos/ktrace.h (ktrace_detail::put and the ktrace_switch / ktrace_syscall_enter / ktrace_syscall_exit / ktrace_irq_enter / ktrace_irq_exit emitters); docs/reference/telemetry.md

- **`telemetry-record-atomic-drop`** -- The telemetry sink is whole-record-or-drop: the ch1 ring checks free space for all n bytes up front and drops the entire record if it won't fit (a half-written binary record would desync the decoder permanently). Records are fixed-length, little-endian, self-delimiting; type tags are nonzero so a zeroed buffer never decodes as valid. One slot is reserved so head==tail is unambiguously empty.
  - *applies:* telemetry record framing, sink; lib/rtt + record.h (all arches)
  - *source:* lib/rtt.cc (kickos_rtt_write_record_ch1); include/kickos/trace/record.h (EventType, TRACE_MAX_RECORD, record_len, the encode_* helpers); docs/reference/telemetry.md

- **`switch-record-from-physical-contexts`** -- The SWITCH {from_tid,to_tid} record must be emitted from the tids read out of the two contexts that PHYSICALLY swapped, never by re-reading g_arch_next or shared scheduler state (a preempting ISR can rewrite the decision between switch_to and the physical swap). trace_tid is stamped once at thread_create and read at the pinned ctx offset; from_tid==0xFFFF on the first switch; multiple wakes in one ISR collapse to exactly one SWITCH record.
  - *applies:* telemetry, context switch; armv7m, armv6m, rx, xtensa, sim
  - *source:* arch/include/kickos/arch/arch.h (arch_trace_stamp_id); arch/arm/armv7m/switch.S (PendSV_Handler's spilled outgoing ctx* and its kickos_trace_switch_done call); arch/sim/sim.cc (trace_switch_arm / trace_emit_switch_in, and isr_frame_leave's deferred swap site); kernel/thread/thread.cc (thread_create's arch_trace_stamp_id); docs/reference/telemetry.md

- **`telemetry-emit-fp-and-fault-free`** -- The context-switch telemetry emit runs in the PendSV/SWINT/L1 tail with the incoming thread's FP state live in registers, so its whole call path is built -mgeneral-regs-only and must touch NO FP register. Fault/NMI handlers must never call ktrace_* (they preempt the BASEPRI/PRIMASK lock and would issue records out of the atomic emit region).
  - *applies:* telemetry FP-register-free ISR paths; armv7m, rx, xtensa
  - *source:* kernel/ktrace/ktrace.cc (kickos_trace_switch_done, the TU built -mgeneral-regs-only); docs/reference/telemetry.md

- **`idle-is-trace-id-zero`** -- Idle must be the first thread created so it receives trace id 0 (the decoder keys CPU% off tid 0 == idle); kmain asserts kernel().idle_tcb.id==0. The per-Kernel tid counter starts at 0 and, on wrap, skips both 0 (idle-only) and 0xFFFF (the no-thread sentinel).
  - *applies:* telemetry framing, thread identity; kernel
  - *source:* kernel/thread/thread.cc (assign_thread_id); kernel/init/kmain.cc (the kernel().idle_tcb thread_create + the idle_tcb.id == KICKOS_TID_IDLE assert); kernel/include/kickos/thread.h (KICKOS_TID_IDLE / KICKOS_TID_NONE)

- **`telemetry-off-zero-cost`** -- With telemetry compiled out, every ktrace_* entry point is an empty inline (no symbols, hot paths byte-unchanged) and the ctx.trace_tid field and arch_trace_stamp_id seam are elided, so the telemetry-OFF struct layout and switch paths are byte-identical to a build that never had telemetry.
  - *applies:* telemetry; kernel + all arches
  - *source:* kernel/include/kickos/ktrace.h (the telemetry-off empty inlines); arch/arm/armv7m/include/kickos/arch/context.h (arch_context::trace_tid, elided with telemetry); arch/include/kickos/arch/arch.h (arch_trace_stamp_id)

- **`telemetry-gate-emission-only`** -- A `KICKOS_TELEMETRY` gate may contain ONLY record emission. Anything that changes signal/interrupt masking, ordering or object lifetime belongs OUTSIDE it: gate such code and the telemetry-OFF build silently loses a correctness property the telemetry-ON build has, which no gate catches because every emulated tree runs telemetry OFF. The sim's fresh-context IRQ-signal block and its matching trampoline unblock were gated this way, and the resulting context corruption reached CI as an intermittent `sim_stress` failure that no local run reproduced; `arch_shutdown`'s shutdown masking and console drain were gated the same way.
  - *applies:* telemetry conditional compilation; all arches, the sim especially
  - *source:* arch/sim/sim.cc (arch_context_init's sigaddset pair, the trampoline's sigprocmask, arch_shutdown's arch_irq_save and console drain)

- **`trace-clock-u32-anchored`** -- arch_trace_now() is a raw monotonic u32 counter that wraps (armv7m DWT CYCCNT, rx/xtensa cycle/CMTW counters, sim ns/1000 us); absolute time is reconstructed by the decoder from the two SESSION clock anchors (near at init, far at shutdown). A target with no such source must not define KICKOS_HAVE_TRACE_CLOCK and cannot enable telemetry. The closing SESSION + ch1 drain at shutdown must run with IRQs masked so no record lands after the records_attempted snapshot.
  - *applies:* telemetry trace clock, record framing; all arches
  - *source:* arch/include/kickos/arch/arch.h (arch_trace_now); arch/arm/armv7m/arch_trace_now_default.cc (the raw DWT CYCCNT read); arch/sim/sim.cc (arch_trace_now, and arch_shutdown's masked final drain); kernel/include/kickos/ktrace.h (ktrace_session, the two SESSION anchors)

## Scheduler & instance state

- **`instance-scoped-state-no-arch-crossing`** -- All kernel runtime bookkeeping (ready lists, current/idle, sleepq, object pools, IRQ table, telemetry counters) lives in the single Kernel instance reached only via kernel(); the sim arch backend keeps its own parallel SimInstance and never crosses the arch seam. Multiple instances co-reside in one host process, so no cross-cutting global may leak scheduler/telemetry state across emulated MCUs.
  - *applies:* instance scoping, arch seam; kernel + sim
  - *source:* kernel/include/kickos/instance.h (struct Kernel, kernel()); arch/sim/sim.cc (SimContext, SimInstance, sim())

- **`ready-bitmap-tracks-lists`** -- The priority ready bitmap bit p must be set iff ready[p] is non-empty: every push sets the bit, every remove that empties the list clears it. top_prio() trusts the bitmap (31-clz) to pick the run list, and priority indexes both the ready[] array and a 1u<<prio shift, so a stale bit or an out-of-range prio is an OOB read/UB.
  - *applies:* scheduler ready structure; kernel (FIFO/RR policy)
  - *source:* kernel/sched/policy_fifo_rr.cc (top_prio, rq_push_back, rq_remove, policy_pick_next); kernel/syscall/syscall_thread.cc (thread_create_call's prio bounds check, the sole entry for a user-supplied priority)

- **`ready-member-is-placeable`** (`KICKOS_KERNEL_CORES > 1`) -- Every thread on core c's ready structure has c in its mask, except a RUNNING one whose mask narrowed under it, which leaves at c's next switch_book.
  - *applies:* per-core ready structures; kernel
  - *source:* kernel/sched/sched.cc (publish_ready's assert, switch_book); kernel/sched/policy_fifo_rr.cc (available_to)

- **`no-pull`** (`KICKOS_KERNEL_CORES > 1`) -- No core removes a thread from another core's ready structure; a publish to another core's structure is made only by the thread's holder or its waker, under the one lock.
  - *applies:* per-core ready structures; kernel
  - *source:* kernel/sched/sched.cc (publish_ready, place, push_take)

- **`ready-never-waits-while-a-core-below-idles`** (`KICKOS_KERNEL_CORES > 1`) -- A READY thread never waits behind equal or higher priority while a started core in its mask has a level strictly below it, equal priority included, so a same-core handoff is had only by pinning: a pass places every thread it made READY and did not take, and a core whose seated priority falls asks the holder to push; a thread whose slay claim is pending stays for its claiming pass.
  - *applies:* cross-core placement; kernel (FIFO/RR policy)
  - *source:* kernel/sched/policy_fifo_rr.cc (policy_place, policy_push_candidate, policy_declined); kernel/sched/sched.cc (place, place_declined, drop_scan, push_take, seat_level)

- **`seated-prio-left-high-across-a-lowering`** (`KICKOS_KERNEL_CORES > 1`) -- Kernel::seated_prio[c] is the priority c's last pass seated, raised with a raise of its running thread and never lowered by set_prio, so the pass after a lowering sees the fall.
  - *applies:* cross-core placement; kernel
  - *source:* kernel/sched/sched.cc (seat_level, set_prio, start)

- **`tcb-link-node-shared-ready-xor-wait`** -- A thread's intrusive `link` node is shared between the ready list and a wait queue (mutually exclusive membership), while timer-list membership uses the SEPARATE tnext link. A wait-queue block must detach_current from the ready list BEFORE pushing onto the wait queue (else it clobbers the links the ready removal needs); a timed wait may be on the timer list and a wait queue simultaneously only because they use different links. That dual membership is what forces the timer expiry to dispatch on `Thread::wait_kind` instead of waking unconditionally: a thread still linked through `link` must be unlinked from its wait queue BEFORE `sched::wake` reuses that node for the ready list, and the deadline must be cancelled at every unpark so the rendezvous and the expiry cannot both claim the same park.
  **The cancel belongs in `sched::wake_no_resched` and NOWHERE else, because a pop is not an unpark.** That is the one funnel every real unpark reaches (`sched::wake` is that call plus a resched, and the IPC paths call `wake_no_resched` directly), so putting the cancel there makes an unpark that forgets it unwriteable: becoming ready IS that call. The tempting alternative -- cancelling in `wq_pop_highest`, `reply_donor_unpark` and `thread_kill`'s hand-unlink, the three places every unpark already funnelled through -- is WRONG for one case, and silently so. `endpoint_recv_locked` pops a `CALL_SEND_WAIT` caller off an endpoint's `send_waiters` only to `reply_donor_park` it onto the server's `reply_waiters`: that is a PARK-TO-PARK MIGRATION, the thread never becomes ready, and a cancel there strips the single deadline a `KOS_SYS_CALL_TIMED` must keep across BOTH call phases. The failure is invisible to a fast-path test -- the caller simply parks forever in `CALL_REPLY_WAIT` whenever a server takes the request via the slow path -- so the arm that covers it must stage the SLOW path specifically (`call_timeout_reply`). The migration needs no re-arm: it moves the caller through `link` while the delta list uses `tnext`, so the armed deadline is untouched by construction.
  Two kinds are on NO list at all, `WAIT_JOIN` and `WAIT_LIVE_LAST`: the tag is the only thing that finds them, and `sched::exit_current` sweeps the thread pool for it at every exit. `WAIT_LIVE_LAST` carries no deadline by construction (`KOS_SYS_WAIT_LAST` takes none), so it must stay in the timer dispatch's `default: kpanic` arm -- a WaitKind reachable by the timer with no unwind of its own is exactly what that arm exists to catch.
  - *applies:* scheduler / sync queue membership; kernel
  - *source:* kernel/sync/sync.cc (wq_block, wq_pop_highest -- deliberately no cancel); kernel/sched/sched.cc (block_current; wake_no_resched, the sole ktime_deadline_cancel site; exit_current's WAIT_JOIN / WAIT_LIVE_LAST sweep); kernel/time/time.cc (ktime_deadline_arm, ktime_on_timer); kernel/syscall/syscall_ipc.cc (endpoint_send / endpoint_recv_locked / endpoint_call timed parks); kernel/thread/park.cc (endpoint_wait_abort); kernel/syscall/syscall_thread.cc (thread_join's queue-less park); kernel/include/kickos/thread.h (Thread::tnext, Thread::wait_kind)

- **`abandoned-reply-cap-cannot-reach-a-later-call`** -- A `KOS_SYS_CALL_TIMED` that expires in `CALL_REPLY_WAIT` leaves its server holding a live one-shot `CAP_REPLY`, because reclaiming an entry from another thread's table would cross a containment boundary. That cap is a DANGLING NAME for a thread that is still running, and `cap_reply_caller` is what must refuse it: index, generation, `BLOCKED`, `CALL_REPLY_WAIT` and the packed `call_seq` low byte. Four of those five come back TRUE the moment the caller makes another call, and the fifth is only 8 bits wide (`KCAP_REPLY_SEQ_BITS`), so it aliases every 256 calls -- at which point a stale resolve names a thread mid-transaction with someone else. What must stop it there is that the caller is parked on the OTHER server's `reply_waiters`: `reply_donor_unpark` returns FALSE when its unlink finds nothing, and both `endpoint_reply` and the `CAP_REPLY` close arm must treat that as "the caller is gone" -- consume the cap, answer `-KOS_ESRCH`/EPIPE-nothing, and touch NEITHER the caller's `wait_result`, NOR its `call_state`, NOR its `link`, which belongs to that other server's list. The unlink therefore DECIDES and must precede every other write. Getting it wrong is silent and cross-thread: the reply copies its bytes into a buffer belonging to a transaction it has no part in and wakes a thread that is still linked elsewhere, corrupting that list. The expiry unwind additionally rolls `call_seq`, which moves the aliasing call by one and is defence in depth rather than the guard: at `KICKOS_CAP_REPLY_MAX == 1` a server holding an abandoned cap can mint no second one, so the caller's live transaction is ALWAYS on a different server and the unlink is the test that fires. Coverage has to drive the caller through the full sequence period to reach it at all -- an arm that merely makes one further call is refused on the sequence and never consults the guard.
  - *applies:* call/reply capability lifetime; kernel
  - *source:* kernel/sync/sync.cc (reply_donor_unpark's bool); kernel/syscall/syscall_ipc.cc (endpoint_reply); kernel/thread/park.cc (endpoint_wait_abort's WAIT_EP_REPLY arm and its call_seq roll); kernel/syscall/cap.cc (cap_reply_caller, the CAP_REPLY close arm); user/apps/common/selftest/main.cc (t_reply_abandoned_cap, t_reply_stale_caller)

- **`join-accepts-the-unreclaimed-exit`** -- The thread pool's per-slot generation bumps at RECLAIM (`ThreadPool::alloc`) and NOT at exit, so a handle to a thread that has EXITED but whose slot has not yet been reused still gen-matches and still resolves. Every syscall resolving a thread BY HANDLE must therefore decide that state deliberately, and the two in tree decide it OPPOSITE ways: `KOS_SYS_THREAD_KILL` refuses it `-KOS_EBADF`, there being nothing left to cancel, while `KOS_SYS_THREAD_JOIN` ACCEPTS it and returns 0, because "the target is gone" is precisely what a joiner asked. Getting join's half backwards fails SILENTLY rather than loudly: the joiner parks on a thread whose exit sweep has already run, so it hangs until its deadline or forever. That is why the coverage joins the SAME handle a second time, bounded, immediately after the first join returned and before any spawn can reclaim the slot -- 0 is the pass, `-KOS_ETIMEDOUT` means the state was read as "still running" and `-KOS_EBADF` means it was read as stale. Both joins answer 0, so an arm that reads only the return value cannot say which path either took: the first join is therefore TIMED against a target that sleeps before exiting, and must last at least that sleep, while the second must not -- without those two bounds a target that had already exited would satisfy the whole arm through the early return and the parked path would go untested. `ThreadPool::release` is the third reader of the rule: undoing a claim on a reclaimed EXITED slot reverts the generation bump `alloc` made, precisely so the prior occupant's join-by-handle keeps resolving. Only a REUSE invalidates the handle.
  - *applies:* thread handles; kernel
  - *source:* kernel/include/kickos/thread.h (ThreadPool::alloc, ThreadPool::release, the generation-timing note); kernel/syscall/syscall_thread.cc (thread_resolve and its two callers); user/apps/common/selftest/main.cc (t_thread_join)

- **`sem-post-direct-handoff`** -- Semaphore wakeups are a direct token hand-off: sem_post wakes the highest-priority waiter (FIFO among equals) and does NOT increment count; the woken waiter returns from sem_wait without decrementing. Count is incremented only when there is no waiter. Breaking this double-counts or loses a token.
  - *applies:* synchronization primitives; kernel
  - *source:* kernel/sync/sync.cc (sem_post, sem_wait, sem_trywait)

## What a test environment can witness

- **`stub-is-a-weaker-environment-than-the-real-thing`** -- An arm that will one day face the real
  participant is NOT validated by passing against a stub, a fake, a loopback or a body. The weaker
  environment does less: it generates no traffic of its own, holds no state between calls, never
  blocks, and never becomes unavailable partway through. So an arm that would break against the
  real thing is SOUND against the stub and STAYS sound for exactly as long as the real thing does
  not exist, which makes its green run a statement about the environment rather than about the
  claim. Two ways this is paid: an arm whose environment is about to be replaced is re-run against
  the replacement before it is believed, and an arm held because its environment does not exist yet
  is a debt rather than a pass.
  - *worked example, and where the rule came from:* the AMP peer. While a peer was a WINDOW LAYER
    it never occupied a receiver and generated no traffic of its own, so `amp_far_reply_guard`
    could count dropped replies over a window it did not own and `amp_far_call` could send before
    it called. Both were correct for as long as they were held under a posture with no live peer.
    Both broke on the first run against a peer that is a KERNEL, one on a stray reply the peer's
    service thread generated and one on N6f's rule that a call finding nothing parked is refused
    on the spot. `amp_far_reply_guard` broke a THIRD time on the same shape: a peer that answers
    every call it takes, an empty reply for a delivery it refused past the take included,
    completes that arm's own caller before the first forged reply is published, so the arm must
    withhold the peer's doorbell seat and wait for it to fall quiet before publishing at all.
    None of the three is a test-writing slip; each is the stronger environment doing something the
    weaker one could not.
  - *applies:* every arm whose counterpart is stubbed, forged, looped back or simulated, which is
    not only AMP: a forged publication, a host seam standing in for a backend, and a loopback
    console are the same shape.
  - *source:* docs/design-multicore.md (N6f, the measurement rule beside the receiving side's
    rules); user/apps/common/selftest/selftest_amp.cc (t_amp_far_call, t_amp_far_reply_guard)

## App entry & init seam

- **`app-entry-via-init-seam`** -- The kernel's root thread calls exactly one seam symbol `kickos_init_entry(argc, argv)` (`<kickos/sys/init.h>`) once kernel init is complete; the app's `main` is NOT itself pid-1. The provider of that symbol is a build-time-selected CMake target (cache var `KICKOS_INIT_PROVIDER`, default `kickos_default_init`, a `kickos_system` service that passes through `kickos_init_entry -> kickos_default_init_run -> kickos_app_main`). Low barrier is preserved: a plain app writes only `int main` and no manifest; a power user names their own provider target and may delegate to `kickos_default_init_run` to reuse the app-main body.
  - *applies:* boot/init, dependency inversion; kernel + build system + kickos_system
  - *source:* kernel/init/kmain.cc (root_entry -> kickos_init_entry); system/init/common/default_init_entry.cc; system/init/common/default_init_run.cc; system/include/kickos/sys/init.h; CMakeLists.txt (the KICKOS_INIT_PROVIDER block)

- **`init-return-is-shutdown`** -- RETURNING from `kickos_init_entry` is a single-shot system shutdown with that int status: root_entry calls the `kos_shutdown` SYSCALL, which reaches `kickos_terminate` -- drain the buffered console (`console_tx_flush_sync`), then `arch_shutdown(status)`. A persistent init must NEVER return (it parks or loops) -- running off its end shuts the whole system down. The shutdown is a gated syscall, not an unconditional call: it needs `AUTH_SYSTEM`, so a root that has narrowed that bit away (`authority-word-narrows-only`) is REFUSED `-KOS_EPERM`, and root_entry then panics `"root: shutdown refused"` rather than running on. That panic MUST route through the `KOS_SYS_PANIC` syscall (`kos_panic`) and never call `kpanic` directly: root is unprivileged (`root-unprivileged-idle-alone-privileged`) and `kpanic` masks IRQs and reads kernel `.bss`, so a call from root's own frame faults on the panic path itself and LOSES the diagnostic -- measured faulting three ways before the syscall existed. An app whose main returns must therefore keep `AUTH_SYSTEM`; the failure is loud, which is why the bit is not forced back on. **EXITING from `kickos_init_entry` is the same shutdown**, and for the same reason: `KOS_SYS_EXIT` issued by root (`every-syscall-caller-holds-a-pool-slot` (3) is how it is recognised) takes the `kickos_terminate` path with the code unchanged, so plain C `exit()`, `abort()` and a failed `assert` from main end the system with children still alive. Ending the system is a right root holds, so it is the same `AUTH_SYSTEM` gate, but the refusal cannot be REPORTED: `kos_exit` is `noreturn` and `_exit` spins after it, so a returned `-KOS_EPERM` would loop root forever with nothing on the wire, and the arm panics `"root: exit shutdown refused"` instead. That panic calls `kpanic` and not `kos_panic`, unlike root_entry's: the syscall arm already runs privileged in the kernel. What the arm protects is that root's *ordinary, userspace* exit ends the system rather than ending one thread. It is NOT what keeps root's slot out of the pool: root MAY reach `EXITED` through a fault, a group cancel or wild-stack containment, and what the pool shape depends on is that `ThreadPool::alloc` never reclaims `ROOT_INDEX`. `KICKOS_THREAD_SLOTS` is one wider than `KICKOS_MAX_THREADS` because root's slot is claimed at boot and RETIRED for the life of the system, alive or dead (porting.md), and the domain and demand-stack budgets follow the same count. Because the slot is never reclaimed, `alloc`'s reclaim sweep never clears the `spawner_tag` of root's children: they keep root's tag, and since no successor can ever answer that tag, none inherits cancel authority over them -- the same standing an ordinary orphan already has. The one reclaim-point action root's retired slot still owes is its capability directory, which `sched::exit_current` returns to the slab itself.
  - *applies:* boot/init lifecycle; kernel
  - *source:* kernel/init/kmain.cc (root_entry's tail: kos_shutdown, then kos_panic on refusal); kernel/init/console.cc (kickos_terminate: console_tx_flush_sync then arch_shutdown); kernel/syscall/syscall.cc (the KOS_SYS_SHUTDOWN and KOS_SYS_EXIT arms, both AUTH_SYSTEM-gated for root); user/src/newlib_stubs.cc (_exit -> kos_exit); system/include/kickos/sys/init.h

- **`ctors-run-before-init-entry`** -- App / libstdc++ / library global constructors run in the kernel root thread (kernel live, thread context so a ctor may issue a syscall like kos_clock_now) BEFORE `kickos_init_entry` is entered -- the normal C++ order. A custom init must not assume its own bring-up precedes those ctors. Every target STATES its app-ctor window: `__kickos_app_init_array_{start,end}` is a STRONG reference, defined by each chip linker script around its `.kickos_app_init_array` bucket and by `arch/sim/start.cc` as a deliberately EMPTY window (a hosted ELF's own runtime has already run the ctors before `main`, so walking them again would double-construct). EMPTY and ABSENT are therefore distinct at LINK time, which is the point: present-but-empty leaves `start == end` so the walk iterates zero times, silently; a script that omits the bucket fails the link with an undefined symbol. These bounds were once WEAK, which collapsed absent into a null the walk skipped -- that is how a monolithic `.init_array` could run every app ctor privileged from the reset handler AND skip the late walk entirely with no diagnostic.
  - *applies:* boot/init ordering, C++ ctors; kernel + all chips + hosted sim
  - *source:* kernel/init/kmain.cc (the __kickos_app_init_array_start / __kickos_app_init_array_end declarations, and root_entry's walk ahead of kickos_init_entry); arch/sim/start.cc (the empty .kickos_app_init_array window)

- **`link-bounds-stated-or-the-link-fails`** -- The SAME rule over every bound the kernel reads out of the image's own layout, and not only the ctor window above: `__kickos_code_{start,end}` and `__kickos_appdata_{start,end}` (the app's MPU grant, `kernel/domain/domain.cc`), `_kickos_heap_{start,limit}` (the banner, `kernel/init/kmain.cc`), `__kickos_app_{rom,sram}_{start,end}` and `__kickos_app_load_delta` (the app image split, `kernel/mem/aspace.cc` and `arch/common/arch_ram_common.cc`). Every one is a STRONG reference (`include/kickos/klink.h`, `KICKOS_LINK_BOUND`), so a script that states none fails the link NAMING the symbol. A target that carves no such window states it EMPTY instead -- `arch/common/sections.ld.h` carries `KICKOS_APP_CODE_WINDOW_NONE`, `KICKOS_APP_DATA_WINDOW_NONE` and `KICKOS_APP_IMAGE_SPLIT_NONE` for a chip script, `arch/sim/start.cc` states the hosted one, `arch/x86/x86_64/pe_image.ld` the PE32+ one -- and `start == end` is what every reader tests, so an empty window admits nothing, silently and on purpose. These were weak undefined references until M8.13, which made absent and empty the same zero. The x86_64 `__kickos_app_*` FIVE are DELIBERATELY not stated, `__kickos_app_load_delta` with the other four: that target compiles no address space today, so nothing references them, and the day it gains one the link fails rather than granting an empty window. Hidden visibility on each declaration is a separate obligation of the same header: on PE32+ an undefined external reference stays GOT-indirect whatever `-fvisibility` says, and `tools/check-x86_64-no-got.sh` refuses a survivor. Two symbols are NOT in this class and must not be swept into it: `__register_frame` is libgcc's and optional by libgcc's contract, and `kickos_app_build_time` is vague linkage emitted by every app TU that defines `main`, so it stays weak and stays in `tests/static/weak_allowlist.txt`.
  - *applies:* image layout, MPU grant, address space, boot banner; kernel + all chips + hosted sim + PE32+
  - *source:* include/kickos/klink.h (KICKOS_LINK_BOUND); arch/common/sections.ld.h (the three empty-window macros); each chip .ld (the windows it carves or states empty); arch/sim/start.cc; tests/static/weak_allowlist.txt

- **`init-provider-fail-loud`** -- Exactly one target supplies `kickos_init_entry`, chosen by `KICKOS_INIT_PROVIDER`; a missing/unknown provider is a CMake FATAL_ERROR (checked late so a provider defined in user/apps is not false-tripped), never a silent fallback and never a weak symbol. The default provider's entry and run body live in DISTINCT TUs so a delegating override referencing only the run body does not drag in a second `kickos_init_entry`. An installed package freezes the provider it was built with and rejects a consumer override.
  - *applies:* build, entry seam; build system + kickos_system + installed package
  - *source:* CMakeLists.txt (the KICKOS_INIT_PROVIDER cache variable, its link group, and the late not-a-target FATAL_ERROR); system/CMakeLists.txt (the default provider's TUs); cmake/KickOSConfig.cmake.in (the frozen-provider FATAL_ERROR)
