# M9.5 x86 same-owner IPC baseline (2026-09-25)

> The [one-vCPU-per-host-core repeat](M9.5_x86_ipc_pinned.md) supersedes this
> sweep for host scaling comparisons. This first capture restricted QEMU to a
> CPU set but did not fix the placement of its individual vCPU threads.

## What ran

This is the M9.5 measurement precondition on the x86_64 SMP bring-up from M9.4.1.
`bench_smp_ipc` creates one independent endpoint, server, and client per KickOS core.
Both threads of each pair are pinned to that core. Every client performs 50,000
call/reply transactions with 8-byte requests and replies, then 50,000 with 256-byte
requests and replies. The server checks the pair tag in the request, the client checks
it in the reply, and the test requires every pair to finish and their active intervals
to overlap. The phase and lock distributions are reset after all peers are ready.

The host is a 12-core/24-thread Ryzen AI 9 HX PRO 370. Logical CPUs 0-3 are four
physical cores with a 5158 MHz advertised maximum; 4-11 are eight physical cores
with a 3289 MHz advertised maximum. CPUs 12-23 are SMT siblings and are excluded.
`taskset` constrains the whole QEMU process to a listed CPU set; individual vCPU
threads may migrate within that set. The one-core guest uses two QEMU vCPUs because
this host's OVMF stalled with one; KickOS starts only one of them. QEMU uses KVM and
`-cpu host`. These are host measurements, not a silicon latency or a guest cycle
counter validation on the other architectures.

Each case ran three times. The matrix reversed case order on alternate repetitions.
The table gives the median aggregate transactions/s and the observed range for the
8-byte pass; the 256-byte column is its median. The complete 48-pass table, including
lock-wait and copy-phase rows, is in [M9.5_x86_ipc_baseline.tsv](M9.5_x86_ipc_baseline.tsv).
The raw console captures stay under ignored `build/m95/runs/` in this workspace.

The four-fast-core rate is essentially the one-fast-core rate despite four pairs
running. The eight-slow-core rate is about 89% of the one-slow-core rate, and the
mixed twelve-core rate is about 39% of the one-fast-core rate. The mixed case has
substantial run-to-run spread, so it is a contention demonstration rather than a
precise speedup estimate. A second physical core was active in the two-core cases;
the flat aggregate rate does not mean only one guest core ran.

## What part can leave the lock today

The one-fast-core phase table in repetition 2 gives the following corrected means.
The three locked brackets occur in separate syscall entries. `CALL_WAKE`,
`RECV_PARK`, and `REPLY_WAKE` are subphases of those brackets; they are the
handoff/parking work that remains under the BKL through the context switch.

| Payload | Call + receive + reply locked cycles | Handoff/parking cycles | Copy cycles | Other locked cycles |
| --- | ---: | ---: | ---: | ---: |
| 8 B | 5,406 | 4,290 (79.4%) | 52 (1.0%) | 1,064 (19.7%) |
| 256 B | 5,491 | 4,350 (79.2%) | 70 (1.3%) | 1,071 (19.5%) |

These are instrumented phase means, with the phase table's stated correction,
and cannot be subtracted from the wall-clock rate as if they were independent
samples. They show that moving **only the two copies** out of the BKL shortens
less than 2% of these three locked spans even at 256 bytes, before the added
snapshot and revalidation work. The copy-only candidate cannot meet M9's 5%
minimum gain. Moving every other non-handoff operation would be a larger
candidate, with about 21% of the measured locked-cycle sum to work on, but the
table is not a predicted throughput gain for that candidate.

The larger same-owner transaction is different. It resolves an endpoint cap, peeks
and removes a receiver, writes into that receiver's user buffer, installs and
discloses a reply cap, changes donation and park state, then wakes and switches.
`kernel/syscall/syscall_ipc.cc` currently keeps those steps in one `IrqLock` interval.
`cap_resolve_e` currently asserts global exclusion across resolve-to-use. The
running caller's own SIGNAL cap keeps its endpoint slot referenced until that
thread can run cap teardown, but this does not protect the receiver's wait state
or mapped buffer from a peer's timeout, cancellation, or map edit. The endpoint
has intrusive wait queues, a raw server TCB pointer, and no payload storage.
A reply cap names a caller TCB without holding an object reference. The
scheduling tail uses the M9.4 per-core rings, but the local scheduler and
frame-park release still run under the global lock; M9.4's stage-2 lock escape
was refused at two cores on LX6 silicon and expressly kept parking passes locked.

Therefore the x86 rate collapse does **not** justify a BKL bypass in this patch.
The copy-only split fails the gain ceiling. A full local IPC path might have a
large payoff at four or twelve cores, but requires a reviewed lifetime protocol
for cap/object/TCB/address-space references and a scheduler switch protocol that
does not publish an outgoing frame before it parks. This capture measures the
baseline and identifies that remaining M9.5 design work; it is not a before/after
measurement of an unlocked implementation. No BKL behavior changed in this stage.
The decision boundary is detailed in
[`docs/design-m9.5-local-ipc.md`](../design-m9.5-local-ipc.md).

## Reproduce

Configure and build `bench_smp_ipc_image` for the x86_64 `bench`, `smp2`, `smp4`,
`smp8`, and `smp12` presets with benchmark instrumentation enabled. Keep the five
build directories at `build/m95/ipc1`, `ipc2`, `ipc4`, `ipc8`, and `ipc12`. Then run:

```sh
tools/bench/run_m95_matrix.sh 3
python3 tools/bench/m95_matrix_report.py build/m95/runs > docs/archive/M9.5_x86_ipc_baseline.tsv
```

The runner retains each serial capture and fails if QEMU or the guest does not
complete. The parser checks the completed call counts, overlap, phase populations,
and guest exit marker before emitting a row.
