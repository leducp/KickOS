# M9.9 ESP32-C6 LP boot witness

This first-stage witness answers only whether a single HP flash can
start the LP CPU and exchange a word through HP SRAM. `c6lpprobe` is a flat
diagnostic image, not a KickOS node on the LP CPU.

## Hardware constraints

The ESP32-C6 TRM v1.2, chapters 3, 5, 12 and 16, gives the LP core RV32IMAC,
one interrupt vector, machine mode only, 16 KiB LP SRAM at `0x50000000`, access
to 512 KiB HP SRAM, and shared atomics only in HP SRAM. Its reset PC is
`0x50000080`. The LP core can run code from HP SRAM, but a full KickOS image
cannot fit in LP SRAM: at the base tree "Finish Arm nano profile and microbit default",
the flat HP `hello` image uses 43,408 bytes of text, 348 bytes of initialized data, and
53,616 bytes of static RAM. At "Tighten the ESP32-C6 LP probe, doorbell fences and LP
grants" it measures 43,412, 348 and 53,616: the four extra text bytes are `arch_init`'s
test of the weak hook that only `c6lpprobe` resolves. The final LP image
therefore needs an LP-SRAM entry stub and code/data in a disjoint HP-SRAM
slice. The HP flash image must carry and load that LP image before waking it.

## Silicon result

The attached ESP32-C6-WROOM-1, revision v0.2, booted `c6lpprobe` from one
flash. The HP kernel copied a 1 KiB-bounded LP stub into LP SRAM, switched
the LP SRAM clock-domain mux, programmed the LP wake source, and triggered the
PMU. The LP stub stored `0x4c503939` in its own SRAM and in a linker-owned HP
SRAM marker. The HP image printed `c6lpprobe: LP wrote HP SRAM` in the final
capture. The LP access needed two narrow REE2 grants: 1 KiB of executable LP
bus space at `0x70000000` through LP_APM, and 64 bytes of HP SRAM marker space
through HP_APM. The LP core stayed in its reset REE2 mode.
The [raw capture](M9.9_lp_boot_capture.log) carries clean commit `b9444ae0`
("Prove ESP32-C6 LP wake and shared SRAM access") and SHA-256
`57475eb10ab2ce36d34cedd8c92981bf3fe9518a02f52f046b1fd77dd7ad8f07`.

The failed probes located those grants. With the PMU wake configured and the
LP code copied, LP_APM reported a refused instruction fetch at `0x70000080`.
Granting that LP bus alias let the stub write its local marker, while its HP
marker stayed zero. Granting the 64-byte HP SRAM range let the final store
land. The source records the diagnostic registers on failure. Those three steps
have archived captures, listed below.

**UNARCHIVED BENCH OBSERVATIONS.** Two further steps rest on bench runs whose
captures are not archived here: a grant on the documented `0x50000000` address
alone did not clear the LP_APM fetch refusal, and removing that grant and the
unused LP_APM0 grant still passed on silicon. Raw logs of the probe sequence
exist, but each was built from an uncommitted tree whose diff was not kept, so
none of them can be tied to the grant it ran with.

A second probe kept only the reset vector and jump in LP SRAM and copied its
payload to `0x40840000` in HP SRAM. The LP core executed that payload and
stored the same marker in both memories. This temporary payload address is
safe for the short probe only; the partition needs linker-owned, disjoint HP
and LP ranges before a full node runs. The payload needs a separate 1 KiB
HP_APM REE2 read/execute grant. Its capture was taken from the uncommitted tree
that became "Prove ESP32-C6 LP execution from HP SRAM", so it is stamped
`3a6e4caa-dirty` ("Archive ESP32-C6 LP silicon boot capture" plus those edits).

The archived probe captures normalize CRLF to LF; their digests cover the
archived bytes. The first three are stamped `359a92fe-dirty`, the base tree
"Finish Arm nano profile and microbit default" plus uncommitted probe edits.
Their `hp-apm` field reads the LP_APM0 exception registers at `0x600998C8`,
not HP_APM; the source now labels it `lp-apm0`.

The PMU software triggers also work in both directions. The HP writes bit 31
of `PMU_HP_LP_CPU_COMM`; with `PMU_HP_SW_TRIGGER_INT_ENA` set, the LP takes
interrupt 30 and reads bit 5 from `LPPERI_INTERRUPT_SOURCE` plus bit 31 from
`PMU_LP_INT_ST`. The LP
writes bit 30 of the same communication register, and the HP sees bit 29 in
`PMU_INT_RAW`. On the LP side, the peripheral accesses require two more narrow
LP_APM grants: the 1 KiB PMU register page as REE2 read/write and the 1 KiB
LPPERI page as REE2 read. LP_APM has four regions, so those use regions 1 and
3 while region 2 covers the LP reset stub.
The [doorbell capture](M9.9_lp_doorbell_capture.log) carries clean commit
`10e0530a` ("Prove ESP32-C6 LP PMU doorbells in both directions"), a `PASS` marker,
and SHA-256 `96b0d3bd400d1aba9fd0e8445bc930e3b6ffca5c1ad0bfa21c413370df996ded`.
Its `HP APM` field is the LP_APM0 exception registers at `0x600998C8`, now labelled
`LP APM0` in the source.

**UNARCHIVED BENCH OBSERVATIONS.** Two statements about the doorbell probe rest
on bench runs whose captures are not archived: clearing
`PMU_HP_SW_TRIGGER_INT_ENA` left the LP interrupt silent, and an attempted
LP_APM region 4 wrote outside the region table and did not permit the peripheral
read. As with the grant sequence above, the raw logs came from uncommitted trees
whose diffs were not kept, so none can be tied to the configuration it ran.

## What this first-stage witness did not yet prove

At this stage the LP node still needed its own flat, machine-mode RV32 backend; timer and
interrupt dispatch for LP interrupt 30; a disjoint HP-SRAM image loaded by the
HP image; bidirectional PMU doorbells into the AMP ring; and an unattended
partition bench capture. The existing own-image builder configured all peers
from one board and one Kconfig posture; the final pair uses that same posture
with a node-specific LP backend. No AMP correctness conclusion follows from this
boot witness alone. The completed [M9.9 AMP record](M9.9_amp.md) carries the
ten-run partition witness.
