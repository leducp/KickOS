# M9.4.1: x86 lock-scaling probe

> **Status: historical host measurement made before the x86 SMP port.** Recorded
> 2026-09-25 from `M9.4.1` at `414a787a`. The actual KickOS SMP bring-up and
> measurements are in [M9.4.1_x86_smp.md](M9.4.1_x86_smp.md).

## Why this probe is separate

The `qemu-x86_64` KickOS backend only runs one kernel core. `CMakeLists.txt`
refuses more than one because `aspace_x86_64.cc` has no remote TLB invalidation;
that file also has a compile-time assertion. The q35 port has no secondary-core
launch or SMP predicate. Its descriptor tables, interrupt/context state, panic
stack, and benchmark switch stamp are single-core. Giving QEMU 12 vCPUs does not
make KickOS run on 12 kernel cores.

This probe instead measures a **synthetic contention envelope** on the host:
one ticket lock shared by all workers versus the same ticket-lock operations on
one lock per worker. The latter is a ceiling for *perfect* partitioning, not an
implementation of M9.4 stage 2. Each worker runs a fixed amount of private work
outside and inside the lock. It does no KickOS IPC, interrupt, scheduler, or
doorbell work. The spin loop does not poll a KickOS doorbell, as a real backend
must. The result cannot establish an end-to-end gain or reopen the M9.4 R0 gate.

## Machine and method

- AMD Ryzen AI 9 HX PRO 370, Linux 7.1.13+deb14-amd64, GCC 16.2.0. One
  package, 12 physical cores, 24 hardware threads. CPUs 0-3 report a 5158 MHz
  maximum; CPUs 4-11 report 3289 MHz. CPUs 12-23 are their SMT siblings.
- Workers are pinned with `pthread_setaffinity_np`. The program refuses a CPU
  without invariant TSC. It uses an invariant-TSC busy interval of 256, 512, or
  2048 requested cycles inside the lock and 1024 or 8192 outside. The requested
  interval includes polling overhead and is a synthetic load, not a measured
  KickOS critical-section length.
- Three 250 ms runs per case; the table uses their median operations per
  second. The raw TSV files contain minimum and maximum too. `taskset` restricts
  the CPU set for the homogeneous subsets. The 24-thread SMT rows in the full
  file show large variation for the global lock, so they are not used below.

Build and run from this worktree:

```sh
g++ -std=c++17 -O2 -Wall -Wextra -Werror -pthread \
  tools/bench/m941_lock_scaling.cc -o /tmp/m941_lock_scaling
/tmp/m941_lock_scaling 0.25 3 > docs/archive/M9.4.1_x86_all.txt
taskset -c 0-3 /tmp/m941_lock_scaling 0.25 3 > docs/archive/M9.4.1_x86_fast4.txt
taskset -c 4-11 /tmp/m941_lock_scaling 0.25 3 > docs/archive/M9.4.1_x86_slow8.txt
```

The ticket lock becomes costly on eight and twelve physical cores when the
private interval is short. When it is long, even twelve cores have little
headroom from perfect sharding in this probe. The eight slow-core subset shows
that the high-contention result does not require mixing the two core classes.
Neither case says how much of an actual KickOS workload M9.4 stage 2 could move
outside its lock.

## One-core KickOS control under KVM

The `qemu-x86_64-bench` image built from `414a787a` passes
`check_bench_lock.sh` under `q35,accel=kvm`, `-cpu host`, `-smp 1`: the gate saw
80,243 lock-hold samples, p50 208 cycles, p99 512 cycles, and max 32,020 cycles.
A subsequent raw run reported p50 512 and p99 768 in its first window. Those
one-core distributions give a rough scale for the synthetic intervals but are
not a contention measurement and are visibly run-dependent.

The gate invocation was:

```sh
QEMU_MACHINE='q35,accel=kvm' QEMU=qemu-system-x86_64 \
QEMU_EXTRA='-cpu host -smp 1' KICKOS_BOOT=uefi-pe QEMU_TIMEOUT=120 \
tests/integration/check_bench_lock.sh \
  /tmp/m941-x86-bench/user/apps/common/bench/bench.efi 1
```

## What a kernel result needed at the time

An x86 shared-kernel SMP port must first launch application processors, give
each its descriptor/TSS/IST and GS-backed syscall state, interrupt/context
state, APIC timer and IPI routing, panic stack, and benchmark state. It needs a
ticket lock that services doorbells while waiting and a synchronous remote TLB
shootdown before the CMake refusal and page-table assertion can be removed.
Then the same KickOS workloads can run at 1, 2, 4, 8, and 12 guest kernel cores
with the vCPUs pinned to named physical cores. On this heterogeneous host the
fast, slow, and mixed sets must be reported separately. Only those runs can
measure the actual BKL cost and rerun M9.4's stage-2 stop condition on x86.

[fast four](M9.4.1_x86_fast4.txt), [slow eight](M9.4.1_x86_slow8.txt).
