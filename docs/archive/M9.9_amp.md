# M9.9: ESP32-C6 HP/LP AMP silicon record

M9.9 is decided on clean implementation commit `45516b62` ("Run ESP32-C6 HP and LP as AMP
nodes"). An ESP32-C6-WROOM-1
(the attached v0.2 part) booted two own-image KickOS nodes from one flash image,
without a button or manual reset between captures. Ten successive remote bench
runs passed the same partition gate. This is a deployment and far-call witness;
it is not an AMP throughput measurement.

## Shape and reason

The HP core runs node 0 at `0x40800000`; the LP core runs node 1 at
`0x40838000`. Each has 224 KiB of private HP SRAM, and the 64 KiB shared
window begins at `0x40870000`. The ESP32-C6 ROM loads both image segments
from one flashed partition. HP copies a small reset stub to the LP's fixed
`0x50000080` entry in LP SRAM, programs narrow LP grants for its node slice,
shared window and needed peripheral pages, and wakes it through PMU. The full
LP kernel cannot fit in its 16 KiB local SRAM; it executes from its HP SRAM
slice. The linked peer images agree on their shared window and loaded spans.

The LP core has one interrupt vector, machine mode only, and no PMP. This removes
the HP node's per-thread privilege split, but does not leave HP's private SRAM
open to LP. The LP remains an REE2 bus master; the HP APM grants REE2 read,
write and execute only in node 1's slice, and read/write in the shared window.
Its catch-all region denies REE2 access elsewhere (TRM v1.2, 16.3.2.3). The LP APM
separately grants the reset stub and LP peripheral pages. Only a TEE-mode
master can change these APM registers. This is directional LP-to-HP memory confinement;
the trusted HP core can still access both node slices. An APM denial returns zero
for a read or drops a write and records an APM violation, rather than causing a
PMP fault (TRM v1.2, 16.5). The first-stage [LP SRAM probe](M9.9_lp_boot.md)
observed an HP SRAM write refused until its narrow grant was added; that probe's
captures are archived there. The final ten-run
partition gate checks successful access and IPC, not a denied access to node 0's slice.

**THE TEN CAPTURES RAN WITH A WIDER LP PERIPHERAL GRANT THAN THE TREE NOW PROGRAMS.** At
"Run ESP32-C6 HP and LP as AMP nodes", LP_APM region 1 granted REE2 read/write on the whole
4 KiB block `0x600B0000`-`0x600B0FFF`. That covers the PMU and LP timer the LP kernel uses, and
also LP_CLKRST (`0x600B0400`) and the eFuse controller (`0x600B0800`), which it never touches;
region 3 granted REE2 read on the LPPERI page, which only the first-stage probe reads. LP_APM has
four regions and region 0 is the reset catch-all, so region 3 is the only one that can carry a
second grant. The tree now grants region 1 the 1 KiB PMU page and region 3 the 1 KiB LP timer
page, both read/write. That narrowing is build-only: no silicon capture has run with it yet.

The LP core's external-pending bit is read-only, so a requested context switch rings the
HP-to-LP PMU input. The switch leaves that interrupt latched until the newly
seated context can service any concurrent HP request. The two PMU directions
otherwise feed the existing AMP ring protocol. The LP RTC's rate is measured
against HP's clock before wake; the ten measured values ranged from 597,379
to 597,879 Hz on this part. Using the assumed 150 kHz rate made the LP timer
expire far too quickly and far calls time out.

HP owns UART0. The C6 has an LP UART, but this port wires none for the LP node: its
console writes are a sink, and it publishes boot and served-call records in shared
memory for HP to report. The
gate reads the LP `mtvec` value, app-alive records, four transformed replies,
the LP served count, and both doorbell counts. It rejects a missing second ROM
load segment, a fault, a panic, or an incomplete capture. This does not claim
that LP debug text is preserved.

## Repeated capture

The command below built and flashed the merged partition, armed the serial
reader, reset the board and ran `check_c6_amp_capture.py` on each capture:

```sh
BENCH_HOST=GlaDOS TAG=m99campaign VARIANT=amp2-n0 APP=ampping_n0 \
  AMP_PARTITION=1 CAP_SECS=15 bash tools/bench/bench.sh esp32c6-wroom
```

Each of ten sequential invocations passed. The archived UART captures normalize CRLF to LF; their digests cover the archived bytes. Every archived log reports commit
`45516b62` ("Run ESP32-C6 HP and LP as AMP nodes"), the two ROM loads, LP `mtvec=0x40838c01` in node 1's slice,
two live node apps, four `ping -> pong` replies, LP served record 4, and
positive bell and drain counts on both nodes. The ROM prints a SHA-256
comparison failure against an all-`f` expected digest and explicitly boots

## Far-call retries

**IN EVERY ONE OF THE TEN RUNS, ROUNDS 2 AND 4 ARE ANSWERED ON THE SECOND ATTEMPT AND ROUNDS 1
AND 3 ON THE FIRST.** `ampping_n0` prints `(node 1 answered on attempt 2)` BEFORE the retried
round's own `ping` line, so each such line belongs to the round below it, not the one above.
`check_c6_amp_capture.py` attributes each attempt line that way and prints the attempt count of
every round and the list of retried rounds; on all ten archived logs it reports rounds 2 and 4.
No run needed more than two attempts, and every round carried its transformed reply.

**ROUND 1 NEEDS NO RETRY, and the reason is the app-alive sweep.** The retry loop exists because
the peer is released after node 0 and parks in its own time, so a first call can find no receiver
(the comment above the loop in `main_n0.c`). On this pair the sweep before the rounds already
waits until the LP app has published its alive mark, which it does just before its first
receive, and round 1 never retried.

**WHY ROUNDS 2 AND 4 RETRY IS OPEN.** What the capture does fix: node 0's doorbell service ran six
times (`bells=6`, every run), which is the four replies plus one answer per failed attempt, while
the LP app's own served record stays at four. So each failed attempt was answered by the LP kernel
without reaching the server, rather than lost. The app does not print the failed attempt's return
code, so the capture cannot tell an immediate refusal from a timeout.

*Hypothesis, not established:* `ampserve` answers with `kos_reply` and only then re-enters
`kos_reply_recv`, so after every answer the LP server is off its receive for a short window, the
same window `main_n0.c`'s notice arm sleeps across before its own call. A far call arriving in it
finds nothing parked and is refused on the spot (design-multicore N6f). Rounds 2 and 4 are the two
issued straight after a round answered on its first attempt. Round 3 follows a retried round, after
which node 0 printed one more console line before calling, and round 1 follows the sweep. The
alternation fits node 0's turnaround after a first-attempt answer being shorter than the LP's
return to its receive (20 MHz, executing from HP SRAM), with one extra printed line enough to cover
the gap. A silicon run printing the first attempt's return code, or settling before every round,
would confirm or refute it.

The two new `trap_redzone` presets pass on their own built images. Node 0's
deepest privileged syscall, exit and return paths measure 832, 640 and 640
bytes against the corresponding AMP reservations; node 1 measures 624, 384
and 384 bytes. `amp_elf_agree`, `preset_defconfig`, `trap_redzone_decls`,
`seam_defaults` and `ternary` also pass. These checks bound this build's
callgraph and image geometry; they do not establish another toolchain or
silicon revision's behavior. The first-stage LP wake and doorbell probes remain
in [the boot witness](M9.9_lp_boot.md).
