# M9.4.1: q35 x86_64 shared-kernel SMP bring-up

The q35 UEFI image now starts application processors through a reserved low SIPI page,
installs per-core GDT, TSS, interrupt stacks and GS-backed syscall state, and seats each
processor in the shared scheduler. The x86 backend uses a ticket kernel lock, x2APIC
doorbells, software-routed IRQ delivery, and synchronous remote TLB invalidation.
Configured presets drive 2, 4, 8 or 12 kernel cores. The existing one-core bench image
is the control. The q35 software IRQ controller has no I/O APIC device-line routing.

## The measurement that exercises every core

The ordinary `bench` app pins its semaphore and call/reply players to core 0. Its 12-core
image boots every AP but leaves most of them idle. `bench_smp` instead launches one thread
per kernel core, pins each thread to that core, waits for all to reach a release barrier,
then makes each call `kos_yield` 2,000,000 times. One yield enters the shared scheduler
lock. The aggregate rate therefore measures a deliberately lock-heavy path with real
concurrent kernel calls; it is not a context-switch rate, and the workers do no private
work between calls.

Each image ran three times with QEMU q35, KVM, `-cpu host`, 512 MiB RAM and OVMF 4M.
The one-core KickOS image used two QEMU vCPUs because this machine's one-vCPU OVMF run
stalled before loading the image; the extra vCPU runs no KickOS kernel. Guest workers
are pinned to guest cores. QEMU vCPU threads were not pinned to host CPUs, and this host
has 12 heterogeneous physical cores and 24 hardware threads. The numbers are exploratory
guest measurements, not isolated silicon measurements.

| KickOS cores | Median yields/s | Range over 3 runs | Median relative to 1 core |
| ---: | ---: | ---: | ---: |
| 1 | 8,265,805 | 8,178,170-8,307,472 | 1.00 |
| 2 | 8,948,532 | 8,941,659-8,976,621 | 1.08 |
| 4 | 8,258,100 | 8,075,477-8,334,985 | 1.00 |
| 8 | 2,351,311 | 2,347,679-2,772,072 | 0.28 |
| 12 | 2,101,406 | 2,094,100-2,125,040 | 0.25 |

Every worker completed its 2,000,000 yields, and their active intervals overlapped.
The full per-run counts and guest wall times are in
[M9.4.1_x86_smp_yield.tsv](M9.4.1_x86_smp_yield.tsv). `span_ms` runs from the
first worker start to the last worker finish. The data show that this
particular shared-lock path saturates by four guest cores and loses aggregate throughput
at eight and twelve. They do not measure a finer-grained implementation or establish
how much normal IPC work could move outside the lock.

## An important measurement correction

The first x86 SMP implementation used CPUID for every `arch_cpu_id()` call. On KVM the
short pinned sweep then yielded about 93,000 calls/s at two cores and 68,000 calls/s at
twelve. Moving core identity to the per-core GS block raised those same 10,000-call
short sweeps to about 8.8 million and 2.3 million calls/s. The table above uses only
the GS-backed build and longer runs. The early CPUID figures do not measure the BKL.

The separate `bench-sweep-row` branch found that sweep-only benchmark distributions
inflated the row accessed by every phase sample. Its correction is included in this
worktree's benchmark code. Call/reply and phase figures from the earlier layout are
not comparable to captures from this one.

## Reproduce

Build an image from the corresponding preset, then run the pinned sweep under KVM:

```sh
source /home/leduc/projets/KickOS/.session/env.sh
cmake --preset qemu-x86_64-smp12 -B /tmp/m941-smp12
cmake --build /tmp/m941-smp12 --target bench_smp_image -j12
tools/bench/run_m941_smp.sh \
  /tmp/m941-smp12/user/apps/common/bench/bench_smp.efi 12 /tmp/m941-smp12-run
```

For the one-core control, use preset `qemu-x86_64-bench` and set
`KICKOS_M941_VCPUS=2` when invoking the runner. The script retains the full console
capture as `run.log` and a CR-stripped `run.txt` in the output directory.

The ordinary bench image remains useful for boot, doorbell, end-to-end IRQ and IPC
regressions. Its call/reply players stay on core 0, so its call/reply throughput should
not be read as a multicore scaling curve.
