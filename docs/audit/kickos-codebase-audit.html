The XMC SPI flip blocker was folklore, recorded as a property of the silicon: FDR/BRG/CCR/INPR are PV-write-only, therefore "privileged by hardware design", therefore "for those boards the design does not work". PV is a genuine Infineon term — RM Table 2 gives U unprivileged, PV privileged, BE bus error — but the conclusion drawn from it is contradicted by the project's own silicon record. consoledemo's scramble test spawns an UNPRIVILEGED thread holding a granted U0C0 window and writes FDR, BRG, SCTR, TCSR, PCR, CCR and KSCFG from inside it; the recorded XMC silicon PASS is that the panic banner survives a DRIVER-GARBLED UART, which it can only be if those writes landed. The real obstacle is PLACEMENT — the bring-up runs in root, and a flipped root holds no MMIO grant for U0C1.

Fix: The three records are fixed and the code move is still open. The THIRD copy, in CMakeLists.txt — the one that decides a preset — no longer tells a reader the registers sit "OUTSIDE any grantable window": it names the four offsets and the 0x200 channel window they sit inside, and calls the blocker placement. Both documents are upgraded from merely "unwitnessed" to "contradicted, not untested", each carrying the reasoning that was never written down beside the claim: the scrambler is spawned privileged=false with the granted U0C0 window, writes exactly the registers in question, and the recorded silicon PASS cannot have happened unless those writes landed.  Medium Security MMIO grant granularity — KSCFG inside the granted USIC window

Granting a peripheral window grants the whole peripheral, including its clock. The same consoledemo scramble test shows an unprivileged driver holding a granted USIC window retune the baud, disable the channel and gate its own kernel clock: KSCFG — MODEN, the channel's module clock enable — lives at win_base + off::KSCFG, INSIDE the window handed over. So an MMIO grant is not "may use this device", it is "may enable, configure and disable this device". A capability and isolation observation, ORTHOGONAL to root privilege: it is equally true of any unprivileged holder on an unflipped board, and it is a property of window granularity rather than a regression.

Fix: Nothing to build, and recorded because the natural reading of "unprivileged driver" is more confined than what is actually handed over. Two consequences worth carrying: a window that happens to span two peripherals hands over both, and a driver that can gate its own clock can silence itself in a way the kernel cannot distinguish from a dead device. Narrowing it would need sub-window or per-register granularity, which PMSA cannot express at this size. Filed in design-unprivileged-root.md §9.

N11new Open Low Arch coherency arch/common — arch_ram_alloc

arch_ram_alloc reserves a naturally-aligned power-of-two block and never reclaims the run-up it skipped to reach that alignment. That is why addab66 has to allocate idle before root even though root is the larger block: taking the small one first lets it sit inside the large one's run-up.  Low Security user/src/newlib_stubs.cc — __malloc_lock

__malloc_lock and __malloc_unlock are no-op weak stubs, so newlib's malloc has no reentrancy guard. Two threads allocating concurrently silently corrupt the arena. The comment documented this as a FOOTGUN and deferred the fix, implying the guard was a handful of lines away.

Fix: STILL OPEN, but the question is now closed rather than deferred: it cannot be done where it is filed, and 291815c replaces the vague FOOTGUN note with three measured facts. (1) Newlib takes this lock RECURSIVELY — disassembling the linked cxxtest image shows _free_r acquiring it and calling _malloc_trim_r, which acquires it again — so a non-recursive lock self-deadlocks and a 'second entry means a second thread' detector fires on a legitimate free. (2) A recursive lock must answer 'am I already the owner', and userspace has no thread identity: no self syscall, and a stack address is not a reliable key. (3) Even given identity there is no lock object two threads can name — capabilities are PER-TASK, and sharing one needs a reserved index, of which none are left. So 'an IrqLock-equivalent is the minimum' is not available: this file is userspace, which is the whole point of the surrounding milestone. Real fix: per-thread libc state via TLS, or a kernel-held lock behind a syscall.

The syscall boundary — 11.6 KiB across dispatch, cap, IPC, spawn and the mem funnel — is still the single largest block, and that is correct here because it is nearly all validation. Scheduler, sync, domains, time and IRQ together are 6.9 KiB. bench/ is opt-in and off by default, so it costs a shipped image nothing.

Questionable for a microkernel

The console is 2.2 KiB of privileged code (console.cc + console_tx.cc) doing a job that is userspace work on paper. The handover mechanism exists to move it out, and this branch gave the sim a posture that finally tests the published route — but until an image actually publishes, every board pays for a device driver in the TCB. The chip_* layer at 3.9 KiB is the other big privileged driver block.

RAM concentration

Static RAM halved, and what is left is more concentrated, not less: instance.cc is 8.9 KiB of the 10.1 KiB total, or 88%, where the two-object split used to be 10.7 + 8.9. Every remaining byte is the static object pools, so a board cutting MAX_THREADS is now cutting almost exactly this and nothing else.
