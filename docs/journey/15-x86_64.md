# 15. x86_64: the same walk on a PC

This chapter walks the x86_64 port on QEMU's `q35` PC with four cores. It follows the same stops
as the reference walk on the Cortex-M4 ([power-on](01-power-on.md) and
[the first syscall](02-first-syscall.md)), and shows only what x86_64 does differently and why.
By the end you will have seen firmware hand the kernel a CPU that is already in 64-bit mode with
paging on, the three descriptor tables a PC needs before it can take a single interrupt, the
`SYSCALL` instruction and the three instructions that run on a stack the caller chose, the local
APIC timer that has to be measured before it can be used, and the page tables a task runs under.

The concepts are in the Book: [Context switching and the silicon contract](../book/context-switching-and-the-silicon-contract.md)
(what a switch must save, and why it is assembly), [Interrupts and traps](../book/interrupts-and-traps.md),
[The syscall path](../book/the-syscall-path-trap-dispatch-return.md) and
[The time base](../book/the-time-base-a-monotonic-clock-you-can-trust.md). The arch seam every
port answers is in [Reference: porting](../reference/porting.md). The page-table walker is shared
with arm64 and rv64, and [the MMU chapter](10-the-mmu.md) walks it; this chapter shows only what
x86_64 feeds it.

## How this port differs, in one table

| Stop | Cortex-M4 (reference) | x86_64 |
|---|---|---|
| Who runs first | the CPU reads a vector table at reset | UEFI firmware calls `efi_main` in 64-bit mode, paging on |
| The image | an ELF linked where flash is | a PE32+ UEFI application the firmware loads |
| Trap table | the vector table, one word per exception | the IDT, 256 gates, plus a GDT and a TSS it depends on |
| Syscall | `svc`, hardware stacks 8 words | `syscall`, hardware stacks nothing and loads no stack pointer |
| Return to the thread | exception return (`bx lr` with `EXC_RETURN`) | `iretq` from a frame the software built |
| Deferred switch | PendSV, lowest priority | the interrupt exit returns a different frame |
| Timer | SysTick | the local APIC timer, calibrated against the legacy PIT |
| Interrupt controller | NVIC | a software controller rung through a local APIC vector |
| Protection | MPU regions committed at the switch | page tables: one root per task, loaded into CR3 |

## The image and the debugger

The build is `build/qemu-x86_64-smp4`, and the app is
`user/apps/common/hello/hello.efi`: two threads that ping-pong. It is not an ELF. The KickOS
linker script `arch/x86/x86_64/pe_image.ld` and `tools/x86_64-link.sh` turn the objects into a
PE32+ file with `-e efi_main` and `--image-base=0x400000`, which is the format UEFI firmware
loads. QEMU's `-kernel` cannot start such a file, so the test harness copies it onto a small FAT
disk as `EFI/BOOT/BOOTX64.EFI` (the path firmware boots when it has no boot entry of its own) and
boots the OVMF firmware from it. `tests/lib/gate.sh` (`boot_args`) holds the exact recipe;
`tools/esp-x86_64.sh` builds the disk:

```
B=build/qemu-x86_64-smp4
tools/esp-x86_64.sh $B/user/apps/common/hello/hello.efi esp.img
cp /usr/share/OVMF/OVMF_VARS_4M.fd vars.fd && chmod u+w vars.fd
qemu-system-x86_64 -M q35 -smp 4 \
    -cpu qemu64,+ssse3,+sse4.1,+sse4.2,+popcnt,+cx16,+lahf-lm,+avx,+avx2,+bmi1,+bmi2,+fma,+f16c,+movbe,+abm,+xsave,+xsaveopt,+smep,+smap,+rdtscp,+x2apic \
    -m 512 -net none -no-reboot -device isa-debug-exit,iobase=0xf4,iosize=0x04 \
    -drive format=raw,file=esp.img \
    -drive if=pflash,format=raw,unit=0,readonly=on,file=/usr/share/OVMF/OVMF_CODE_4M.fd \
    -drive if=pflash,format=raw,unit=1,file=vars.fd \
    -nographic -gdb tcp::1234 -S
```

`ctest --test-dir $B -N -V -R qemu_x86_64_hello` prints the processor model and machine the
harness uses. Four gdb habits for this port:

- gdb cannot read this PE file's debug information (it complains about `DW_FORM_strp`), so give
  it a copy with symbols only: `objcopy --strip-debug hello.efi hello.sym.efi`, then
  `gdb-multiarch hello.sym.efi -ex 'set architecture i386:x86-64' -ex 'target remote :1234'`.
  Every stop below breaks on symbols and reads registers and memory, which is all it needs.
- Firmware loads the image after you connect, over any software breakpoint gdb planted. Start
  with a hardware breakpoint: `hbreak efi_main`, `continue`, `delete`. From there the image is
  in memory and ordinary `break` works.
- For a PE target gdb uses the Windows data model, where `long` is 32 bits. Write
  `*(long long*)` when you mean a 64-bit word.
- Each of the four cores is a gdb thread. A breakpoint can fire on any of them; the
  `Thread N hit` line says which.

The addresses below are from one run; the image is loaded at its preferred base `0x400000`, and
the boot banner says so (`x86_64 app relocation: base=0x0000000000400000 load_delta=0x0000000000000000`).

### Stop 1: firmware calls the kernel
**Where:** `arch/x86/x86_64/entry_x86_64.cc`, `efi_main`; then `kickos_x86_64_floor`
(`arch/x86/x86_64/floor_x86_64.cc`)

On the Cortex-M4 the CPU itself starts KickOS: it reads the initial stack pointer and the
`Reset_Handler` address from the vector table and runs. On a PC the CPU starts in 16-bit real
mode in firmware, and the firmware does all the climbing: it enters protected mode, then long
mode (64-bit), builds page tables that map memory one-to-one (an *identity map*: virtual address
equals physical address), installs its own descriptor tables, and finally calls the
application's entry point. So the first KickOS instruction already runs in 64-bit mode, with
paging on, on a stack the firmware chose, and with interrupts ENABLED.

`efi_main` is called with the Microsoft x64 calling convention (`KICKOS_EFIAPI`), so its two
arguments arrive in `rcx` and `rdx`, not in `rdi` and `rsi` as everywhere else in KickOS. It first
checks that the processor has the instruction set the image was compiled for (x86-64-v3, see
`arch/x86/chip/q35/cpu.cmake`); `kickos_x86_64_floor` is compiled for the base level so that it can
run on an older processor and refuse cleanly. Then it reads the state firmware handed over and
masks interrupts:

```cpp
    // Read BEFORE the cli, which is the last moment the flag firmware handed over is visible.
    // Two volatile asm statements cannot be reordered against each other.
    uint64_t rflags_in = 0;
    __asm__ volatile("pushfq\n\tpop %0" : "=r"(rflags_in) : : "memory");
    uint64_t const cr0_in = read_cr0_ordered();
    uint64_t const cr3_in = read_cr3_ordered();
    uint32_t const efer_lo = read_msr_low_ordered(msr_efer);

    __asm__ volatile("cli");
```

The console line it prints from these values is the handover report:
`handover if=1 paging=1 longmode=1 root=1 wp=1 nx=1 nxcap=1`.

**Try it:** `hbreak efi_main`, `continue`, then `p/x $cr0`, `p/x $efer`, `p/x $cs`, `p $eflags`,
`p/x $rcx`, `p/x $rdx`. You should see:

```
Thread 1 hit Breakpoint 1, 0x000000000041f28f in efi_main ()
$1 = 0x80010033          <- cr0: PG (bit 31), WP (bit 16), NE, ET, MP, PE
$2 = 0xd00               <- efer: LME (bit 8), LMA (bit 10), NXE (bit 11)
$3 = 0x38                <- cs: the FIRMWARE's code selector, not KickOS's
$4 = [ IOPL=0 IF ZF PF ] <- IF set: firmware runs with interrupts on
$5 = 0x1e53a618          <- rcx: the image handle
$6 = 0x1fcc1018          <- rdx: the UEFI system table
```

**Why, and the contract:** [Book: the machine underneath](../book/the-machine-underneath.md),
[Reference: boards, qemu-x86_64 caveats](../reference/boards.md)

### Stop 2: leaving the firmware behind
**Where:** `arch/x86/x86_64/entry_x86_64.cc`, `efi_main` (the second half), `pick_arena`,
`early_idt_load`, `fp_enable_install`, `kickos_x86_64_fp_enable`

While firmware is still in charge, KickOS asks it two things. `get_memory_map` describes every
range of physical memory; `pick_arena` keeps the largest run of free ("conventional") memory
above 1 MiB, aligned up to 2 MiB, and that run becomes all the RAM KickOS will ever use. Then
`exit_boot_services` ends the firmware's life: from that call on, firmware code and data may be
reused, and nothing of it may be called again. The memory map buffer is a static array on
purpose: allocating it from firmware would change the map and invalidate the key that
`exit_boot_services` must be given.

Two things must happen at once after that call. The interrupt table firmware left behind
(the IDT) points at handlers in memory that has just been released, and `cli` does not hold off
the non-maskable interrupt or a machine check. So `early_idt_load` installs a 32-gate stopgap
table whose every gate reports and halts. Then `fp_enable_install` turns on x87, SSE and AVX with
the `xsetbv` instruction and checks that the save area for them is exactly the 832 bytes the
switch code reserves (`KICKOS_X86_64_XSAVE_SIZE`). On a Cortex-M4F the FPU is enabled in a
coprocessor register and its state is saved lazily by the hardware; here every thread's vector
state is saved eagerly with `xsave64` on every switch.

**Try it:** run the image without gdb and read the console. You should see, among others:

```
KICKOS-X1 8c41d7a2 x86_64/q35 uefi-handover map descriptors=106 stride=48 version=1 conventional_pages=117263 arena=0x0000000001800000 arena_pages=107324
KICKOS-X1 8c41d7a2 x86_64/q35 uefi-handover fp enabled em=0 ts=0 mp=1 ne=1 osfxsr=1 osxmmexcpt=1 osxsave=1 xcr0=7 xsave=832
KICKOS-X1 8c41d7a2 x86_64/q35 uefi-handover boot services left
KICKOS-X1 8c41d7a2 x86_64/q35 uefi-handover if_after_exit=0
```

**Why, and the contract:** [Reference: invariants, `x86-64-kernel-no-vector-state`](../reference/invariants.md)

### Stop 3: the landing, and the road to `kmain`
**Where:** `arch/x86/x86_64/landed_kernel_x86_64.cc`, `kickos_x86_64_landed`,
`kickos_x86_64_kernel_main`; `arch/x86/chip/q35/chip_q35.cc`, `kickos::q35::ram_publish`;
`kernel/init/kmain.cc`, `kmain`

On the Cortex-M4 `Reset_Handler` copies `.data` from flash, zeroes `.bss`, runs the constructors,
calls `arch_init` and enters `kmain`. Here the firmware's loader already did the first two: it
placed every section at its address and zero-filled the tail of each, so there is no copy table
to walk (`arch/x86/x86_64/sources.cmake` says why `common/startup_ranges.cc` is left out). What
is left is short:

```cpp
extern "C" void kickos_x86_64_landed(uintptr_t ram_base, uint64_t ram_size)
{
    kickos::q35::ram_publish(ram_base, static_cast<size_t>(ram_size));
    for (void (**fn)() = __init_array_start; fn != __init_array_end; fn++)
    {
        (*fn)();
    }
    // The return address `call` pushes is what gives the callee its psABI stack alignment.
    uintptr_t const top = reinterpret_cast<uintptr_t>(g_boot_stack) + boot_stack_bytes;
    __asm__ volatile("movq %0, %%rsp\n\t"
                     "xorl %%ebp, %%ebp\n\t"
                     "call kickos_x86_64_kernel_main"
                     // ...
```

It publishes the arena (the RAM bounds come from the firmware map, not from a linker script as
on the Cortex-M4), runs only the KERNEL's constructors (`pe_image.ld` collects them into `.kosinit`; the
app's run later, unprivileged, from `kickos_root_entry`), and moves off the firmware's stack onto
a 128 KiB boot stack of its own. `kickos_x86_64_kernel_main` then calls `arch_init`, then
`kickos::x86_64::app_relocate` (Stop 6), then the same `kmain` every board runs.

**Try it:** `break kickos_x86_64_landed`, `continue`, `p/x $rdi`, `p/x $rsi`. You should see the
arena the console line named: `$1 = 0x1800000` and `$2 = 0x1a33c000` (107324 pages of 4 KiB).

**Why, and the contract:** [Reference: porting, "Adding a board/chip"](../reference/porting.md)

### Stop 4: the three descriptor tables
**Where:** `arch/x86/chip/q35/chip_q35.cc`, `arch_init`, `legacy_pic_init`;
`arch/x86/x86_64/desc_x86_64.cc`, `kickos::x86_64::desc_init`, `build_idt`, `build_tss`,
`load_gdt`; `arch/x86/x86_64/include/kickos/arch/desc.h`; `arch/x86/x86_64/trap_x86_64.S`,
`kickos_x86_64_vector_base`

The Cortex-M4 needs one table to take an exception: the vector table. x86_64 needs three, and
they point at each other.

- The **GDT** (global descriptor table) holds *segment descriptors*. In 64-bit mode segments no
  longer translate addresses, but the code segment still carries the privilege level: ring 0
  (kernel) or ring 3 (user). KickOS builds one per core with five live entries: kernel code
  `0x08`, kernel data `0x10`, user data `0x1b`, user code `0x23` (the low two bits of a selector
  are its ring), and the TSS at `0x28`. Their order is not free: `SYSCALL` and `SYSRET` compute
  selectors by adding 8 and 16 to one base, and `desc.h` asserts it.
- The **TSS** (task state segment) is no longer used for task switching. It holds two things
  KickOS needs: `rsp0`, the stack the CPU switches to when an interrupt arrives while ring 3 runs,
  and the *interrupt stack table*, dedicated stacks for the double fault, the NMI and the machine
  check. It also carries the I/O permission bitmap (one bit per port, Stop 11).
- The **IDT** (interrupt descriptor table) is the real equivalent of the vector table: 256
  gates, each naming a handler and a code selector. All 256 are filled, so even a vector KickOS
  never planned for still reports. Every gate is an *interrupt gate*, which clears the interrupt
  flag on entry.

`arch_init` masks the legacy i8259 interrupt controller first (`legacy_pic_init`), because
firmware leaves it delivering on vector 8, which is the double-fault vector. Only then does
`desc_init` load the new tables. The 256 IDT entries point at 256 small stubs in
`trap_x86_64.S`. Each pushes a zero where the hardware pushes no error code, pushes its vector
number, and jumps to one common entry, so a single frame layout (`struct trap_frame` in
`arch/x86/x86_64/include/kickos/arch/trap.h`) covers every vector.

**Try it:** `break 'kickos::x86_64::apic_init()'` (it runs right after these tables are loaded),
`continue`, then `monitor info registers` (QEMU's own register dump, sent through gdb). You
should see, trimmed:

```
CS =0008 0000000000000000 ffffffff 00af9a00 DPL=0 CS64 [-R-]
FS =0000 ffff8000f5000000 00000000 00000000
GS =0000 00000000004c7d40 00000000 00000000
TR =0028 00000000004ada40 00002068 00008900 DPL=0 TSS64-avl
GDT=     00000000004ada00 00000037
IDT=     00000000004a69e0 00000fff
CR0=80010033 CR2=0000000000000000 CR3=000000001f401000 CR4=00340668
EFER=0000000000000d01
```

The code selector is now KickOS's `0x08`. The GDT limit `0x37` is 7 entries of 8 bytes (the TSS
descriptor takes two), and the IDT limit `0xfff` is 256 gates of 16 bytes. `info symbol 0x4ada00`
names `g_cpu + 24576`, this core's slot in the per-core descriptor array, and `info symbol
0x4a69e0` names `g_idt`. CR3 is still the firmware's page-table root. The FS base is a poison
value no thread uses (`KICKOS_X86_64_FS_POISON`), and the new low bit in EFER is the next stop.

**Why, and the contract:** [Book: interrupts and traps](../book/interrupts-and-traps.md)

### Stop 5: arming the fast syscall instruction
**Where:** `arch/x86/x86_64/ring3_x86_64.cc`, `kickos::x86_64::ring3_init`, `ring3_cpu_init`;
`arch/x86/x86_64/include/kickos/arch/ring3.h`, `struct cpu_block`

The Cortex-M4 `svc` instruction needs no setup beyond a vector table entry. `SYSCALL` is
configured entirely through model-specific registers (MSRs): `IA32_LSTAR` holds the entry
address, `IA32_STAR` the selectors, `IA32_FMASK` the flags to clear on entry, and `EFER.SCE`
switches the instruction on (that is the low bit of `0xd01` above).

The important register is the flag mask. `SYSCALL` does not switch stacks: privileged code starts
on whatever `rsp` the user left, which may point anywhere. If interrupts stayed on, an interrupt
could arrive on that pointer. So `fmask` names the interrupt flag, and a `static_assert` refuses a
mask without it.

The other piece is the GS base. Each core has a small `cpu_block` (the running thread's kernel
stack top, a parking slot for the user `rsp`, the core id). `ring3_cpu_init` writes its address
into `IA32_GS_BASE`. While a thread runs at ring 3 the `swapgs` instruction keeps it parked in
`IA32_KERNEL_GS_BASE`, which ring 3 cannot write, and the entry brings it back.

`ring3_cpu_init` also sets SMEP and SMAP in CR4 where CPUID offers them: with them, a ring 0
fetch from a user page or data access to one faults, so the kernel can reach a task's memory
only through the kernel-half view the copy functions use. The banner names what it got,
`uaccess smep smap`, and that is the `0x300000` in the `CR4` value above. One flag
could still undo it: `RFLAGS.AC` set lifts SMAP, ring 3 can set it, and an interrupt arrives with
it. `fmask` names it for `SYSCALL`, and the interrupt entry starts with `push $2; popfq`, which
clears it along with the direction flag.

**Try it:** in the `monitor info registers` output above, the `GS` line has base `0x4c7d40`, and
`info symbol 0x4c7d40` gives
`kickos::x86_64::(anonymous namespace)::g_cpu in section .bss`: core 0's `cpu_block`. (Two
different arrays in two files are both called `g_cpu`; this one is in `ring3_x86_64.cc`.)

**Why, and the contract:** [Reference: invariants, `syscall-in-priv-thread-context`](../reference/invariants.md)

### Stop 6: adopting the firmware's page tables
**Where:** `arch/x86/x86_64/aspace_x86_64.cc`, `kickos::x86_64::aspace_init`,
`arch_aspace_create`, `arch_aspace_activate`, `arch_aspace_user_offset`;
`arch/x86/x86_64/apprel_x86_64.cc`, `kickos::x86_64::app_relocate`; `kernel/mem/aspace.cc`,
`aspace_activate_for`

The Cortex-M4 protects memory with MPU regions. On x86_64 paging is mandatory in 64-bit mode, so
the port uses it. The firmware already built a full identity map, and KickOS adopts it as the
*kernel half* rather than building its own: `aspace_init` reads CR3, checks that the map really
is one-to-one over the image, checks that no leaf in it is reachable from ring 3 (the "user" bit
is clear all the way down), and refuses global pages (they would survive a CR3 reload). Then it
picks the first empty top-level slot above slot 0 as the start of the *user half*.

A task's address space (`arch_aspace_create`) is a fresh top-level table whose entries are copies
of the firmware root's, so the kernel half is shared by every space. A task reaches a physical
page at its physical address plus `arch_aspace_user_offset`, the base address of that first empty
slot. In this run the firmware's map fills the first two 512 GiB slots, so the offset is
`0x10000000000` (1 TiB). The app's code and data are in the same PE file as the
kernel, so they too are reached at that offset, and every absolute pointer stored in the app
window must point at the alias, not at the loader's address. `app_relocate` walks the image's
retained base-relocation records once, before the first space exists, and adds the offset to
each such word.

Switching spaces is a CR3 write (`install_root`), done by `aspace_activate_for` in `switch_book`,
where the Cortex-M4 only stashes its MPU regions for the physical switch to commit
([10, Stop 7](10-the-mmu.md#stop-7-installing-the-space-at-the-first-switch) explains why a page-table
root can be written that early). PCIDs (address-space tags) are not used, so every
CR3 write flushes the non-global translations. The table edits themselves go through the shared
walker in `arch/common/aspace_walk.h`, which [the MMU chapter](10-the-mmu.md) walks on arm64.

**Try it:** stop at root's first ring 3 instruction (Stop 8 shows how), then `p/x $cr3` and
`monitor info mem`. You should see CR3 `0x1814000` (root's own table, not the firmware's
`0x1f401000`) and, at the end of the map:

```
000000001fe41000-0000010000000000 000000ffe01bf000 -rw
00000100004fd000-000001000050c000 000000000000f000 ur-
000001000050c000-0000010000515000 0000000000009000 urw
0000010001822000-0000010001832000 0000000000010000 urw
```

Everything below 1 TiB is the kernel half, with no `u`: ring 3 cannot touch it. Above it are the
only three user mappings: the app's code and read-only data, its writable data, and root's 64 KiB
stack. (The app text at `0x100004fd000` is `0x4fd000`, where `.apptext` was loaded, plus 1 TiB.)

**Why, and the contract:** [Book: protection follows the CPU](../book/protection-follows-the-cpu-not-the-schedulers-intent.md),
[Reference: porting, "The map editor's acquire pair"](../reference/porting.md)

### Stop 7: the timer that must be measured
**Where:** `arch/x86/x86_64/apic_x86_64.cc`, `kickos::x86_64::apic_init`, `calibrate`,
`clock_now`, `timer_arm`; `arch/x86/chip/q35/chip_q35.cc`, `kickos_x86_ref_spin`;
`arch/x86/x86_64/arch_x86_64.cc`, `arch_clock_now`, `arch_timer_arm`

The Cortex-M4's SysTick counts at a frequency the chip states. Every x86 core has a *local APIC* (its
private interrupt controller), which contains a one-shot countdown timer, and every core has the
TSC, a 64-bit cycle counter. Neither frequency can be read on this processor model. So
`apic_init` measures both against the one clock whose rate is fixed by the PC standard: the old
i8254 PIT at 1193182 Hz. `calibrate` starts the APIC countdown masked, spins
`kickos_x86_ref_spin` for 40000 PIT ticks, reads how far the countdown and the TSC moved, and
scales.

After that, the time base and the timer are simple. `clock_now` scales the TSC to nanoseconds;
being 64 bits, it needs no software wrap extension. A thread reads the same clock without
entering the kernel: `ring3_cpu_init` clears `CR4.TSD` on every core, so `rdtsc` runs at ring 3,
and `kos_clock_now` (`user/src/syscall_stubs.cc`) applies the same scale. The rate it scales by is
the one `apic_init` measured, answered by `KOS_SYS_CPU_CLOCK_HZ` and seated by `kickos_clock_seat`
in each address space before its constructors run. `timer_arm` turns a deadline into a count
for the APIC's 32-bit initial-count register, writing at least 1, because zero stops the timer
rather than firing it. The timer delivers vector `0x30`. `apic_init` prefers *x2APIC* mode,
where the APIC registers are MSRs; the four-core build requires it.

**Try it:** `break 'kickos::x86_64::timer_arm(unsigned long)'`, `continue`, `p $rdi`, `bt 2`. You
should see a deadline in nanoseconds (it differs from run to run) and its caller, the tickless
kernel's re-arm:

```
Thread 2 hit Breakpoint 2, 0x000000000041aa48 in kickos::x86_64::timer_arm(unsigned long) ()
$1 = 2005489360
#1  0x00000000004070f2 in kickos::ktime_rearm(kickos::Thread const*, kickos::Held) ()
```

Then `delete`, `break kickos_x86_64_isr if *(long long*)($rdi+120) == 0x30` (offset 120 is the
`vector` field of the frame), `continue`, `p/x *(long long*)($rdi+136)` (the interrupted `rip`),
`p/x *(long long*)($rdi+144)` (its `cs`) and `info symbol *(long long*)($rdi+136)`:

```
Thread 2 hit Breakpoint 3, 0x000000000041a556 in kickos_x86_64_isr ()
$2 = 0x41a554
$3 = 0x8
arch_idle_wait + 2 in section .text
```

The timer woke an idle core, right after its `hlt` (`arch_idle_wait` is `sti; hlt; cli`).

**Why, and the contract:** [Book: the time base](../book/the-time-base-a-monotonic-clock-you-can-trust.md),
[the sleep chapter](03-sleep.md)

### Stop 8: entering the first thread
**Where:** `arch/x86/x86_64/arch_x86_64.cc`, `arch_context_init`, `arch_start`,
`publish_current`; `arch/x86/x86_64/switch.S`, `kickos_x86_64_start`;
`arch/x86/x86_64/trap_x86_64.S`, `kickos_x86_64_resume`

On the Cortex-M4 the first thread's frame, fabricated by `arch_context_init`, looks like what
PendSV would have saved, and `arch_start` pends PendSV so that an exception return starts it. x86_64 does the same with one frame
format for everything: `struct trap_frame`, the 15 general registers, the vector and error code,
and the five words `iretq` pops (`rip`, `cs`, `rflags`, `rsp`, `ss`). An interrupt builds it,
the voluntary switch builds it, and `arch_context_init` fabricates it. Every resume is the same
`kickos_x86_64_resume` epilogue ending in `iretq`.

The frame carries `cs` and `ss`, so it decides the privilege level the thread starts at.
`arch_context_init` therefore places an unprivileged thread's frame on the thread's *kernel*
stack (`ctx->kernel_sp`), where the thread itself can never write, with `cs = 0x23`,
`ss = 0x1b` and `rflags = IF | bit 1`. That `rflags` is the first time interrupts are ever
enabled on the core. `arch_start` publishes the thread (`publish_current`: the TSS `rsp0`, the
`cpu_block` kernel stack top, the I/O bitmap, the FS base) and jumps to the epilogue:

```asm
    addq    $16, %rsp
/* The pair of the entry's swap, tested on the FRAME's cs: a switch resumes a frame some other
 * entry built, so what matters is the level this iretq delivers control to. */
    testb   $3, 8(%rsp)
    jz      .Lresume_same_level
    swapgs
.Lresume_same_level:
    iretq
```

**Try it:** `disassemble kickos_x86_64_resume` shows the `iretq` at `0x41d9d5` in this build.
`break *0x41d9d5 if *(long long*)($rsp+8) == 0x23` stops only on a return to ring 3. `continue`,
`x/5gx $rsp`, `stepi`, then `p/x $rip`, `p/x $cs`, `p/x $cr3`, `p/x $k_gs_base`:


### Stop 9: the syscall
**Where:** `arch/x86/x86_64/switch.S`, `arch_syscall`, `kickos_x86_64_syscall_entry`;
`kernel/syscall/syscall.cc`, `syscall_dispatch`

The user stub is three instructions, placed in an `.apptrap` section so that the task can fetch
it from the app window:

```asm
arch_syscall:
arch_syscall64:
    movq    %rcx, %r10
    syscall
    ret
```

`syscall` overwrites `rcx` (with the return address) and `r11` (with the flags), so the stub
moves the fourth argument out of `rcx` first. Now the important difference from `svc`. `svc`
makes the Cortex-M4 hardware push eight registers onto a stack the kernel controls. `SYSCALL` pushes
nothing and does not change `rsp` at all: the first privileged instruction runs on the user's
stack pointer. So the first three instructions of the entry are chosen to never use it:

```asm
kickos_x86_64_syscall_entry:
    swapgs
    movq    %rsp, %gs:KOS_CPU_USER_RSP
    movq    %gs:KOS_CPU_KERNEL_SP, %rsp
```

`swapgs` brings back the per-core block, the user `rsp` is parked in it, and the calling thread's
own kernel stack top is loaded. From here the entry pushes a full `trap_frame` (with `cs` and `ss`
stamped as ring 3, vector `0x100`), cleans the flags the thread will get back, and calls
`syscall_dispatch` with the arguments moved from the frame. Just as on the Cortex-M4 after
`svc_trampoline`, dispatch runs in privileged thread context on the thread's own stack, so it may
block. The return is not `SYSRET`: the entry stores the result into the frame's `rax` and jumps to
the same `kickos_x86_64_resume` epilogue, whose `iretq` restores the user `rsp` from the frame.

**Try it:** the first syscall of the hello app's `main`. Its text runs at its link address plus
1 TiB, in a space that does not exist yet when you set the breakpoint, so the breakpoint is a
hardware one; four cores take syscalls, so the rest of the walk stays on the thread that hit it:
`hbreak *(0x10000000000 + (unsigned long long)&kickos_app_main)`, `continue`,
`set $t = $_thread`, `delete`, `eval "break kickos_x86_64_syscall_entry thread %d", $t`,
`continue`, then `p/x $cs`,
`p/x $rdi`, `p/x $rcx`, `p/x $r11`, `p/x $rsp`, `p/x $gs_base`, `x/gx $rsp`; then `stepi 3`,
`p/x $rsp`; then `delete`, `eval "break syscall_dispatch thread %d", $t`, `continue`, `p $rdi`,
`finish`, `p/x $rax`:

```

$2 = 0x32                <- rdi: syscall number 50
```

### Stop 10: the context switch
**Where:** `arch/x86/x86_64/arch_x86_64.cc`, `arch_switch`, `kickos_x86_64_isr`;
`arch/x86/x86_64/switch.S`, `kickos_x86_64_switch_now`; `arch/x86/x86_64/trap_x86_64.S`,
`kickos_x86_64_trap_common`

The Cortex-M4 always defers: `arch_switch` pends PendSV, and the swap happens in that lowest-priority
exception. x86_64 has no such exception, and it takes two routes depending on where the switch
was decided:

```cpp
void arch_switch(struct arch_context* from, struct arch_context* to)
{
    CpuState& cpu = local_state();
    if (cpu.isr_depth != 0)
    {
        // Deferred, which arch.h permits: the interrupted thread's state is already in the
        // frame the entry built, so the swap is two stores at the exception exit. `from` is
        // dropped here; see g_ctx_current.
        cpu.switch_to = to;
        return;
    }
    // ...
    publish_current(to);
    kickos_x86_64_switch_now(from, to);
}
```

From thread context (a semaphore wait that blocks, a sleep), `kickos_x86_64_switch_now` builds a
`trap_frame` around its own return address, as if an interrupt had arrived there, saves the
vector state with `xsave64`, swaps `rsp`, restores the incoming thread's vector state and jumps
to the epilogue. From an interrupt (the timer woke a higher-priority thread), `arch_switch` only
records the target; `kickos_x86_64_isr` then saves the vector state, records the interrupted
frame as the outgoing thread's `sp`, and returns the incoming thread's frame instead, which the
common entry pops. Both paths end in the same `iretq`.

The cost is the Book's point about hardware stacking: the Cortex-M4 hardware saves eight words and the
switch saves nine more; here the software saves all 15 general registers plus an 832-byte XSAVE
area. Above one core, both paths call `kickos_switch_unlock` once the outgoing frame is complete
(see [the multicore chapter](11-multicore.md)). An interrupt whose last booked switch names the
very thread it interrupted swaps nothing, so `kickos_x86_64_isr` calls `kickos_switch_unlock`
itself and returns the same frame.

**Try it:** `break kickos_x86_64_switch_now`, `continue`, `bt 2`, `p/x $rsi`,
`x/22gx *(long long*)$rsi`. In this run the first voluntary switch was core 0 handing the CPU to
its idle thread. The incoming context's saved frame is the one `arch_context_init` fabricated for
idle; its last six words are:

```
#1  0x0000000000410db8 in kickos::(anonymous namespace)::pick_and_seat(...) ()
0x180ffc8:  0x0000000000000000  0x0000000000403849   <- error, rip = idle_entry
0x180ffd8:  0x0000000000000008  0x0000000000000202   <- cs (ring 0), rflags
0x180ffe8:  0x000000000180fff8  0x0000000000000010   <- rsp, ss
```

**Why, and the contract:** [Book: context switching](../book/context-switching-and-the-silicon-contract.md),
[Reference: invariants, `arch-switch-may-defer`, `deferred-switch-lowest-band`](../reference/invariants.md)

### Stop 11: the interrupt controller is software
**Where:** `arch/x86/x86_64/arch_x86_64.cc`, `arch_irq_mask`, `arch_irq_unmask`,
`arch_irq_inject`, `dispatch_doorbell`, `arch_irq_window`;
`arch/x86/x86_64/include/kickos/arch/irq_inline.h`, `arch_irq_save`, `arch_irq_restore`;
`arch/x86/x86_64/desc_x86_64.cc`, `tss_load_ports`

On the Cortex-M4 the NVIC masks, latches and prioritises device lines. A PC routes device interrupts
through an I/O APIC, which this port does not drive: the `q35` chip file names no device line
(`platform/q35/chip.yaml`). The kernel's lines are a software controller: two 32-bit bitmaps (masked,
pending) and a route per line. Raising a line (`arch_irq_inject`) sets a bit in the target core's
doorbell word and sends the local APIC vector `0x31` to that core; the handler drains the word and
calls `kickos_isr_irq` per line. A raise on a masked line is latched and delivered at unmask,
which is the same contract the NVIC keeps in hardware.

The critical section is the interrupt flag: `arch_irq_save` is `pushfq; pop; cli` and returns
only the IF bit, and `arch_irq_restore` executes `sti` only if that bit was set, so nesting works.
There is no priority band to set, and no equivalent of BASEPRI: on x86_64 a critical section masks
every maskable interrupt.

Devices on a PC are often reached through I/O *ports*, a second address space with `in`/`out`
instructions. A thread granted a port window gets those ports opened in the I/O permission bitmap
behind its core's TSS, and `publish_current` reloads the bitmap on each switch
(`tss_load_ports`, which compares first and does nothing when the set is unchanged).

**Try it:** once the threads run (for example `break syscall_dispatch`, `ignore 2 300`,
`continue`), `x/wx &'(anonymous namespace)::g_irq_masked'`. You should see
`0x4204d0 <_ZN12_GLOBAL__N_1L12g_irq_maskedE>: 0xffffffff`: every line masked, since `hello`
claims none. A driver's unmask clears its bit.

**Why, and the contract:** [Book: a masked interrupt is latched](../book/a-masked-interrupt-is-latched-not-lost.md),
[the interrupt chapter](07-interrupt-to-a-driver.md), [Reference: porting, `arch_irq_*`](../reference/porting.md)

### Stop 12: the other three cores
**Where:** `arch/x86/x86_64/smp_trampoline.S`, `kickos_x86_64_ap_begin`;
`arch/x86/x86_64/smp_boot_x86_64.cc`, `kickos_x86_64_ap_prepare`, `kickos_x86_64_ap_start`;
`arch/x86/chip/q35/chip_q35.cc`, `ap_main`

The firmware only brings up one core, the bootstrap processor. The others ("application
processors") are still in 16-bit real mode, waiting for an INIT and a startup message from a local
APIC. The startup message can only point at a 4 KiB page below 1 MiB, so `efi_main` reserves one
while firmware still owns memory (`kickos_x86_64_ap_reserve`), and `arch_init` copies a small
trampoline there and patches in CR3, CR4, a stack and the 64-bit entry address. This is the one
place where KickOS itself climbs to long mode: the trampoline loads a tiny GDT, sets CR4, loads
the boot CR3, sets `EFER.LME`, and sets protection and paging in CR0 in one write, then a far
jump lands in 64-bit code. Each core then runs `ap_main`: enable the vector state, its own GDT and
TSS (`desc_init_secondary`), its own syscall MSRs and GS block (`ring3_cpu_init`), its own local
APIC, and park until the kernel needs it.

**Try it:** at the same stop as above, `info threads`. You should see four CPUs: the one that
hit the breakpoint (which core it is varies from run to run) and three peers asleep in
`arch_idle_wait`:

```

* 2    Thread 1.2 (CPU#1 [running]) 0x0000000000415adf in syscall_dispatch ()
  3    Thread 1.3 (CPU#2 [halted ]) 0x000000000041a554 in arch_idle_wait ()
  4    Thread 1.4 (CPU#3 [halted ]) 0x000000000041a554 in arch_idle_wait ()
```

**Why, and the contract:** [the multicore chapter](11-multicore.md)

### Stop 13: when a thread faults
**Where:** `arch/x86/x86_64/fault_x86_64.cc`, `kickos_x86_64_trap`;
`arch/x86/x86_64/arch_x86_64.cc`, `arch_fault_is_user_thread`, `arch_fault_redirect_to_exit`

Every vector the backend does not own (anything other than the timer, the doorbell and the
spurious vector) falls to the fault path. x86_64 has no register saying which privilege level was
interrupted; the only record is the `cs` the hardware pushed, which is memory. So
`arch_fault_is_user_thread` first checks that the frame sits on the running thread's own kernel
stack, which is where the CPU puts a ring 3 fault's frame (it loaded `rsp0` from the TSS), and
only then believes the `cs` word. To kill the thread, `arch_fault_redirect_to_exit` rewrites all
five `iretq` words, ring 0 selectors included, so the next `iretq` lands in
`kickos_thread_fault_exit`. A page fault also reports `cr2`, the faulting address.

**Try it:** this stop is read from the code; [9. Fault and kill](09-fault-and-kill.md) runs the
same kill on the reference walk.

**Why, and the contract:** [the fault chapter](09-fault-and-kill.md),
[Reference: porting, "Fault-isolation contract"](../reference/porting.md)
