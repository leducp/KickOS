# 16. RX: the same walk on a Renesas RXv3

This chapter walks the port to the Renesas RX72M, an RXv3 core with a double-precision FPU, an
interrupt controller called the ICU and a small memory protection unit. It follows the stops of
the reference walk on the Cortex-M4 ([power-on](01-power-on.md) and
[the first syscall](02-first-syscall.md)) and shows only what RX does differently and why. By
the end you will have seen two vector tables instead of one, a syscall that is a numbered
software interrupt, a context switch that is always deferred and always saves everything, a
timer built from two counters, and an MPU that checks user mode only, which is why the trap code
checks every stack pointer a thread hands it.

The concepts are in the Book: [Context switching and the silicon contract](../book/context-switching-and-the-silicon-contract.md),
[Interrupts and traps](../book/interrupts-and-traps.md),
[The syscall path](../book/the-syscall-path-trap-dispatch-return.md) and
[Alignment across the syscall boundary](../book/alignment-across-the-syscall-boundary.md). The arch
seam is in [Reference: porting](../reference/porting.md), which also gives the RX MPU register
encodings.

## How this port differs, in one table

| Stop | Cortex-M4 (reference) | RXv3 |
|---|---|---|
| Reset | vector table at address 0: initial SP, then the reset PC | a fixed table at the top of memory; its last word is the reset PC, and software sets the stack |
| Vector tables | one, relocatable (VTOR) | two: a fixed exception table and a relocatable 256-slot interrupt table (INTB) |
| Two stacks | MSP and PSP, chosen by CONTROL | ISP and USP, chosen by PSW.U |
| Privilege | CONTROL.nPRIV | PSW.PM |
| Critical section | BASEPRI | PSW.IPL, set with `mvtipl` |
| Syscall | `svc`, hardware stacks 8 words | `int #1`, hardware stacks only PC and PSW |
| Deferred switch | PendSV, lowest priority | the software interrupt SWINT, lowest priority |
| Switch frame | 8 words by hardware, 9 by software | everything by software: 236 bytes with the FPU |
| Timer | SysTick | two compare-match timers: one free-running, one one-shot |
| Protection | PMSAv7 MPU, checks every mode | RX MPU, 8 regions of 16-byte pages, checks user mode only |

## The image, without an emulator

No emulator in this tree models the RX72M, so nothing here was run under gdb. Two kinds of
Try-it follow. The static ones read the linked image with the toolchain's `rx-elf-objdump` and
`rx-elf-nm`; they were checked on a build of the `rx72m` preset
(`cmake --preset rx72m -B build/rx72m`, then `cmake --build build/rx72m --target hello`), and
the addresses below come from that build. The live ones need the board and a debugger attached
through an E2 Lite; the tree has no recipe for that (the flashing guide covers only
[programming the board](../flashing.md)), so they say what to expect, not what a run printed.

One naming rule before you start: the RX ABI prefixes every C name with an underscore, so the
C function `syscall_dispatch` is `_syscall_dispatch` in `nm`, in the linker script, and in
`switch.S`.

### Stop 1: reset
**Where:** `arch/rx/chip/rx72m/startup.S`, `.fvectors`, `.ofsm`, `_start`;
`arch/rx/chip/rx72m/chip_rx72m.cc`, `rx_reset_handler`; `arch/common/crt_tail.h`,
`kickos_crt_tail`

On the Cortex-M4 the reset hardware reads two words from address 0: the initial main stack pointer and
the address of `Reset_Handler`. The RX reads one word: the reset vector, which is the last word
of a fixed table at the very top of the address space (`0xFFFFFFFC`). It sets no stack pointer.
So `_start` has two instructions of real work before C can run:

```asm
_start:
    mov.l   #_istack, r0          /* ISP = top of SRAM (U=0 at reset -> R0 = ISP) */
    mov.l   #_g_rvectors, r5
    mvtc    r5, intb              /* relocatable interrupt table base */
    bra.a   _rx_reset_handler     /* C runtime init + kmain (noreturn) */
```

`R0` is the stack pointer on RX, and which stack it means depends on the PSW's `U` bit: with
`U = 0` it is the *interrupt stack* (ISP), with `U = 1` the *user stack* (USP). This is the same
idea as the Cortex-M4's MSP and PSP. Reset leaves `U = 0`, so the first line sets the ISP to the top of
SRAM. The second points `INTB` at the interrupt table (Stop 3).

Before that code even runs, the chip reads the *option-setting memory* (`.ofsm`), four words in a
special flash area that pick the byte order and say whether the watchdogs start. KickOS writes all
ones, the values that mean little-endian and watchdogs off, so the boot never depends on what an
erased flash happened to hold.

`rx_reset_handler` is then the same C startup the reference walk uses: `kickos_ranges_init`
copies `.data` and zeroes `.bss`, and `kickos_crt_tail` runs the kernel's constructors, calls
`arch_init`, and enters `kmain`.

**Try it:** `rx-elf-objdump -s -j .fvectors hello` prints the fixed table. Its last line ends with
the reset vector, stored little-endian:

```
 fffffff0 92f1c0ff 92f1c0ff 92f1c0ff 68f1c0ff  ............h...
```

`68f1c0ff` is `0xffc0f168`, and `rx-elf-nm hello | grep ' _start$'` prints
`ffc0f168 T _start`. The other words in that line are `_rx_trap`, the catch-all reporter.

**Why, and the contract:** [Book: interrupts and traps](../book/interrupts-and-traps.md)

### Stop 2: the chip comes up
**Where:** `arch/rx/chip/rx72m/chip_rx72m.cc`, `arch_init`; `arch/rx/rxv3/arch_rxv3.cc`,
`kickos_rxv3_init`

`arch_init` is where the RX differs from the Cortex-M4 most in shape, not in idea. Many RX control
registers are locked by a protect register (`PRCR`) and must be unlocked around a write
(`unlock_registers`). The clock is switched to the 240 MHz PLL, and each peripheral the kernel
uses is released from its *module stop* state (`MSTPCRA`/`MSTPCRB`), the RX's per-peripheral
power switch. The frequency is then read back from the clock registers rather than assumed, and
the timer rate is derived from it: the compare-match timers count at the peripheral clock
divided by 8 (`kickos_rx_timer_hz`).

`kickos_rxv3_init` then sets up the core side: the priority of the deferred-switch interrupt
(Stop 7) and the free-running counter the clock reads (Stop 8).

**Why, and the contract:** [Reference: porting, "Clock retune"](../reference/porting.md)

### Stop 3: two vector tables
**Where:** `arch/rx/chip/rx72m/startup.S`, `_g_rvectors` (`.rvectors`), `_g_fvectors`
(`.fvectors`), `_rx_ex_access` and the other exception shims; `arch/rx/rxv3/arch_rxv3.cc`,
`kickos_rx_default_irq`

The Cortex-M4 has one table: sixteen core exceptions, then one word per external interrupt. RX splits
this in two.

- The **fixed vector table**, at `0xFFFFFF80`, holds the *exceptions*: privileged instruction,
  access violation (the MPU), undefined instruction, address error, floating point, NMI, and reset.
  Each KickOS entry is a tiny shim that puts a cause code in `r1` and calls
  `kickos_rx_fault_report`.
- The **relocatable vector table**, wherever `INTB` points, has 256 slots, and it serves two
  masters. A peripheral interrupt `n` arrives through slot `n`. And the instruction `int #n`
  also jumps through slot `n`. So the syscall is simply `int #1` with slot 1 holding the
  syscall trap. Slots 0 to 15 have no peripheral behind them, which is why a low number is safe.

KickOS's table, from the top of `startup.S`: slot 1 is the syscall trap, slot 26 is `SWINT2` (the
doorbell that delivers software-raised lines), slot 27 is `SWINT` (the deferred switch), slot 30 is
the timer compare match, and slots 86 and 87 are the console UART. Every other slot goes to
`kickos_rx_default_irq`, which asks the chip code to find the source. It has to ask: unlike the
Cortex-M4, where `IPSR` says which exception is running, an RX handler cannot read the vector it was
entered through.

**Try it:** `rx-elf-objdump -s -j .rvectors hello | head -3`, then compare with
`rx-elf-nm hello`:

```
 ffc00000 92f1c0ff 01f3c0ff 902cc0ff 902cc0ff  .........,...,..
```

Slot 0 is `0xffc0f192` (`_rx_trap`), slot 1 is `0xffc0f301` (`_kickos_rx_syscall_trap`), and
slot 2 onwards is `0xffc02c90` (`_kickos_rx_default_irq`). The table sits at the start of flash,
`0xffc00000`.

**Why, and the contract:** [Book: interrupts and traps](../book/interrupts-and-traps.md)

### Stop 4: the PSW, privilege and the critical section
**Where:** `arch/rx/rxv3/regs.h`, `PSW_I`, `PSW_U`, `PSW_PM`, `IPL_LOCK`, `IPL_DEVICE`,
`IPL_PENDSW`; `arch/rx/rxv3/arch_rxv3.cc`, `arch_irq_save`; `arch/rx/rxv3/switch.S`,
`_arch_irq_restore`

One register, the PSW (processor status word), holds what the Cortex-M4 spreads over CONTROL, PRIMASK
and BASEPRI:

- `PM` (bit 20): 0 is supervisor, 1 is user. This is the privilege bit.
- `U` (bit 17): which stack `R0` means, ISP or USP.
- `I` (bit 16): interrupts enabled.
- `IPL` (bits 27 to 24): the current interrupt priority level. An interrupt is accepted only if its
  level is above `IPL`.

The critical section raises `IPL` to 12 with one instruction, `mvtipl #12`, and returns the old
level. Device lines are programmed at level 4, the deferred switch at level 1, both below 12, so
a critical section holds them all off. This is the same banding the Cortex-M4 does with BASEPRI. Unlike
the Cortex-M4's `msr basepri`, `mvtipl` needs no barrier after it to take effect.

Every KickOS thread runs on its own USP: a kernel thread with `PSW = I | U`
(`PSW_THREAD_KERNEL`), a user thread with `PSW = I | U | PM` (`PSW_THREAD_USER`). The ISP is only
for boot and interrupt entry, because accepting an interrupt or exception clears `U`, whatever was
running.

`_arch_irq_restore` is in assembly for a reason worth knowing: restoring `IPL` is the moment a
switch pended under the lock fires (Stop 7), and the switcher will push the double-precision
registers 8 bytes at a time right below the current stack pointer. So the restore aligns `R0` down
to 8 for the one instruction that writes the PSW back, and puts it back after.

**Try it:** `rx-elf-objdump -d hello | grep -A3 '<_arch_irq_save>:'` shows `mvfc psw, r1` then
`mvtipl #12`.

**Why, and the contract:** [Reference: invariants, `irqlock-nesting-safe`, `device-irq-in-maskable-band`](../reference/invariants.md)

### Stop 5: entering the first thread
**Where:** `arch/rx/rxv3/arch_rxv3.cc`, `arch_context_init`; `arch/rx/rxv3/switch.S`,
`_arch_start`, `_kickos_rx_restore`; `arch/rx/rxv3/include/kickos/arch/context.h`,
`struct arch_context`

As on the Cortex-M4, the first thread starts by "returning" into a frame that looks exactly like what
the switcher saves. The RX frame is the full register set, low address to high:

```cpp
//   [+0 A0LO][+4 A0HI][+8 A0GU][+12 A1LO][+16 A1HI][+20 A1GU][+24 FPSW]
//   [+28 R1=arg .. +84 R15][+88 PC=entry][+92 PSW]
```

with the double-precision FPU registers below it when the build uses them, and one more word above
it: the address a returning `entry` falls into (`kickos_user_thread_return` for a user thread,
which leaves through the exit syscall). `A0` and `A1` are the two 72-bit accumulators the RX
multiply-accumulate instructions use. A user thread's frame carries `PSW_THREAD_USER`.

The frame lives on the thread's OWN stack, not on a kernel stack as on x86_64 (see
[chapter 15](15-x86_64.md)). The reason is the return instruction. `rte` pops PC then PSW from
`R0`, and once the popped PSW sets `U`, `R0` IS the thread's USP. So the stack the thread resumes
on is, by construction, the stack the frame came off. `_arch_start` sets `U`, loads `R0` from the
first thread's `sp`, and branches to `_kickos_rx_restore`, which commits the thread's MPU regions,
pops the frame and ends in `rte`.

The context itself (`struct arch_context`) is small: the saved `sp`, the stack bounds, and the
top of the thread's kernel stack (`kernel_sp`, Stop 6). Everything else is in the frame.

**Try it:** with a debugger on the board, `break arch_start`, `continue`, then step to the `rte`
at the end of `_kickos_rx_restore` and read `$psw`. It should be `0x00130000` (I, U and PM set,
IPL 0) for the unprivileged root thread, and the PC after the `rte` should be
`kickos_root_entry`.

### Stop 6: the syscall
**Where:** `arch/rx/rxv3/switch.S`, `_arch_syscall`, `_kickos_rx_syscall_trap`,
`_svc_trampoline`; `arch/rx/rxv3/include/kickos/arch/rx_trap_stack.h`;
`kernel/syscall/syscall.cc`, `syscall_dispatch`

The user stub is two instructions:

```asm
_arch_syscall:
_arch_syscall64:
    int     #1                 /* SYSCALL_VECTOR (regs.h) */
    rts                        /* return to caller, R1:R2 = result */
```

The arguments are already where the RX calling convention puts them (`R1` to `R4`, the fifth on
the stack), and `int` saves no general register, so no shuffling is needed. `int #1` pushes PC
and PSW on the ISP, clears `U` and `PM`, and jumps through slot 1.

From here the RX follows the same plan as the Cortex-M4. The Cortex-M4's `SVC_Handler` does not dispatch
inside the exception: it rewrites the stacked return address so that the exception return lands in
`svc_trampoline`, which runs privileged in thread mode and can block. `_kickos_rx_syscall_trap`
does the same with PC and PSW. It writes the user's PC and PSW onto the user stack (eight bytes),
replaces the stacked PC with `_svc_trampoline` and the stacked PSW with "supervisor, on the
USP", and executes `rte`. `_svc_trampoline` then moves `R0` to the top of the calling thread's own
kernel stack (`ctx.kernel_sp`), calls `syscall_dispatch`, and `rte`s back to the user's PC and
PSW with the result in `R1:R2`.

The trap begins with checks the Cortex-M4 does not need. Every store this code makes through the user's
stack pointer runs in supervisor mode, and the RX MPU checks user mode only. A thread could point
its USP one word above the bottom of its stack and have the kernel write, with full rights, into
the neighbouring thread's saved frame. So the trap checks that the USP is 4-aligned, that it is
inside the thread's stack, and that there is room below it for everything the trap and a switch
taken during the trap can write. `rx_trap_stack.h` derives each figure and
`tests/static/check_trap_redzone.sh` re-measures them.

There is one shortcut: when `R1` is `56` (`KOS_SYS_CALL_REG`), the trap saves the full switch frame
and calls `kickos_ipc_fastpath` directly, so a call and reply between two threads can hand over the
CPU without the generic path (see [call and reply](05-call-and-reply.md)).

**Try it:** `rx-elf-objdump -d hello | grep -A2 '<_arch_syscall>:'`:

```
ffc0f479 <_arch_syscall>:
ffc0f479:	75 60 01                      	int #1
ffc0f47c:	02                            	rts
```

and the start of `_kickos_rx_syscall_trap` is the alignment test: `mvfc usp, r15`, then
`and #3, r14` on a copy and a branch away if it is not zero. Live, `break syscall_dispatch` on
the board would show `$r1` holding the syscall number and `$psw` with `PM` clear and `U` set.

### Stop 7: the context switch
**Where:** `arch/rx/rxv3/switch.S`, `_arch_switch`, `_kickos_rx_pendsw`, `_kickos_rx_restore`;
`arch/rx/rxv3/regs.h`, `SWINT_VECTOR`, `IPL_PENDSW`

The Cortex-M4 pends PendSV and swaps in that exception. The RX does the same with its software
interrupt, `SWINT` (slot 27), at level 1, the lowest active level:

```asm
_arch_switch:
    mov.l   #_g_arch_next, r3
    mov.l   r2, [r3]           /* g_arch_next = to */
    mov.l   #ICU_SWINTR, r3
    mov.b   #1, [r3]           /* pend SWINT (deferred switch) */
    rts
```

`arch_switch` is always called under the kernel lock (IPL 12), so `SWINT` waits. It is taken
when the lock's `_arch_irq_restore` lowers the level, or when the last interrupt handler returns.
A voluntary block and a preemption therefore reach the same code and produce the same frame.

The difference is the size of that frame. On the Cortex-M4 the hardware has already pushed eight words
when PendSV starts, and the switcher adds nine. `int` and interrupt acceptance push only PC and
PSW, so `_kickos_rx_pendsw` saves everything itself: it moves PC, PSW and `R15` from the ISP to
the outgoing thread's USP, switches to the USP, and pushes `R1` to `R14`, `FPSW`, both
accumulators, and the 16 double-precision registers with their three control registers: 236 bytes.
Then it stores `R0` in the outgoing context, sets `g_arch_current` to the incoming one, loads its
`sp`, and falls into the same `_kickos_rx_restore` that started the first thread. This is the
Book's "no hardware stacking" case: one simple frame format for every switch, at the price of a
full save on every switch.

Two RX details. Before building the frame on the outgoing USP, the switcher checks it the way the
syscall trap does, accepting a USP inside the thread's kernel stack only if the interrupted PSW
says supervisor (a thread preempted in the middle of a syscall). And it clears the SWINT request
flag by hand: a software interrupt's flag survives acceptance, and leaving it set re-fires the
switcher forever.

**Try it:** `rx-elf-objdump -d hello | grep -A6 '<_arch_switch>:'` shows the four stores and the
`rts` above, with `ICU_SWINTR` resolved to `#0x872e0`. Live: `break _kickos_rx_pendsw` and print
`$isp` and `$usp`; you are on the ISP, and the outgoing thread's USP is the address its frame will
be written below.

### Stop 8: the timer and the clock
**Where:** `arch/rx/rxv3/arch_rxv3.cc`, `now_cycles`, `arch_clock_now`, `arch_timer_arm`,
`arch_timer_disarm`, `kickos_rx_timer_isr`, `kickos_rxv3_init`

The RX72M has no core timer like SysTick. KickOS uses two units of the peripheral *compare match
timer W* (CMTW):

- **CMTW1** counts up freely from 0 to `0xFFFFFFFF` and wraps. It is the clock. `now_cycles`
  extends it to 64 bits in software: if the counter is below the last value seen, a wrap happened.
  That only works if every wrap is seen, so something must read the clock at least once per wrap
  period; the Book chapter on the time base explains the fragility.
- **CMTW0** is the one-shot timer. `arch_timer_arm` converts the deadline into a count, stops the
  unit, zeroes its counter, writes the compare value, and starts it. When the counter reaches the
  compare value the unit raises vector 30.

Resetting the counter on every arm means the deadline is relative to the moment of the arm. If the
kernel re-armed the same far deadline on every context switch, the counter would keep restarting
and never reach it. `ktime_rearm` prevents that by skipping the call when the programmed deadline
has not changed.

The interrupt handler is plain C with GCC's `interrupt` attribute, which saves the general
registers and returns with `rte`. There is no `IPSR` to say "in an interrupt", so each first-level
handler counts itself in `g_in_isr`, and `arch_in_isr` reads that counter. The syscall trap does
not count, so `syscall_dispatch` is not "in an interrupt", as the contract requires.

**Try it:** `rx-elf-objdump -d hello`, find `<_kickos_rx_timer_isr>:`. It opens with
`pushm r1-r15`, increments the counter, calls the kernel's timer entry, decrements, and ends with
`popm r1-r15` and `rte`.

**Why, and the contract:** [Book: the time base](../book/the-time-base-a-monotonic-clock-you-can-trust.md),
[the sleep chapter](03-sleep.md)

### Stop 9: the RX MPU
**Where:** `arch/rx/rxv3/arch_rxv3.cc`, `arch_mpu_apply`, `kickos_arch_mpu_commit`,
`arch_mpu_region_encodable`, `arch_fault_is_user_thread`, `arch_fault_redirect_to_exit`;
`arch/rx/rxv3/rx_mpu_encode.h`, `kickos::rxv3::rx_mpu_encode`

The RX MPU has eight regions. Each is a start page and an inclusive end page in 16-byte pages,
plus three permission bits (read, write, execute) that apply to USER mode only. A ninth,
background region covers everything else, and KickOS keeps its permissions at zero: overlapping
regions OR their permissions together, so any nonzero background would quietly grant every user
thread everything. Supervisor code is never checked.

The commit follows the Cortex-M4's shape. `arch_mpu_apply` only remembers the incoming thread's encoded
regions; `_kickos_rx_restore` calls `kickos_arch_mpu_commit` after the physical swap and before the
`rte` that drops into the thread, so the outgoing thread keeps its own regions until it has stopped
running. The commit writes only the slots that differ from what the MPU holds, writes the start
page before the end page (which carries the valid bit, so a slot is never valid with stale bounds),
and reads an MPU register back, which the manual requires before the next `rte` relies on the new
regions. A region the 16-byte pages cannot express exactly is left invalid, never widened.

A user access outside the regions raises the access exception at fixed offset `0x54`. The fault
code reads `MPESTS` (was it a fetch or a data access, a read or a write) and `MPDEA` (the data
address), then rewrites the stacked PC and PSW so the `rte` lands in `kickos_thread_fault_exit`,
supervisor on the thread's kernel stack. One RX trap: these exceptions cancel the faulting
instruction and restore the stack pointer, so a stack overflow looks like an in-bounds USP. The
code checks `MPDEA` against the stack bottom to tell.

**Try it:** `rx-elf-objdump -d hello | grep -A1 '<_kickos_rx_restore>:'` shows the restore
opening with `bsr.a` to `_kickos_arch_mpu_commit` (`0xffc0290c` in this build). Live: run the
`mpu_fault` app and the console should print the fault report with `MPESTS` and the address.

### Stop 10: the interrupt controller
**Where:** `arch/rx/rxv3/arch_rxv3.cc`, `arch_irq_mask`, `arch_irq_unmask`,
`arch_irq_inject`, `vector_to_ipr`, `kickos_rx_swint2`; `arch/rx/chip/rx72m/chip_rx72m.cc`,
`kickos_rx_group_arm`, `kickos_rx_dev_dispatch`

The ICU has three registers per source, like the NVIC: `IR` (request pending), `IER` (enabled,
eight sources per byte) and `IPR` (priority). Two things are different. First, `IPR` is shared:
several vectors can use one priority register, so `vector_to_ipr` maps the vector to its `IPR`
index instead of assuming they are equal. Second, many peripherals do not have a vector of their
own: they are members of a *group* interrupt, and the group's handler reads a status register to
find the member. KickOS numbers group members as logical lines above `GROUP_LINE_BASE` and arms a
group's vector only when one of its members is unmasked.

Software cannot pend a real peripheral line on RX. So lines below 32 are software lines: a mask
bit and a pending bit in memory, delivered through the second software interrupt, `SWINT2`
(`kickos_rx_swint2`). A raise on a masked line is latched and delivered at unmask, the same
contract the NVIC keeps in hardware.

**Why, and the contract:** [Book: a masked interrupt is latched](../book/a-masked-interrupt-is-latched-not-lost.md),
[the interrupt chapter](07-interrupt-to-a-driver.md)

### Stop 11: alignment and other RX quirks
**Where:** `arch/rx/rxv3/include/kickos/arch/rx_trap_stack.h`, `KICKOS_RX_TRAP_SP_ALIGN`;
`arch/rx/rxv3/switch.S`, `_arch_irq_restore`; `arch/rx/rxv3/emutls.cc`;
`arch/rx/rxv3/arch_rxv3.cc`, `arch_idle_wait`

A few RX facts bite a porter who comes from ARM:

- **`alignof(uint64_t)` is 4.** The RX ABI aligns 64-bit values to 4 bytes, where ARM and RISC-V
  use 8. Kernel code that checks a user pointer's alignment must ask the compiler (`alignof`), not
  hard-code 8; the Book chapter on alignment shows both ways to get this wrong.
- **Stacks are 4-aligned, and the trap insists.** The syscall trap and the switcher refuse a USP
  that is not a multiple of 4 (`KICKOS_RX_TRAP_SP_ALIGN`), since every store in the frame would
  then be misaligned too. The double-precision registers are better at 8, which is why
  `_arch_irq_restore` aligns `R0` to 8 around the PSW write (Stop 4).
- **Displacements are unsigned.** `disp[Rn]` addressing has no negative form, so `switch.S` always
  moves the pointer first and then uses a positive offset.
- **No thread pointer.** GNU RX has no native thread-local storage: every `thread_local` access
  calls `__emutls_get_address`, and `emutls.cc` provides a per-thread version in place of
  libgcc's single-threaded one.
- **Idle must be privileged.** `arch_idle_wait` is the `wait` instruction, which user mode may not
  execute. This is the one reason the idle thread on RX could not be unprivileged.

**Why, and the contract:** [Book: alignment across the syscall boundary](../book/alignment-across-the-syscall-boundary.md),
[Book: privilege is three axes](../book/privilege-is-three-axes-not-one-bit.md)
